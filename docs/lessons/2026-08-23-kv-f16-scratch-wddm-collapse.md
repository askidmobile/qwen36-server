# WDDM-коллапс decode на длинном контексте: диагностика и фикс

**Дата:** 2026-08-23
**Симптом:** Qwen3.6-35B-A3B IQ2_XXS на yttri-win (RTX 3060 12 GB): decode 36 tok/s
на коротком контексте → **2.4 tok/s при ctx ≈ 24K**, TTFT второго запроса 4+ минуты,
VRAM 97–98%. Пользователь видел те же «3–4 ток/с» в реальной работе.

## Root cause (цепочка из трёх факторов)

1. **CUDA default pool release-threshold = 0** (дефолт драйвера): каждый sync
   возвращает страницы ОС; decode hot path делает десятки аллокаций/шаг →
   page-map churn.
2. Наивный «retain всё» (threshold = MAX) тоже вреден: пул удерживает пиковые
   префилл-транзиенты навсегда — ранее измеренный 7x регресс при 98% VRAM.
3. **Решающий:** batched decode на каждом шаге каждого attention-блока вызывал
   `f16_prefix(kv_len)` — полную деквантацию q8→f16 префикса с fresh-аллокациями
   (`narrow().contiguous()`, ~48 MB на слот-шаг). При занятости 97%+ драйвер
   размещал эти страницы в WDDM shared memory → чтение/запись через PCIe на
   каждом шаге → коллапс ×12. С retain-порогом страницы мапились один раз под
   давлением — и **залипали в shared навсегда**, поэтому порог сам по себе не помог.

Диагностика осложнялась: `SLOTS=1` использует single-slot `CandleEngine`, а не
BatchedEngine (main.rs: `qwen35 && slots > 1`) — первые инструментальные прогоны
шли мимо целевого пути.

## Что сделано (candle-fork @ f6cac6b1)

- `mem_pool::set_release_threshold_mib()` — ограниченный порог: мелкие буферы
  переиспользуются, крупные транзиенты возвращаются системе. Сервер ставит 512 MiB
  (`QWEN36_MEMPOOL_RETAIN_MIB`).
- **Shared flat f16 scratch** на уровне ModelWeights: один буфер на модель
  (32K токенов = 32 MiB ×2 по умолчанию, `QWEN36_KV_SCRATCH_TOKENS`), выделяется
  лениво при первом decode, пока dedicated VRAM свободна → страницы закрепляются
  в дискретке. Заполнение чанками по 4096 токенов + zero-copy view для FA2
  (`narrow(0,0,n).reshape(...)` плоского буфера — физически contiguous).
  Fallback на старый путь при kv_len > cap.
- Сервер `BUDGET_FRAC 0.93 → 0.89`: постоянные ~1.35 GB dedicated-запаса, чтобы
  страницы пула не выталкивались в shared.

## Результаты (одинаковый протокол bench)

| ctx | до | после |
|-----|-----|-------|
| ~8K bench | 36.6 tok/s | 36.8 ✓ без регресса |
| ~6K | 30.4 | 28.9 (шум) |
| ~24K | **2.4** | **11.2 (×4.7)** |

## Остаток (Stage-2, следующий шаг)

Оставшиеся 11 vs 36 tok/s — compute dequant-fill на каждом шаге (чанки ×10 блоков).
Лечение: **инкрементальное f16-зеркало** — dual-write при `set_row`/
`shift_and_append`/`seed` (деквантация одной строки за раз), декод читает зеркало
zero-copy. Цена: +f16 к хранению KV (~+2×q8), нужно учесть в vram_plan.
Touchpoints: BatchedKvCache::{set_row, shift_and_append, copy_prefix_to},
seed_slot_batched, migrate-путь (6834).

## Уроки процесса

- В этом стеке два движка: SLOTS=1 → CandleEngine (single-slot path), SLOTS≥2 →
  BatchedEngine. Инструментируй тот, что реально работает у пользователя.
- WDDM: важен не только объём аллокаций, но и **момент первого размещения страниц** —
  размещённое под давлением остаётся в shared после освобождения давления.
- SSH-сессии на yttri-win имеют урезанный PATH: CUDA 12.4 runtime DLL нужны рядом
  с exe или через PATH-prepend (скрипты phase0_* уже делают; DLL скопированы в
  target\release).
