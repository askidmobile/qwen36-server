# План: MTP × CUDA-графы

**Спека:** [2026-08-27-mtp-cuda-graphs.md](../specs/2026-08-27-mtp-cuda-graphs.md)
**Дата:** 2026-08-27 (переписан после разведки по коду)
**Оценка:** 5–8 рабочих дней до включаемого MTP на 27B

## Главное: MTP уже работает и уже окупается

В коде, `scheduler.rs:89-90`, лежит замер, сделанный до нас:

```
27B IQ2_XXS, 128 токенов:
  baseline 18.6 ток/с
  K=2  →  22.8   (+23%)
  K=3  →  26.6   (+43%)
  K=4  →  15.1   (−19%)
```

**Спекулятивный декод даёт плюс сорок три процента при ширине 3.** Убыточна только ширина 4.

### Почему наш замер показал обратное

Замер через `qwen35_mtp_gate` дал −11..−42% и был истолкован как «MTP убыточен». Это неверно: мерился не MTP, а **карантин движка**. Два гейта слишком широки.

**Гейт 1** — `adapter.rs:1330`, префилл:
```rust
if self.mtp.is_some() || self.multimodal[slot].is_some() || !self.graphs_enabled {
    return Ok(None);
}
```
Срабатывает по факту **загрузки** MTP, а не по активному раунду. Как только веса MTP в памяти, графовый префилл выключен для всех запросов навсегда — и страничный пул на этом пути не наполняется. Отсюда и наблюдавшееся отсутствие строки `paged pool: window=` в логе.

**Гейт 2** — `adapter.rs:1512`, декод:
```rust
if self.target_transactions.iter().any(|t| t.is_some()) {
    return Ok(None);
}
```
`any()` по **всем** слотам: активная транзакция одного слота уводит на eager шаги всех остальных. Цена соседу — 52.4 мс против 34.2, то есть плюс 53% на шаг, при том что сосед никакого MTP не просил.

Пока гейты не сужены, **любой замер MTP меряет не MTP**.

## Почему переписывать eager не нужно

Разложим измеренный простой хоста по длине контекста (21 мс при 32K, 80 мс при 128K):

```
наклон         = (80 − 21) / (128 − 32) = 0.615 мс на 1K токенов
свободный член = 21 − 32 × 0.615        = 1.33 мс
```

Число запусков ядер от длины контекста не зависит — оно определяется числом слоёв. Значит **весь фиксированный хостовый бюджет укладывается в 1.33 мс**: диспетчеризация candle, запуски ядер, чтение переменных окружения, блокировки. Это 2.5% шага при 32K и 1.7% при 128K.

Остальные 94–98% простоя **пропорциональны длине KV** — то есть это не диспетчеризация, а перекладывание префикса на каждом шаге в старом хранилище.

Отсюда два вывода. Первый: переписывание диспетчеризации адресует 1.33 мс и смысла не имеет. Второй: «переписать eager так, чтобы он не перекладывал префикс» означает «читать KV постранично на месте» — а это уже написано и называется `forward_decode_batch_graphed` со страничным пулом.

**Отдельное подтверждение из репозитория:** `model_weights.rs:1652` — слитая in-projection замерена 2026-08-26 на целевой RTX 3060: префилл на 1% хуже, декод неотличим. Гипотеза «меньше запусков ядер = быстрее» здесь уже опровергнута замером.

## Почему K=4 обваливается

`speculative_accept` (`adapter.rs:1173-1204`) при частичном принятии (`consumed < K`) делает `restore_slot_batched` и **полный** `forward_decode_batch` по принятому префиксу.

При доле принятия 0.87 частичных раундов: K=3 — около 34%, K=4 — около 43%. Амортизированно это добавляет к раунду примерно 11.6 мс при K=3 и 14.6 мс при K=4. Отсюда и обвал.

## Состояние на 2026-08-27 (реализация начата)

**Сделано и остаётся в дереве** (все коммиты собираются):
- Графовый префил отдаёт hidden всех позиций (`forward_prefill_graphed` возвращает `hidden_all`, он и так его считал).
- Захват префила сохраняет hidden во второй внешний буфер.
- Декодный граф тоже выводит hidden и возвращает его **глубокой копией** — буфер перезаписывается следующим launch, а проверка спекуляции держит состояния между вызовами.
- Декодный граф переведён из единственного экземпляра в пул по ключу `(b, slots)`.
- `catch_up` вызывается на обоих путях префила (в ветке захвата операции записываются, а не исполняются, поэтому там нужен hidden прогревочного прохода, а не буфер графа).

**Гейт префила ВОЗВРАЩЁН.** Снять не удалось: при графовом префиле MTP перестаёт запускаться.

**Симптом:** `drafted=2 accepted=0 used=false` против `drafted=39 accepted=19 used=true` при выключенных графах. Первый черновик не принимается, адаптивная ширина срезает K до 1 и пропускает раунды.

**Опасность симптома:** он молчаливый. Вердикт шлюза «совпадает», ошибок нет, декод даже быстрее (27.2 → 30.8 ток/с) — но ускорение даёт графовый префил, а спекуляция мертва. Три зелёных признака из трёх. Ловится только счётчиками `drafted`/`accepted`.

**Проверено и отвергнуто как причина:**
1. Пропущенный вызов `catch_up` на первом чанке (ветка захвата) — вынесен за ветвление, не помогло.
2. Маршрутизация проверки спекуляции через декодный граф — откачена, не помогло. Отдельно установлено, что она неверна по существу: формы `(k, 1)` и `[B, 1]` совпадают, но смысл разный (k токенов на одном слоте против b слотов по токену), а `kv_len` у пула один на слот.
3. Различие скрытых состояний между путями — обе ветки возвращают `self.norm.forward(&layer_in)`, данные идентичны.
4. Флаг `slot_seeded` — засев на финальном чанке выполняется независимо от того, шёл префил графом или eager.
5. Различие источников эмбеддингов (`tok_embeddings` против `tok_embeddings_cuda`) — первое обнуляется только в GPU-only режиме, в прогоне поле живое и ошибки нет.

**Поправка к пункту 5 и к самой диагностике (важно).** Печать состояния перед вызовом `catch_up` дала `mtp=false`, и я заключил, что вызов не срабатывает вовсе. Вывод неверен: **шлюз прогоняет два прохода** — сначала базовый без MTP, затем с MTP, — а я смотрел первые строки вывода, то есть базовый проход. В нём `self.mtp` пусто по определению. Шестая ошибочная версия, и причина та же, что у восьми пустых замеров за сессию: не проверено, к какому прогону относится число.

**Правило для продолжающего:** при чтении вывода `qwen35_mtp_gate` всегда убеждаться, из какого прохода строка. Диагностику надо помечать признаком прохода, иначе она вводит в заблуждение сильнее, чем её отсутствие.

**Решение BD-030 снимает часть неопределённости:** MTP грузится при старте, когда включён, поэтому в замерах он либо есть с самого начала, либо его нет вовсе. Третьего состояния — «включён, но в момент префила ещё не загружен» — больше не будет.

**Следующий шаг — диагностика, а не гипотеза.** Сравнить состояние MTP после графового и eager префила напрямую: снять `pending_target_hidden` и содержимое `MtpKv` в обоих режимах на одном промпте и найти, где они расходятся. Пять версий подряд не подтвердились, значит рассуждение здесь исчерпано.

## Разбор 2026-08-27 (вечер): причина найдена чтением кода, префил ни при чём

**Все шесть версий искали на стороне префила и `catch_up`. Ломается проверка.**

Цепочка (пути — `yttri-forge/engine/qwen35-batch/src`):

1. Графовый префил пишет KV только в страничный пул (`model_weights.rs:3937`
   `forward_attn_prefill_paged` → `launch_append_multi`), single-slot `kv_cache`
   не трогает. Снимок на финальном чанке несёт `Attention(None)`,
   `seed_slot_batched` ставит `kv_cache_batched[slot] = None`, затем
   `set_kv_len_batched(slot, 8192)` (`adapter.rs:960`). Итог: кеш пуст, длина 8192.
2. `speculative_verify` (`adapter.rs:1175`) идёт eager: `forward_decode_batch_with_hidden`
   по batched-кешу — и **не вызывает `rehydrate_kv_from_paged`**. Единственный
   вызов rehydrate — в `decode_batch` (`adapter.rs:1075`), на пути обычного декода.
3. `forward_attn_decode_batch` (`model_weights.rs:4189`) при `kv_cache_batched[slot]
   == None && kv_cache_len_batched[slot] > 0` возвращает ошибку
   «batched KV освобождён (len=8192), нужен rehydrate_kv_from_paged»
   (добавлена f9652c7e 2026-08-26, то есть ДО всех замеров этого дня).
4. Планировщик (`scheduler.rs:423`) глотает ошибку: `_ => rollback; return
   Fallback::Commit` — **без единой строки в лог**. Отсюда `drafted=2 accepted=0
   used=false`: черновик был, проверка упала, `used` ставится только после commit.
   Слот дальше живёт обычным графовым декодом, поэтому вердикт «совпадает» и
   скорость выше.

То же самое ждёт `speculative_accept` (`adapter.rs:1258`, re-run через eager
`forward_decode_batch`) и `checkpoint_slot_batched` (снимает batched-кеш, а не пул).

**Подтверждение за один прогон (до любой правки):** в `speculative_slot`
напечатать проглоченные ошибки в ветках `_ =>` после `speculative_draft`,
`speculative_verify`, `speculative_accept`, `speculative_commit` и снять гейт.
Ожидаемая строка — п.3. Заодно станет видно, почему рундов после первого не
было (адаптивная ширина при (m=1,k=2) обязана пробовать снова через раунд —
`drafted=2` за весь прогон этому противоречит; вероятно, короткий `--new`).

**Подтверждено прогоном соседней сессии (forge-gpu, 8K, `--new 32`, адаптив вкл):**
единственная строка за прогон — `speculative verify forward: slot 0: batched KV
освобождён (len=8192), нужен rehydrate_kv_from_paged`. Печать проглоченных
ошибок теперь в main yttri-forge (123ba502, 0b264a3a).

**Второй дефект — отчего после первого провала раундов не было.**
`scheduler.rs:368-392`: `speculative_begin` (чекпоинт слота + `mtp.begin`)
вызывается ДО расчёта адаптивной ширины, а ветка `k_next <= 1` возвращает
`Fallback::Draft` без `speculative_rollback`. Транзакция остаётся открытой,
`speculative_available` даёт false до конца запроса. Хронология: раунд 1 —
проверка падает, (m,k)=(1,2); раунд 2 — k→1, пропуск, утечка; дальше только
обычный декод. `drafted=2` сходится точно; при `QWEN36_MTP_ADAPTIVE=0` пропусков
нет — отсюда 66–110 черновиков.

Следствие для прода: адаптив включён по умолчанию, и в eager-режиме MTP умирает
при первом же отвергнутом первом черновике (~32% раундов при принятии 68%), то
есть на 2–4 раунде каждого запроса. Таблица выше снята с `ADAPTIVE=0` и потому
верна, но к проду не относилась. Правка — перенести блок адаптивной ширины выше
`speculative_begin` (заодно уходит бесполезный чекпоинт DeltaNet на пропущенных
раундах). Передана соседней сессии вместе с проверкой: eager, 8K, ширина 2,
адаптив вкл, `--new 64` — `drafted` должен расти весь прогон.

**Правка внесена и проверена замером** (yttri-forge main, forge-gpu, Qwen3.8-27B
Q8_0, Q8-голова `mtp.ytf`, 8K, ширина 2, `--new 128`, по два повтора):

| адаптив | drafted | accepted | used | базовый | MTP | ускорение |
|---|---|---|---|---|---|---|
| вкл — **до правки** | 2 | 0 | **false** | — | — | нет (MTP мёртв) |
| вкл — после правки | 128 | 95 (74%) | true | 25.03 / 25.07 | 27.76 / 27.83 | **1.11x** |
| выкл | 136 | 107 (79%) | true | 25.12 / 25.15 | 28.66 / 28.67 | **1.14x** |

Повторы сходятся до второго знака — путь детерминированный. Дефолт подтверждён
по коду: `mtp_adaptive_on()` даёт `unwrap_or(true)`, то есть в проде работал
именно мёртвый путь.

**Развёртка по ширине — дефолт менять не нужно.** Вывод «адаптив не окупается»
был снят на ширине 2 и на неё же только и распространяется: дефолт
`speculative_width()` — **3**, и эта пара не измерялась ни разу. Полная
развёртка (8K, `--new 128`, два повтора на точку, все точки годны по шлюзу):

| ширина | адаптив | drafted | accepted | принятие | ускорение |
|---|---|---|---|---|---|
| 2 | вкл | 128 | 95 | 74% | 1.11x |
| 2 | выкл | 136 | 107 | 79% | **1.14x** |
| 3 | вкл | 147 | 101 | 69% | **1.13x** |
| 3 | выкл | 152 | 101 | 66% | 1.09x |
| 4 | вкл | 156 | 97 | 62% | 1.11x |
| 4 | выкл | 169 | 93 | 55% | 1.02x |

Адаптив вредит **только** на ширине 2, а на 3 и 4 окупается с запасом: 1.13
против 1.09 и 1.11 против 1.02. Его работа — срезать избыточную ширину, а на
ширине 2 срезать некуда, кроме пропуска раунда, что и есть чистый убыток.
Видно и по счётчикам: на ширине 3 адаптив даёт то же число принятых (101) при
меньшем числе черновиков (147 против 152) — ровно экономия на отброшенных.

**Решение: дефолты не трогаем.** Штатная пара «ширина 3 + адаптив» даёт 1.13x —
на один пункт ниже ручного оптимума (ширина 2 без адаптива, 1.14x), но
устойчива: адаптив сам сходится к ширине 2 при любом старте, а жёстко
приколоченная ширина 2 без адаптива теряет защиту, если принятие просядет на
другой модели, кванте или длине контекста. Один пункт — честная цена
устойчивости.

**Уточнение к ранее заявленным +19%.** Та цифра снята на `--new 64`
(`/root/logs/q8-final.log`), где разогрев амортизируется короткой генерацией. На
`--new 128` та же конфигурация даёт 1.14–1.15x. Оба замера верны, к проду
относится длинный.

**Правило шлюза для всех будущих замеров MTP:** при `used=false` или
`accepted=0` замер недействителен независимо от показанных ток/с. Дважды число
выглядело победой при полностью мёртвой спекуляции — `ускорение=1.14x` при
`drafted=2 accepted=0` и ложные +19% на графовом префиле. `enabled=true` не
означает ничего.

**Почему «добавить rehydrate перед verify» — не решение, а костыль.** Он делает
черновики принимаемыми (можно использовать как второе подтверждение диагноза:
две строки — `rehydrate_kv_from_paged(slot)` в начале `speculative_begin` до
`checkpoint_slot_batched`), но после первого раунда batched-кеш уходит вперёд
пула: `decode_batch_graphed` видит `positions != kv_len_host` → `Ok(None)` → весь
остаток запроса eager. Множители не складываются, и это тот же −35..−66%.

**Решение — проверка через страничный пул, и почти всё для неё уже написано.**
Проверка k токенов одного слота — это префил-чанк длины T=k на страничном пути,
а не декод B=k. Именно поэтому попытка b3754c43 через декодный граф была
неверна: у декодного append одна позиция на слот, у префил-append — T позиций
подряд (`launch_append_multi`), и FA2 varlen с `window_right=0` даёт нужную
причинность «строка i видит 0..kv0+i» (`model_weights.rs:4034`).

- Attention: `forward_attn_prefill_paged(x[1,k,H], ctx, rope_pos[k])` как есть.
  Стейджинг вне графа тот же, что у префил-графа: `stage_inputs(&[slot], …)`,
  `set_prefill_seqlens_q(k)`, `seqlens_k_for_prefill(1, k)`; в конце
  `launch_increment_t(1, k)`.
- DeltaNet: НЕ префил-ветка (она работает на single-slot `cuda_ctx`), а
  `delta.forward_decode_batch(x[k,1,H], slots=[slot;k])` — ветка `serial_rows`
  (`model_weights.rs:2027`) уже прогоняет повторяющиеся слоты последовательно на
  batched-состоянии, бит-эксактно k одиночным шагам. Между слоями reshape
  `[k,1,H] ↔ [1,k,H]`.
- Новая `forward_verify_graphed(ids[1,k], rope[k]) -> (logits[k,vocab], hidden[k,H])`:
  как `forward_prefill_graphed`, но блок-функция гибридная (выше), а `output`
  считается над всеми k строками. Захват — пул графов по ключу `(k, slot)`, как
  у префила, с внешними буферами logits/hidden.
- Откат отвергнутых строк в пуле — сдвиг длины (FR-007): `kv_len_host[slot] =
  pos + m`, `reset_kv_len`. Строки `pos..pos+m` в пуле уже верны (посчитаны по
  верному префиксу), пересчитывать их для attention не нужно. DeltaNet при
  m < k: `restore_slot_batched` (только его часть значима) и прогон m строк той
  же `forward_verify_graphed` с длиной пула, откаченной на `pos`, — она допишет
  те же строки поверх. Это оставляет обвал Ф3, но уже на графах.
- Хостовые зеркала: после раунда `set_kv_len_batched(slot, pos+m)`, чтобы
  eager-откат (`rehydrate`) при отказе графов собирал правильную длину.
- Гейт `self.mtp.is_some()` в `prefill_chunk_graphed` снимается; черновик MTP
  остаётся eager (один блок, дёшево).

Нюанс для Ф4б: префил-путь пишет строки F16 (`pgraph_f16_kv`), декодный — через
q8-round-trip; строки проверки и строки обычного декода будут отличаться на
шум квантования. BD-029 это допускает, но шлюз при ширине 1 должен это учитывать
(сравнивать с включёнными графами в обеих ветках).

Оценка: ~200 строк (блок-функция ~40, модельная ~60, адаптер ~100), 1–2 дня.

## Цена проверки от окна пула — причина и правка (2026-08-27, ночь)

Замер соседней сессии: на 32K verify 44.4 мс при окне 40960 и 67.0 при
196608 (9.3 мкс/страница), на 8K не зависит от окна, draft и декод плоские;
на 128K verify 74 мс при принятии 98% — раунд стоит 2.3 шага, выигрыш
обнуляется. Отсюда падение после 32K в таблице против llama.cpp.

Причина — `engine/candle-flash-attn/kernels/flash_api.cu`: для `seqlen_q > 1`
число сплитов по K берёт апстримная эвристика по волнам от `b·h·m` (у проверки
24) → 5 сплитов, а блоков на сплит — от `seqlen_k`, то есть от **окна пула**.
При окне 196608 — 308 блоков на сплит, и контекст 32K (256 блоков) идёт одним
сплитом на голову; на 8K при любом окне активен один сплит на 64 блока —
потому плоско; на 128K одна цепочка на 1024 блока. Декод не платит: своё
правило (до 128 сплитов) и GQA-свёртка; префил — 192 CTA, эвристика честно
даёт 1 сплит.

Правка `831d15a6`: для `seqlen_q ≤ 16` сплитов `min(num_n_blocks/2, 128)`.
**Замер:** 32K — verify 48.65→43.58 при окне 65536 и 67.06→43.67 при 196608
(зависимость от окна исчезла, 1.12x при обоих); 128K — 74.30→71.41, всего
4%, MTP там 0.93x. Остаток над шагом декода растёт с контекстом: +9.2 мс на
32K, +30.5 на 128K — это отсутствие GQA-свёртки: одна причинная FA2 на k
строк не проходит `mask_is_noop`, 24 CTA читают KV своей kv-головы
шестикратно, ×16 слоёв. mmvq при b=2 от контекста не зависит (~7 мс).

**Правка сплитов откачена** (`3906e355`): серверный замер при окне 131072
дал 128K с MTP 26.8→24.7 (−8%) при идентичном принятии (65 токенов в 32
чанках в обоих прогонах) и чистом происхождении бинаря; 64K при этом +3.3%.
Версия: без GQA-свёртки шесть голов kv-группы читают одни блоки — 120
длинных CTA идут почти синхронно и делят L2, 3072 коротких планировщик
разносит, трафик растёт к шестикратному; при окне 196608 старый вариант
имел лишь 96 CTA, и там параллелизм перевешивал. Правильное лечение —
сама свёртка (ниже); после неё проверка попадает в декодное правило.

## Хостовая сторона шага (наблюдение пользователя: одно ядро CPU на 100%)

Большая часть — spin-wait CUDA на D2H логитов (не рычаг; гигиена —
`CU_CTX_SCHED_BLOCKING_SYNC`, важна на yttri-win, где то же ядро обслуживает
HTTP). На критическом пути между шагами GPU, серийно по слотам:
1. `engine_batched.rs:752` `drain_after_step` — `decode_text` по ВСЕЙ
   generated на каждом шаге + `String` всего текста + сравнение префиксов:
   O(n) на токен, O(n²) на запрос; при thinking-выводах 8–16K и 4 слотах —
   единицы–десятки мс на шаг из 33. Замена точная для byte-level BPE:
   инкрементальный декод хвоста от последней стабильной границы (без U+FFFD).
2. `sampler.rs` — quickselect по 152K индексов + копия логитов + температура,
   ~1–1.5 мс на токен на слот; при 4 слотах 4–6 мс на шаг. Лечится top-k на
   GPU внутри графа: D2H 64 пар вместо 600 КБ на слот; штрафы — вектором на
   устройстве или по top-k.
CPU-время процесса оказалось непригодной метрикой (при spin-wait оно равно
времени на стене), `perf` на стенде нет. Вместо замера-прокси — правки по
асимптотике и прямая инструментация (серверный крейт, коммит
«perf(server): хостовая сторона шага»): инкрементальный декод хвоста от
стабильной границы (O(n²)→O(n), байты те же), инкрементальное множество
penalties в состоянии слота (третья находка соседа: HashSet пересобирался из
всех токенов на каждом токене), частичный отбор при `top_k=0` от клиента
(quickselect 1024 + нуклеус от полной нормировки, тест паритета с полной
сортировкой), `QWEN36_HOST_TIMING=1` — sample на вызов и drain на шаг раз в
48 шагов. **Замер (`[host]`, 8K, пресет instruct):** drain 0.048 мс на шаг в начале и
0.049 после 3200 токенов — квадратичность снята; sample 0.229→0.475 мс за
3200 токенов (штраф перебирает уникальные токены — по природе штрафа);
`top_k=0` работает. Хост в сумме ~0.5 мс из 33 (1.5%) — **загруженное
ядро CPU это spin-wait драйвера**, не наша работа. Гигиена сделана
(`cuda_prefer_blocking_sync`, `CU_CTX_SCHED_BLOCKING_SYNC`, откат
`QWEN36_CUDA_SPIN=1`). Top-k на GPU не нужен: сэмплер — 0.2–0.5 мс.

**Попутный старый баг стрима, найденный контролем «дельты против полного
декода»:** сплиттер reasoning/content в `openai.rs` отдавал последний
удержанный кусок размышления через `trim()` и срезал его ведущий пробел
(«Let's» + « craft.» → «Let'scraft.»); контент после `</think>` в потоке не
обрезался, в non-stream — обрезался (лишний `\n\n`). Исправлено (fix(api)):
обрезка начала только у первого куска, контент — до первого непустого куска.
Чистая модель drain проверена автономно: 20 000 случайных разрезов UTF-8 на
токены с шагами по 1–3 токена, расхождений нет.

## Память: разрыв с llama.cpp постоянен (~2.2 ГБ) — раскладка

Разница не в KV (рост 8K→128K у нас +7.68 ГБ, у llama.cpp +7.80). Замер
соседней сессии на 8K: после загрузки llama.cpp 27219 / forge 28683 МБ
(+1464), после первого запроса 27237 / 29465 (+18 / +782). Сняты замером:
удержание мемпула (ровно 0), порог мемпула (0), графы (−250 МБ), сайдкар
ytf16 (файла нет, харнесс всегда ставил `QWEN36_DISABLE_YTF16=1`).

Раскладка по коду. «На запрос» — разовое: страничный пул создаётся лениво
при первом графовом декоде (512 МБ при окне 8192; у llama.cpp KV под n_ctx
сидит в «после загрузки») + графы 250 + рабочий набор ~20 МБ (как 18 у
llama.cpp). «При загрузке» ~2 ГБ с учётом переноса пула: **эмбеддинг
токенов копией на GPU** (`tok_embeddings_cuda`, обязателен для графов;
llama.cpp держит `token_embd` на хосте — входной слой, нужен только gather;
0.8–1.35 ГБ в зависимости от vocab и кванта) + дубль состояния DeltaNet
(single-slot для префила + batched для декода, ~384 МБ) + ядра/cuBLAS/графы.

Подтверждено кодом (`model_weights.rs:5531`): `tok_embeddings_cuda` —
«дублирующий token_embd на GPU», оригинал `QuantizedEmbedding::from_mmap`
остаётся на хосте; копия ставится только при запасе VRAM (`embed_bytes +
PREFILL_HEADROOM (+ GRAPH_POOL_RESERVE)`), и на 27B/12 ГБ гейт её отсекает —
а вместе с ней и графы, которым она обязательна («no CUDA embedding»).
Поэтому для целевой карты рычаг — не «убрать копию», а **графы без копии**:
gather строки эмбеддинга на хосте и стейджинг вектора [B, hidden] (для
префила [1, T, hidden]) во входной буфер графа вместо ids. Это даёт 12 ГБ
одновременно и −0.8–1.35 ГБ, и графовый декод (+75% на длинном контексте).

**Сделано** (yttri-forge, «perf(vram): вход графов — готовый вектор
эмбеддингов»): `embed_for_graph` — хост-деквант из mmap + H2D, графы
принимают вектор вместо ids, копия на GPU только под `QWEN36_EMB_GPU=1`
(A/B). Ожидание на 4090: VRAM −1288 МиБ, VERDICT match, ток/с ±1%; на 12 ГБ —
графы перестают отключаться по «no CUDA embedding» (проверка только на
yttri-win). Разбор соседней сессии по коду: lookup — единственный
потребитель ids во всех трёх путях, стейджинг буфера обязан идти до guard
кэша htod (порог 4096 Б).

Рычаги для целевых 12 ГБ по убыванию: графы с эмбеддингом на хосте
(−0.8–1.35 ГБ и графы; llama.cpp держит `token_embd` на хосте) — сделано → один буфер состояния DeltaNet на слот (−0.38) → Q4-голова при
MTP (−0.35) → графы (−0.25, на 12 ГБ и так выключены гейтом по запасу).
Проверки без стенда: тип/размер `token_embd.weight` из дампа GGUF, строка
«CPU buffer size» в логе llama.cpp; со стендом — прирост на втором и третьем
запросе (разовое против «на запрос»).

## 2026-08-28: падение при вытеснении префил-графа (найдено внешним агентом)

Сценарий: девятый уникальный хвостовой чанк (T=45 при lru=8) → захват →
вытеснение LRU → следующий шаг `CUDA_ERROR_INVALID_VALUE`. Диагноз «Drop
разрушает незавершённый граф» не сходится: каждый чанк заканчивается D2H
логитов (полная синхронизация), к моменту Drop вытесняемый граф завершён;
пул — настоящий LRU, живых ссылок на буферы вытесняемого графа нет.
Правка `66d86a9e`: хвосты короче `QWEN36_PGRAPH_MIN_T` (256) считаются
прогревочным проходом без захвата — в пуле остаются графы полного чанка по
числу слотов, вытеснений в штатной работе нет; `QWEN36_PGRAPH_LRU` — размер
пула; `QWEN36_PGRAPH_EVICT_LEAK=1` — вытеснение без разрушения (диагностика).
Локализация корня — отдельно: `MIN_T=0 LRU=2 TRACE=1`, затем то же с
`EVICT_LEAK=1` (разрушение против самого захвата).
Дефект 1 того же теста (function.arguments строкой против объекта в шаблоне)
починен соседней сессией нормализацией на входе (`normalize_tool_call`).

## 2026-08-28: графы на нескольких слотах падали (OQ-7) — причина найдена

yttri-win, Ornith-1.5-9B Q6_K, 4 слота: с графами `CUDA_ERROR_ILLEGAL_ADDRESS`
и смерть процесса в nvcuda в 4 прогонах из 5; на одном слоте — никогда;
вытеснение графов исключено замером (14 захватов при пуле 16). Причина —
`delta_rule_batched_cuda.rs`, `temp.slot_ids_cache`: кэш device-буфера
slot_ids на одну запись; при смене состава батча (ранний EOS, приём запроса,
проверка MTP с `[slot]`) старый буфер освобождался, а его адрес запечён в
аргументы ядер DeltaNet внутри захваченного графа прежнего состава — повтор
читал освобождённую память, ядра писали состояние по мусорному слоту.
Правка `57c0ba5b`: кэш — растущий список «состав → буфер», ничего не
освобождается (составы — подмножества слотов в возрастающем порядке, ≤2^слотов).
**Подтверждено замером (сессия 09):** ILLEGAL_ADDRESS и падения процесса
ушли; 4 слота без гейта — 94.0 и 103.7 ток/с (было 84.8 с гейтом).
**Второй дефект того же OQ-7 — вытеснение декодного графа:** с пулом 6 при
девяти захватах `CUDA_ERROR_INVALID_VALUE` на шаге планировщика (сервер
выживает), с пулом 32 чисто. Тот же класс, что падение при вытеснении
префил-графа (обход `66d86a9e`). Корень не локализован; переключатели для
локализации — `QWEN36_DGRAPH_EVICT_LEAK=1` (не разрушать) и
`QWEN36_GRAPH_DROP_SYNC=1` (sync перед разрушением) плюс `QWEN36_TRACE=1`.
Дефолты: `QWEN36_DGRAPH_LRU` 32, `QWEN36_GRAPH_MAX_B` без ограничения как
предохранитель. Проверка у сессии 09: печать замены кэша на прежней сборке
(падение на первом повторе графа заменённого состава), затем сборка с
правкой при `QWEN36_GRAPH_MAX_B=8` — ожидание ILLEGAL=0 и 96–103 ток/с на
4 слотах вместо 84.8 с гейтом.

## 2026-08-28: Metal — `Tensor::copy()` алиас, ветка serial_rows читала строку 0

По замечанию сессии yttri-66: `MetalStorage::try_clone` в форке возвращает
`self.clone()` с тем же `start_offset`, то есть `copy()` на Metal не копирует.
Metal-ветка последовательных строк DeltaNet (проверка MTP с k строками одного
слота) полагалась на `.copy()` входов и выхода — на macOS она читала строку 0
во всех k и возвращала общий scratch. Правка (fix(metal)): копия через
`zeros + slice_set`. CUDA не затронут. Для macOS-разработки MTP это значит,
что проверка спекуляции там до правки была неверна. Заодно урок
профилирования на ленивом Metal — в память проекта.

## 2026-08-28: conv_state DeltaNet не обновлялся при префиле короче conv_k−1

Найдено по вопросу Metal-порта (сессия yttri-66, деградация на коротком

**Не удаляет `kv_cache_batched`.** На нём висят шесть возможностей, которых у пула нет: скользящее окно BD-017 (в пуле нет вытеснения), Metal и CPU (пул только под CUDA), vision через mrope, seed из снимка, полные логиты в графовом префиле, плюс латентный выход за границу в append-ядрах. Каждая — отдельная работа, ни одна не ускоряет запросы.

**Не трогает мультимодальность.** Гейт PD-204 для mrope остаётся.

**Инвариант выхода закрыт решением BD-029** (2026-08-27): требуется сохранение распределения, а не реализации. Совпадение токен в токен снято как требование — блокировка Ф5 снята.

  раунда разброс 0.2 мс.

операций вместо пакетного. Ни байтовая арифметика, ни число узлов этого не
объясняют. Следующий шаг — профиль по блокам. `verify` теперь занимает 76%
раунда, поэтому это самый крупный оставшийся рычаг после `accept`.

## Почему выигрыш MTP падает с ростом контекста (замерено 2026-08-27)

**Не из-за качества головы.** Принятие с контекстом не падает, а растёт: на 128K
голова угадала 45 черновиков из 46 (98%) против 34 из 47 (72%) на 8K. Съедает
выигрыш стоимость проверки.

**Стоимость проверки растёт с размером пула страниц.** Решающий опыт: контекст
32K, запрос один и тот же, меняется только `QWEN36_GRAPH_WINDOW`:

| окно | блоков | verify | draft | база | +MTP | итог |
|---|---|---|---|---|---|---|
| 40960 | 640 | **44.4 мс** | 7.74 | 28.78 | 31.08 | **1.08x** |
| 65536 | 1024 | 48.7 | 7.92 | 28.95 | 31.46 | 1.09x |
| 131072 | 2048 | 60.8 | 7.88 | 28.92 | 26.42 | 0.91x |
| 196608 | 3072 | **67.0** | 7.88 | 28.92 | 24.43 | **0.84x** |

Линейно, около 9.3 мкс на страницу пула. `draft` и базовый декод плоские — эту
цену платит только путь проверки (`forward_attn_prefill_paged`), а декодный путь
нет. Экономика раунда отсюда и следует: раунд даёт ~2 токена, а при большом пуле
стоит как 2.2–2.3 обычных шага, поэтому выигрыш обнуляется.

**Взаимодействие с длиной контекста не объяснено.** На 8K смена окна с 1024 на
3072 блока стоит +0.6 мс (42.8 → 43.4), на 32K та же смена стоит +18.3 мс
(48.7 → 67.0). То есть это не простой обход всей таблицы страниц — иначе цена не
зависела бы от используемой длины. Модели нет, данных для неё недостаточно.

**Практическое следствие для прода.** Окно пула на сервере задаётся из `CTX`,
то есть под максимальный контекст развёртывания. Значит сервер, настроенный на
128K, платит увеличенную стоимость проверки и на коротких запросах тоже. Размер
окна стоит привязывать к длине запроса, а не к потолку конфигурации.

**Отвергнуто замером: та же причина у отставания префила.** Версия была
соблазнительной, и арифметика сходилась почти точно — 9.3 мкс на страницу при
чанке 512 давали расчётные 4.9 с накладных расходов на 128K против измеренных
5.3 с разрыва с llama.cpp. Прямая проверка опровергла: префил при росте окна с
640 до 3072 блоков меняется на 0.6% (2128.8 → 2115.9 ток/с). **Отставание
префила по-прежнему без объяснения**, и совпадение арифметики было случайным —
третий такой случай за день.

## Идея: MTP-голова из основного файла модели

Проверено чтением заголовка GGUF: основной файл `Qwen3.8-27B-Q8_0.gguf` уже
содержит **все 15 тензоров головы** в блоке 64 (`blk.64.attn_*`, `blk.64.ffn_*`,
`blk.64.nextn.*`), метаполе `qwen35.nextn_predict_layers=1`. Отдельный артефакт
`mtp.ytf` на 446 МБ — точная копия того, что уже есть в модели. Загрузчик
намеренно отрезает блок 64 от основной модели
(`block_count = block_count_raw - nextn_layers`, `model_weights.rs:5299`), а
`load_mtp` читает отдельный файл.

Правка прямая: читать блок 64 из основного GGUF. Что даёт:

- уходит целый класс проблем — сборка, версионирование и перевозка артефакта, а
  также риск несовпадения кванта головы с моделью (два дефекта упаковщика этого
  артефакта чинились сегодня);
- **экономии VRAM не даёт**: 0.8 ГБ — это сами веса головы, они нужны в памяти
  независимо от источника чтения. Сэкономить их можно только отказом от
  отдельной головы, то есть черновиком по существующим слоям (ранний выход) —
  это другая техника, сложнее и с худшим принятием.

«больше чанк лучше». llama.cpp на 128K даёт 1818, то есть отставание закрывается
настройкой. **Дефолт не менялся:** 512 защищал от материализации attention
scores на eager-пути (комментарий `scheduler.rs:65-70`), а в многослотовом
режиме длинный чанк задерживает декод соседей вдвое дольше. Нужен замер пика
VRAM на 12 ГБ и многослотовой отзывчивости; решение о дефолте — за
пользователем.

*Правка сплитов flash-attn (`831d15a6`) помогает на 32K и вредит на 128K.*
Гейт, тайминг, `verify` в мс:

| точка | до | после |
|---|---|---|
| 32K, окно 65536 | 48.65 | **43.58** |
| 32K, окно 196608 | 67.06 | **43.67** |
| 128K, окно 196608 | 74.30 | 71.41 |

На 32K зависимость от окна исчезла полностью (43.58 против 43.67 при
трёхкратной разнице окна). Но сервер при `CTX=131072` показал регресс:
декод 26.8 → 24.7 при **идентичном принятии** (65 токенов в 32 чанках в обоих
прогонах) и идентичном префиле (1616 против 1615). Происхождение бинарей
проверено: сборка «до» сделана от `1af9dc2c`, куда входят `009aa39f` и
`29075776`, то есть сравнение изолирует ровно правку сплитов.

**Не проверено, стенд упал раньше.**

- Серверные числа с чанком 1024 — то есть префил на продакшен-пути.
- Трёхсторонний опыт `prev` / `splits` / `perrow` на четырёх комбинациях
  контекста и окна. Он должен был проверить версию про потерю локальности L2
  **формой результата**: смена знака между окнами 131072 и 196608. Скрипт
  готов (`/root/three_way.sh`), три бинаря сохранены на стенде.
- **`b8dcbdfe` и `3906e355` не собирались под CUDA ни разу.**

**Предупреждение.** Три последние правки (`831d15a6`, `b8dcbdfe`, `3906e355`)
лежат в `main` yttri-forge, из них две последние не компилировались под CUDA и
не мерялись. Первая измерена и даёт регресс на серверной конфигурации 128K.
Собирать `main` для продакшена в этом состоянии нельзя без проверки на железе.

## Память: откуда +2.2 ГБ против llama.cpp (замерено 2026-08-27)

**Разложение по замеру** (Qwen3.8-27B Q8_0, RTX 4090, один слот):

| замер | llama.cpp | forge | разница |
|---|---|---|---|
| на карте при контексте 512 | 26731 | 28203 | **+1472** |
| на карте при контексте 8192 | 27219 | 28683 | **+1464** |
| прирост кеша 512→8192 | +488 | +480 | вровень |

**Разница постоянна при пустом кеше** — значит целиком в весах и постоянных
структурах, ни грамма в KV. По кешу мы даже чуть экономнее.

**Прирост на запрос — разовый, не на каждый запрос:**

```
после загрузки 29195 МБ
запрос 1: +782   запрос 2: +0   запрос 3: +0
запрос 4 (другая длина): +16    запрос 5: +0
```

Страничный пул создаётся лениво при первом графовом декоде, поэтому попадал в
колонку «запрос». Утечки нет; новая длина промпта стоит 16 МБ на захват графа.

**Главная статья — копия эмбеддинга на карте.** `token_embd.weight` =
1288 МБ (Q8_0, 5120 × 248320). `tok_embeddings_cuda` (`model_weights.rs:5531`) —
дубль на GPU, обязательный для графов; оригинал остаётся на хосте. 1288 из
1470 — это 88% перерасхода. Остаток ~180 МБ не объяснён: сборка llama.cpp не
печатает размещение буферов даже при полной подробности, а арифметика по
размеру файла даёт разброс в сотни мегабайт. **Утверждать, что эмбеддинг — вся
разница, данные не позволяют.**

**Опровергнуто замером** (не проверять заново): удержание мемпула
(`QWEN36_NO_MEMPOOL_RETAIN=1` — эффект ровно ноль), порог мемпула (ноль),
графы (−250 МБ), сайдкар ytf16 (файла `.ytf16` нет, и харнесс всё время
выставлял `QWEN36_DISABLE_YTF16=1`).

**Следствие для целевой 12 ГБ важнее самой экономии.** Копия эмбеддинга
ставится только при запасе VRAM, а на 12-гигабайтной карте гейт её отсекает — и
вместе с ней отключаются графы, которым она обязательна. То есть целевая карта
сейчас работает **без графового декода**, теряя измеренные +21%. Рычаг — не
«сэкономить гигабайт», а «графы без копии эмбеддинга»: подавать в граф готовый
вектор [B, hidden], выборку строк делать на хосте. Карта получает и память, и
графовый декод.

**Оговорка к самой цифре.** 2.2 ГБ честны как «сколько занято на карте» (это
видят соседи и WDDM), но не как «сколько нужно». Для вопроса «влезем ли в
12 ГБ» считать надо второе, и оно на 4090 не измеряется.

**Попутно:** llama.cpp не грузит MTP-голову вовсе — в его логе пятнадцать строк
`unused tensor blk.64.* — ignoring`. Для этой модели у него спекуляции нет как
таковой, и это стоит держать в уме при чтении наших +21…+56% по декоду.

## Порядок

```
Ф1 (гейты) ──> Ф3 (обвал K=4) ──> Ф4 (замер ширины)
     └──> Ф2 (int8-путь)
Ф5 (артефакты) — параллельно всему
```

Ф1 первым и один: пока гейты широки, любой замер по MTP недостоверен, а значит вехи Ф3 и Ф4 нечем проверять.

## Риски

| риск | что делаем |
|---|---|
| Сужение гейта откроет гонку по hidden в graph-pool буфере | копировать hidden сразу после replay; веха Ф1 требует совпадения выхода с eager-путём |
| Латентный выход за границу в append-ядрах (`attn_window` до 81920 против `max_blocks`) | правка до снятия гейтов, иначе запись в чужой слот |
| Замер из `scheduler.rs:89` сделан на IQ2_XXS, а мы целимся в Q8_0 | Ф4 перемеряет на Q8_0; если +43% не воспроизведётся, пересматриваем ширину, а не замысел |
| Ф3 затронет корректность отката | веха требует совпадения выхода при том же seed |
