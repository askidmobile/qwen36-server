# План: MTP × CUDA-графы

**Спека:** [2026-08-27-mtp-cuda-graphs.md](../specs/2026-08-27-mtp-cuda-graphs.md)
**Дата:** 2026-08-27 (переписан после разведки по коду)
**Оценка:** 5–8 рабочих дней до включаемого MTP на 27B

## Главное: MTP уже работает и уже окупается

В коде, `scheduler.rs:89-90`, лежит замер, сделанный до нас:

```
27B IQ2_XXS, 128 токенов:
  baseline 18.6 ток/с
  K=2  →  22.8   (+23%)
  K=3  →  26.6   (+43%)
  K=4  →  15.1   (−19%)
```

**Спекулятивный декод даёт плюс сорок три процента при ширине 3.** Убыточна только ширина 4.

### Почему наш замер показал обратное

Замер через `qwen35_mtp_gate` дал −11..−42% и был истолкован как «MTP убыточен». Это неверно: мерился не MTP, а **карантин движка**. Два гейта слишком широки.

**Гейт 1** — `adapter.rs:1330`, префилл:
```rust
if self.mtp.is_some() || self.multimodal[slot].is_some() || !self.graphs_enabled {
    return Ok(None);
}
```
Срабатывает по факту **загрузки** MTP, а не по активному раунду. Как только веса MTP в памяти, графовый префилл выключен для всех запросов навсегда — и страничный пул на этом пути не наполняется. Отсюда и наблюдавшееся отсутствие строки `paged pool: window=` в логе.

**Гейт 2** — `adapter.rs:1512`, декод:
```rust
if self.target_transactions.iter().any(|t| t.is_some()) {
    return Ok(None);
}
```
`any()` по **всем** слотам: активная транзакция одного слота уводит на eager шаги всех остальных. Цена соседу — 52.4 мс против 34.2, то есть плюс 53% на шаг, при том что сосед никакого MTP не просил.

Пока гейты не сужены, **любой замер MTP меряет не MTP**.

## Почему переписывать eager не нужно

Разложим измеренный простой хоста по длине контекста (21 мс при 32K, 80 мс при 128K):

```
наклон         = (80 − 21) / (128 − 32) = 0.615 мс на 1K токенов
свободный член = 21 − 32 × 0.615        = 1.33 мс
```

Число запусков ядер от длины контекста не зависит — оно определяется числом слоёв. Значит **весь фиксированный хостовый бюджет укладывается в 1.33 мс**: диспетчеризация candle, запуски ядер, чтение переменных окружения, блокировки. Это 2.5% шага при 32K и 1.7% при 128K.

Остальные 94–98% простоя **пропорциональны длине KV** — то есть это не диспетчеризация, а перекладывание префикса на каждом шаге в старом хранилище.

Отсюда два вывода. Первый: переписывание диспетчеризации адресует 1.33 мс и смысла не имеет. Второй: «переписать eager так, чтобы он не перекладывал префикс» означает «читать KV постранично на месте» — а это уже написано и называется `forward_decode_batch_graphed` со страничным пулом.

**Отдельное подтверждение из репозитория:** `model_weights.rs:1652` — слитая in-projection замерена 2026-08-26 на целевой RTX 3060: префилл на 1% хуже, декод неотличим. Гипотеза «меньше запусков ядер = быстрее» здесь уже опровергнута замером.

## Почему K=4 обваливается

`speculative_accept` (`adapter.rs:1173-1204`) при частичном принятии (`consumed < K`) делает `restore_slot_batched` и **полный** `forward_decode_batch` по принятому префиксу.

При доле принятия 0.87 частичных раундов: K=3 — около 34%, K=4 — около 43%. Амортизированно это добавляет к раунду примерно 11.6 мс при K=3 и 14.6 мс при K=4. Отсюда и обвал.

## Фазы

### Ф1. Сузить гейты (1–2 дня) — делать первым

**Гейт префилла.** Заменить `self.mtp.is_some()` на условие по активной транзакции конкретного слота. Загруженные веса MTP не должны отключать графовый префилл для запросов, которые спекуляцию не используют.

**Гейт декода.** Заменить `any()` по всем слотам на проверку транзакции **текущего** слота. Соседи не должны платить за чужую спекуляцию.

**Проверяемые вехи:**
- [ ] MTP загружен, но раунд не активен — в логе есть строка `paged pool: window=…`, счётчик replay графа больше нуля.
- [ ] Два слота, MTP активен на одном — второй держит 29.2 ток/с на 32K, а не 19.1.
- [ ] Замер MTP через шлюз, повторённый после правки, даёт результат, сопоставимый с `scheduler.rs:89`: K=3 не ниже baseline.

**Риск:** гейт стоит там не случайно — комментарий гласит, что MTP читает hidden, а буфер graph-pool перезаписывается следующим запуском. Сужение гейта требует, чтобы hidden копировался из графового буфера до следующего replay, а не читался лениво. Это часть работы, а не оговорка.

### Ф2. Собрать int8-путь (2–3 дня)

`kv_pool_dequant_q8` готово (`quantized.cu:7211`), бенч точности есть (`bin/bench_kvq8.rs`), а в `model_weights.rs:8118` стоит отказ с комментарием «путь ещё не собран». Собрать его.

**Что даёт:** вдвое меньше KV — на целевой карте 12 ГБ это условие длинного контекста, — и снятие несовместимости MTP с int8.

**Проверяемые вехи:**
- [ ] `QWEN36_KV_POOL_Q8=1` работает вместе с загруженным MTP, без отказа.
- [ ] Пул на 128K занимает вдвое меньше: около 2 ГиБ вместо 4.
- [ ] `bench_kvq8` держит относительную ошибку ниже 2%.

### Ф3. Устранить обвал при частичном принятии (2 дня)

Убрать полный re-forward из `speculative_accept`. Состояние после принятого префикса должно достраиваться, а не пересчитываться с нуля.

**Проверяемые вехи:**
- [ ] Доля раундов с полным re-forward падает с 34% до нуля при K=3.
- [ ] K=4 перестаёт быть убыточным: не ниже baseline 18.6 ток/с.
- [ ] Выход не изменился относительно до правки при том же seed и той же ширине.

### Ф4. Замер и выбор ширины (1 день)

После Ф1–Ф3 перемерить K от 1 до 8 на 27B Q8_0, на 32K и 128K, и зафиксировать значение по умолчанию.

**Проверяемые вехи:**
- [ ] Таблица ширин с долей принятия и скоростью, три прогона на точку, медиана.
- [ ] Значение по умолчанию в `scheduler.rs` обновлено с приведением чисел.

### Ф4б. Шлюз качества вместо снятого совпадения токенов (1 день)

BD-029 снял требование побитового совпадения, но взамен нужна измеримая защита от регрессии, иначе качество не контролируется вовсе.

- Провести `bin/perplexity.rs` через тот же путь, что и рабочий запрос: сегодня он идёт через batched-кеш и MTP не задействует, поэтому при сравнении даёт одинаковые числа независимо от настроек (проверено).
- Добавить в шлюз две меры: перплексия с MTP против без него, и совпадение выхода при ширине драфта 1.

**Проверяемые вехи:**
- [ ] Перплексия с включённым MTP отличается от базовой не более чем на 0.5% на корпусе в 2048 токенов.
- [ ] При ширине 1 выход совпадает токен в токен — расхождение здесь означает дефект реализации, а не арифметику: форма батча не меняется.
- [ ] Прогон с намеренно испорченным черновиком (артефакт от другой модели) шлюз отклоняет — то есть шлюз действительно что-то ловит.

### Ф5. Артефакты Q8 и подключение к серверу (2 дня)

Идёт параллельно Ф1–Ф4, ни от чего не зависит.

- `forge-convert` пакует MTP в Q8_0 для 4B, 9B и 27B.

- Сервер принимает путь настройкой, грузит по требованию (BD-027).
- Откат на обычный декод при доле принятия ниже 0.25 за окно из 32 раундов.

**Проверяемые вехи:**
- [ ] Три артефакта по 15 тензоров, проходят валидацию профиля.
- [ ] Артефакт от 4B, поданный к 9B, отклоняется с указанием размера.
- [ ] Поле `mtp` в ответе содержит `enabled: true` и ненулевые счётчики.

## Что этот план сознательно НЕ делает

**Не переписывает eager-путь.** Обоснование выше: фиксированная часть простоя — 1.33 мс, а пропорциональная снимается переходом на страничное чтение, которое уже написано.

**Не удаляет `kv_cache_batched`.** На нём висят шесть возможностей, которых у пула нет: скользящее окно BD-017 (в пуле нет вытеснения), Metal и CPU (пул только под CUDA), vision через mrope, seed из снимка, полные логиты в графовом префиле, плюс латентный выход за границу в append-ядрах. Каждая — отдельная работа, ни одна не ускоряет запросы.

**Не трогает мультимодальность.** Гейт PD-204 для mrope остаётся.

**Инвариант выхода закрыт решением BD-029** (2026-08-27): требуется сохранение распределения, а не реализации. Совпадение токен в токен снято как требование — блокировка Ф5 снята.

## Порядок

```
Ф1 (гейты) ──> Ф3 (обвал K=4) ──> Ф4 (замер ширины)
     └──> Ф2 (int8-путь)
Ф5 (артефакты) — параллельно всему
```

Ф1 первым и один: пока гейты широки, любой замер по MTP недостоверен, а значит вехи Ф3 и Ф4 нечем проверять.

## Риски

| риск | что делаем |
|---|---|
| Сужение гейта откроет гонку по hidden в graph-pool буфере | копировать hidden сразу после replay; веха Ф1 требует совпадения выхода с eager-путём |
| Латентный выход за границу в append-ядрах (`attn_window` до 81920 против `max_blocks`) | правка до снятия гейтов, иначе запись в чужой слот |
| Замер из `scheduler.rs:89` сделан на IQ2_XXS, а мы целимся в Q8_0 | Ф4 перемеряет на Q8_0; если +43% не воспроизведётся, пересматриваем ширину, а не замысел |
| Ф3 затронет корректность отката | веха требует совпадения выхода при том же seed |
