# logprobs в Chat Completions

**Статус:** спека, реализация не начата.
**Дата:** 28 августа 2026. Ведёт эту сессия, курирует сессия движка.
**Повод:** OQ-9. Нужны для двух вещей — числовой критерий устойчивости промпта
при сравнительных замерах и совместимость с клиентами, которые поле просят.

---

## Зачем

Сегодня при сравнении двух конфигураций мы отличаем настоящий дефект от
численного шума **голосованием разбиений**: гоняем промпт при нескольких
размерах чанка без короткого хвоста и берём в работу только совпавшие. Метод
рабочий — 28.08.2026 он отбраковал ровно тот промпт, на котором была ложная
тревога о дефекте `conv_state`, — но стоит четырёх перезапусков сервера вместо
одного запроса.

С `logprobs` устойчивость становится числом: если на шаге расхождения разрыв
между первым и вторым кандидатом порядка сотых, это грань, а не дефект.

---

## Контракт

Как в OpenAI Chat Completions, без отклонений.

### Запрос

| поле | тип | умолчание | ограничения |
|---|---|---|---|
| `logprobs` | bool | `false` | — |
| `top_logprobs` | int | — | 0…20, только при `logprobs: true` |

`top_logprobs` без `logprobs: true`, больше 20 или меньше 0 → **400** с внятным
текстом, тем же способом, что и переполнение контекста (BD-031).

### Ответ, обычный

```
choices[i].logprobs = {
  "content": [
    { "token": "…", "logprob": -0.31, "bytes": [208, 191],
      "top_logprobs": [ { "token": "…", "logprob": -0.31, "bytes": […] }, … ] },
    …
  ],
  "refusal": null
}
```

При `logprobs: false` — `"logprobs": null`.

### Ответ, потоковый

**Отклонение от контракта OpenAI, требует решения куратора.** Записи идут
ОТДЕЛЬНЫМ чанком с `"content": ""`, а не полем у текстового:

```
{"choices":[{"delta":{"content":"П"}, ...}]}
{"choices":[{"delta":{"content":""}, "logprobs":{"content":[{"token":"П",...}]}, ...}]}
```

Причина не в лени, а в устройстве потока. Наш сплиттер режет его на
размышление и ответ **по тексту** и придерживает недособранные UTF-8 хвосты,
поэтому у одной дельты движка бывает и ноль текстовых чанков, и несколько.
Привязать записи к одному из них без натяжки нельзя. При этом фаза определена
точно — по идентификатору токена `</think>`, а не по тексту, — так что
содержимое записей верное, спорна только их упаковка.

Пустая строка, а не `null`: некоторые клиенты падают на `null` там, где ждут
строку.

Что можно сделать иначе, если куратор сочтёт отклонение недопустимым: провести
`logprobs` пятым параметром через все восемнадцать точек выдачи чанков и
прикреплять к первому текстовому чанку каждой дельты, а при его отсутствии —
всё равно отдавать отдельным. Это больше кода и всё равно с оговоркой.

### Токены и байты

`token` — текст **одного** токена, `bytes` — его сырые байты массивом чисел.
Для байтовых и неполных UTF-8 токенов строка содержит U+FFFD, а `bytes`
остаются честными.

**Оговорка:** дельта текста может не совпадать с конкатенацией `token` на
границах — мы режем поток на reasoning и content и обрезаем пробелы при
переходе. Это допустимо и ожидаемо.

Замерено 28.08.2026 на границе размышления: токен `\n\n` сразу после
`</think>` получает запись (он content по идентификатору), а его текст
сплиттер обрезает как ведущий пробел. Поэтому склейка записей вышла
`"\n\nПариж"` при `content` равном `"Париж"`. Из размышления в 157 символов
записей не пришло ни одной — фаза по идентификатору работает.

### Что вне области

Только content-токены; reasoning-токены внутри think в `logprobs` не входят —
их нет и у OpenAI.

**Служебные токены записей не получают вовсе** — `<|im_end|>`, `<|endoftext|>`,
`<think>`, `</think>`. У OpenAI стоп-токен не входит ни в `message.content`, ни
в `logprobs.content`; у нас он декодировался бы в пустую строку с непустым
числом, то есть в мусор для клиента. Признак служебности — пустые байты:
`decode_bytes` отбрасывает токены вида `<|...|>`, а `<think>` и `</think>`
отсеиваются как границы фазы.

**Оговорка:** правило опирается на то, что у любого неслужебного токена
словаря есть хотя бы один байт. Для Qwen это так; при смене словаря
перепроверить.

Отсюда точная формулировка: **число записей равно числу неслужебных
content-токенов**, а не всех сгенерированных. Responses API и Anthropic Messages не трогаем: у Anthropic
поля нет вовсе, в Responses это `include=…` и отдельная работа.

## Семантика чисел

`logprob` — log-softmax по **всему словарю** от **сырых логитов модели**:
без температуры, без штрафов, без `top_k` и `top_p`.

Это «вероятность модели», как у OpenAI. Критерий устойчивости из-за этого не
зависит от настроек сэмплинга. Выбранный токен при температуре и штрафах может
иметь низкий `logprob` — это нормально и не признак ошибки.

### Почему нельзя взять готовое

Первоначальный замысел считал, что нужные числа в сэмплере уже есть и поле
обойдётся бесплатно. Это **не так**, `sampler.rs`:

```rust
let full_denom: Option<f32> = if top_k == 0 && idx.len() < logits.len() {
    Some(logits.iter().map(|&l| ((l - max_l) / temperature).exp()).sum())
} else { None };
```

Две причины:

1. Полная сумма считается **только при `top_k == 0`** и частичном отборе. Во
   всех наших пресетах `top_k = 20`, то есть в рабочем режиме её нет вовсе.
2. Когда она есть, в неё внесена температура.

Сверх того, штрафы за повторы меняют **порядок** кандидатов, поэтому топ-20
после штрафов — не топ-20 модели.

### Как считаем

Отдельный проход по сырым логитам **до того, как сэмплер что-либо трогает**.
Один проход даёт за раз:

- максимум `max`,
- сумму `Σ exp(l − max)` при температуре 1,
- топ-K сырых кандидатов (K ≤ 20) через небольшую кучу.

Отсюда `logprob(id) = logit − max − ln Σ` для любого идентификатора. Выбранный
токен получает своё число по тому же знаменателю **после** того, как сэмплер
выбрал его обычным путём.

**Абсолютное требование:** включение `logprobs` не меняет выбор токенов — ни
одного лишнего обращения к генератору случайных чисел, ни изменения порядка
операций отбора.

### Цена

Около 151 тысячи экспонент плюс отбор топ-K, на каждый сгенерированный токен
на слот, и **только при `logprobs: true`**.

**Замерено** 28.08.2026 на 3060, Ornith-9B Q6_K, один слот, запрос на 200
токенов, по три прогона на режим:

| версия | без `logprobs` | с `logprobs`, `top_logprobs: 5` | накладные |
|---|---|---|---|
| два прохода | 5,12 с | 5,48 с | **+7,0%** |
| **один проход** | 5,12 с | 5,42 с | **+5,8%** |

Оценка была 2–4%, факт оказался вдвое выше — оценку сняли, в спеке стоит замер.

Слияние в один проход (максимум, топ-K и сумма считаются вместе, накопленное
перемасштабируется при появлении большего максимума) дало 1,2 процентных
пункта. Порог принятия был «меньше процента — не менять», поэтому версия
оставлена.

Оставшиеся 5,8% — цена честного прохода по словарю на каждый токен. Отсечение
ниже `max − 30` уже стоит и в этих числах учтено. Дальнейшее удешевление
потребовало бы векторизации `expf`, и браться за неё стоит только если поле
начнут просить в горячем пути.

Возможное удешевление, если проценты окажутся заметны: не считать экспоненту
для логитов ниже `max − 20`, их вклад меньше 1e-9 и теряется в f32. Отдельным
коммитом после замера, не раньше.

## Где живёт

| файл | что делает |
|---|---|
| `src/sampler.rs` | проход по сырым логитам, возврат `{token, logprob, top}` при запросе; при выключенном — прежний путь без аллокаций |
| `src/engine_batched.rs` | `SlotSampler` и drain несут logprobs вместе с токенами до API |
| `src/api/openai.rs` | формат ответа, обычного и потокового |

**Спекуляция.** Принятые токены MTP проходят через тот же сэмплер построчно по
логитам проверки, значит и logprobs берутся оттуда же. Отдельного пути быть не
должно. Если при реализации окажется, что accept обходит сэмплер — остановиться
и обсудить, а не дописывать второй путь.

## Проверки, по которым принимаем

1. **Правильность числа.** Тест в `sampler.rs`: logprob первого кандидата равен
   log-softmax, посчитанному в лоб по всему словарю, в пределах 1e-5. Сумма
   `exp(top_logprobs)` не превышает единицы.
2. **Невмешательство.** Фиксированный seed, `logprobs` включён и выключен —
   тексты совпадают байт в байт. Проверить и на жадном режиме, и на
   температуре 0.7.
3. **Форма JSON.** Обычный и потоковый ответы против полей выше. В потоке число
   записей `content` равно числу токенов дельты. Байты многобайтного токена
   (кириллица) верные.
4. **Ошибки.** 400 на `top_logprobs` без `logprobs`, на значении больше 20 и
   меньше нуля.
5. **Живая проверка.** Сделана 28.08.2026. Механизм подтверждён, критерий —
   нет.

   Хрупкий промпт 1025 расходится между чанками 1024 и 2048 на восьмом шаге,
   и разрыв между кандидатами там 0,1223: `' entirely'` против `' almost'`.
   Это прямое подтверждение, что расхождение — почти-ничья, а не потеря входа.

   **Но разрыв не годится как критерий отбора.** У устойчивого промпта 513
   разрыв на том же восьмом шаге меньше — 0,0690, — и он не переворачивается;
   у 1537 он 0,0865, и тоже нет. То есть малый разрыв для расхождения
   необходим, но недостаточен: нужно ещё, чтобы возмущение от смены порядка
   суммирования его перекрыло, а величина возмущения у каждого промпта своя и
   из logprobs не видна.

   | длина | разошлись | разрыв в точке | минимум по ответу |
   |---|---|---|---|
   | 513 | нет | — | 0,0690 |
   | 514 | нет | — | 0,3152 |
   | 1025 | **да**, шаг 8 | **0,1223** | 0,1223 |
   | 1026 | нет | — | 0,1661 |
   | 1537 | нет | — | 0,0865 |
   | 1538 | нет | — | 0,1760 |

   Вывод для будущих замеров: отбор устойчивости остаётся голосованием
   разбиений. `logprobs` дают не замену ему, а объяснение — показывают, где
   именно и насколько близко модель колебалась.
