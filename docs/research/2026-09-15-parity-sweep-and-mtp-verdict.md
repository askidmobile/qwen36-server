# Ornith-1.5-9B: развёртка конфигураций и вердикт по MTP (2026-09-15)

Один GPU (RTX 3060 12 GB), один слот, один и тот же GGUF
`Ornith-1.5-9B-Q4_K_M.gguf`. Все замеры — на `yttri-win`, движок из
`D:\Projects\yttri-forge` (коммит `fbcbeab3` + синхронизированные 5 файлов),
llama.cpp — `D:\Projects\yttri-inference\llama.cpp-bin\llama-server.exe`.

## Метод

- Длинный профиль: 24 500 слов `word ` → 24 536 токенов (замер `prompt_tokens`
  из ответа).
- Короткий профиль: 400 слов → 436 токенов.
- Prefill: запрос с `max_tokens=1`, `prompt_tokens / time_total`.
- Decode: один и тот же промпт, `max_tokens=65`, три прогона подряд; decode
  считается как `(completion_tokens-1) / (t_тёплый − t_тёплый_prefill)`, чтобы
  вычесть повторный префил хвоста (у yforge это by design: кэшируется граница
  последнего чанка, а не конец промпта, см. `src/engine_batched.rs` — «Кешируем
  не конец промпта, а границу последнего чанка префила»).
- llama.cpp отдаёт собственные `timings.prompt_per_second` /
  `predicted_per_second` — берём их, плюс wall-clock.

## Итоговое сравнение с llama.cpp (24.5k токенов, один и тот же GGUF)

Прогон `final_ab2`: один и тот же промпт три раза подряд (`max_tokens=1`),
затем `max_tokens=65`, оба движка по очереди.

| метрика | yforge (f16 KV, chunk 16384, FFN 16384) | llama.cpp (`-fa on -c 131072`) |
|---|---|---|
| холодный префил 24 536 токенов | 16.35 s → 1500.8 t/s | 15.51 s → 1582.3 t/s |
| повторный префил того же промпта | 16.09 / 16.12 s | 0.11 s |
| декод на 24k | 37.9 t/s | 48.1 t/s |

### Главная находка: кэш промпта

llama.cpp на повторном идентичном промпте отдаёт первый токен за 0.11 s — он
держит KV всего промпта и переиспользует его целиком. yforge в этом же
сценарии префилит заново (16.09 s ≈ холодные 16.35 s). Разрыв ~150 раз по TTFT.
В диалоге это незаметно (хвост последнего хода всё равно новый), но для
«длинный документ + повторный/похожий вопрос» это потеря десятков секунд.

Дизайн yforge это объясняет: `src/engine_batched.rs` кэширует границу
последнего чанка префила, а не конец промпта — «запись во всю длину перестаёт
быть его префиксом, попадания не было бы никогда». Для многоходового диалога
это верно, поэтому повтор идентичного промпта не попадает.

### FFN_PREFILL_CHUNK=16384 вреден, откатили

Промежуточная развёртка давала у FFN_PREFILL_CHUNK=8192/16384 тёплый префил
1.07 s, но аккуратный замер (три одинаковых запроса) даёт 16.1 s — кэш не
срабатывает, а декод падает 41.5 → 37.9. Те 1.07 s были артефактом.
FFN_PREFILL_CHUNK возвращён к дефолту 4096.

Отдельная проверка с PREFIX_CACHE_MIB=0:

| конфигурация (кэш выключен) | холодный префил | декод |
|---|---|---|
| FFN 4096 | 1525.6 t/s | 37.9 t/s |
| FFN 16384 | 1526.6 t/s | 39.1 t/s |

При выключенном кэше разницы нет — эффект был во взаимодействии с кэшем.

## Попытка закрыть кэш промпта: хвост-сплит (отрицательный результат)

Гипотеза: если префилить последний токен отдельным чанком, снимок границы
ляжет на `len-1`, и повторный промпт досчитает один токен вместо хвостового
чанка. Реализовано в форке (`a554d5a7`, env `PREFIX_CACHE_TAIL_SPLIT=1`),
собрано под CUDA на yttri-win.

Замер на живом сервере (6 024 токена, три одинаковых запроса):

```
TS6K|prompt=6024|cold=4.229|rep2=3.985|rep3=3.982|cold_tps=1424.5
```

Повтор не ускорился: 3.98 s против 4.23 s холода, то есть кэш не срабатывает.
В логе есть `[pcache] snapshots saved: 1/1`, но строки `[pcache] slot=0 primed: ...`
(попадание) нет — запись сохранена, но `find` её не находит.

Разбор кода (`src/prefix_cache.rs`):

- `BLOCK_TOKENS = 64`, поиск идёт по хешам ПОЛНЫХ блоков
  (`boundary_hashes`: `n_blocks = tokens.len() / BLOCK_TOKENS`);
- `put` берёт ключ как `boundary_hashes(&tokens)[tokens.len()/BLOCK_TOKENS - 1]`,
  то есть при длине, не кратной 64, ключ и длина записи расходятся;
- `find` ищет кандидата только среди хешей блочных границ ВХОДЯЩЕГО промпта.

Вывод: снимок на невыровненной позиции (`len-1`) в текущем индексе не
находится. Правка откачена — `PREFIX_CACHE_TAIL_SPLIT` убран из `.env`,
сервер перезапущен на проверенной конфигурации.

Что это значит для следующей попытки: позиция снимка должна быть кратна 64
(странице paged-пула). Тогда цель — не `len-1`, а наибольшее кратное 64 ≤
`len-1`; остаток префила ≤ 65 токенов, это ~0.05 s, что практически совпадает
с 0.11 s у llama.cpp. Менять надо `put`/`find` (принимать и находить записи с
невыровненной длиной) либо хвост-сплит выравнивать по 64.

Итог по конфигурации прода (проверено): `KV_POOL_Q8=0`, `PREFILL_CHUNK=16384`,
`MTP=0`, `MTP_TIMING=0`, `FFN_PREFILL_CHUNK` не задан, `PREFIX_CACHE_TAIL_SPLIT`
отсутствует.

### Выровненный хвост-сплит: тоже без попадания

Попытка №2 (`f0a53e82`, `PREFIX_CACHE_TAIL_SPLIT=1`, `PREFIX_CACHE_TAIL_ALIGN=64`):
граница чанка ставится на наибольшее кратное 64 ≤ len-1 (для 6024 → 6016),
чтобы ключ `put` совпал с блочным хешем `find`.

Замер на живом сервере:

```
TSALIGN|prompt=6024|cold=4.175|rep2=3.808|rep3=3.871|cold_tps=1442.8
```

Повтор снова почти равен холоду (3.8 s против 4.2 s). В логе есть
`[pcache] snapshots saved: 1/1, entries 1, bytes 562 MiB`, но строки
`[pcache] slot=0 primed:` нет, а соседние `[hb]` показывают `pcache=0 ent/0MiB`
— то есть запись исчезает из кэша до повторного запроса. Диагностика `find`
(строка `[pcache] miss:`) тоже не печатается, что означает пустой `by_id`.

Значит проблема не в выравнивании, а в жизненном цикле кэша: запись живёт
один запрос и пропадает. Это следующий объект отладки: смотреть, где
`PrefixCache` пересоздаётся/очищается между запросами (в engine_batched он
`Option<PrefixCache>` рядом с обработчиком; возможно, на каждый запрос
поднимается новый инстанс движка/обработчика, и 24.5k-попадание в прошлых
замерах объяснялось другим путём).

Флаги отката: `PREFIX_CACHE_TAIL_SPLIT` и `PREFIX_CACHE_TAIL_ALIGN` не заданы
в `.env`, `bench-overrides.env` удалён, сервер перезапущен (pid 22500,
порт 18099, `kv_pool=f16`, `prefill_chunk=16384`).

### Важная поправка к методике: снимок снимается только в Decoding

В `src/engine_batched.rs` (блок «Prefix cache: снять снимок после завершения
префила») стоит условие:

```rust
if sched.slots_mut()[idx].status != SlotStatus::Decoding { continue; }
```

Снимок сохраняется, только если слот к этому моменту в состоянии `Decoding`.
Запрос с `max_tokens=1` завершается сразу после первого токена, к моменту
сохранения слот уже `Finished`, и снимок не сохраняется вовсе.

Следствие: замеры «повтор того же промпта» с `max_tokens=1` систематически
недооценивали кэш — в кэше нечего было находить. Поэтому:

- в развёртках `sweep`/`v3` тёплый префил был 6.2 s: снимок сохранялся от
  предыдущего запроса с 65 токенами, попадание приходилось на границу чанка
  (16 384) с досчётом 8 152 токенов;
- в `sweep2` у `FFN_PREFILL_CHUNK=8192/16384` тёплый префил стал 1.07 s —
  попадание почти в конец промпта (границы чанков сместились из-за под-чанков
  FFN); это настоящий эффект, а не артефакт;
- в тестах `TS6K`/`TSALIGN`, где все запросы шли с `max_tokens=1`, попаданий не
  было вообще, значит «повтор = холод» ничего не доказывает про хвост-сплит.

Правильная проверка хвост-сплита: сначала запрос с генерацией (`max_tokens=65`)
оставляет снимок, затем повторные `max_tokens=1`. Ожидание — повтор ~0.05–0.2 s
вместо 4 s. Этот прогон ещё не выполнен и является следующим шагом.

Отдельно зафиксировано, что `bench-overrides.env` действительно применяется:
`PREFILL_CHUNK=4096` и `KV_POOL_Q8=1` из файла перекрыли `.env` (в логе
`prefill_chunk = 4096`, `kv_pool = q8`), то есть инструмент A/B рабочий.

Конфигурация: `KV_POOL_Q8=0`, `PREFILL_CHUNK=16384`,
`PREFIX_CACHE_TAIL_SPLIT=1`, `PREFIX_CACHE_TAIL_ALIGN=64`, промпт 24 528

```

Механизм подтверждён логом:

## Стоимость попадания в prefix cache: фикс + линейный член

Замеры повтора после снимка (запрос с генерацией, затем повторные
`max_tokens=1`), конфигурация прода:

| промпт, токенов | повтор, s |
|---|---|
| 3 028 | 0.376 / 0.322 |
| 6 027 | 0.430 / 0.398 |
| 24 528 | 0.863 / 0.780 |

Линейная аппроксимация: `t ≈ 0.25 s + 0.022 ms × токен`. То есть попадание
почти целиком состоит из восстановления снимка (host→device копия сотен МиБ)
плюс фиксированные ~0.25 s на переинициализацию/досчёт хвоста, а не из
префила как такового: досчитываются единицы токенов (лог: «досчитать 11»).

У llama.cpp повтор идентичного промпта — 0.11 s, у нас 0.78 s на 24.5k.
Отсюда следующий шаг с оценкой: держать горячие снимки (1–2 последних) в VRAM
вместо host, либо передавать их страницами во время досчёта хвоста. Ожидание —
0.78 s → ~0.3 s (останется фиксированный член и распаковка страниц).

Примечание: замер на 12 000 слов оказался невалидным — запрос с генерацией
вернулся за 0.286 s (ошибка/пустой ответ), снимок не сохранился, и повторные
запросы честно префилили целиком (13.7 / 16.0 s). В таблицу не включён.

## Где именно теряется декод: GDN-ядро с крошечной сеткой

Разбор CUDA-пути gated delta net в декоде
(`engine/qwen35-batch/src/real/delta_rule_cuda.rs`, `dispatch_delta_rule`,
вызывается на каждый слой на каждый токен):

| kernel | grid | block | строк |
|---|---|---|---|
| `delta_conv1d_prep` | `ceil(channels/256)` ≈ 1 блок | 256 | 179 |
| `delta_l2_norm_expand` | `n_v` (8–16) | `head_k_dim` | 203 |
| `delta_rule_kernel` (сама рекуррентность) | **`n_v` (8–16 блоков)** | `head_v_dim` | 221 |
| `delta_norm_gate_kernel` | `n_v` | `head_v_dim` | 243 |

То есть рекуррентное ядро запускает 8–16 блоков по ~128 потоков —
это 1–2 тысячи потоков на GPU с 3584 ядрами, загрузка единицы процентов.
При ~33 слоях это ~132 запуска на шаг декода, и именно этот блок даёт 58 %
времени шага (профиль GPROF). Для сравнения, в fused-prefill
(`dispatch_delta_rule_prefill`, строки 319+) уже есть более широкая сетка —
на декоде её нет.

Что делать (стандартный приём из flash-linear-attention / mamba.cpp):
параллелить обновление по элементам матрицы состояния `[head_k_dim ×
head_v_dim]` внутри головы, а не только по головам. Тогда сетка становится
`(n_v, hkd_tiles, hvd_tiles)` и задействует тысячи потоков вместо сотен.
Ожидаемый эффект — снятие большей части из 58 % времени шага декода; это
главный оставшийся рычаг по декоду (сейчас 41.5 t/s против 48.1 у llama.cpp).

Проверять: декод t/s на 24k и на коротком промпте (текущие опорные значения
41.5 и 50.3), плюс численная сверка логитов (`tests/fa2_paged`,
`qwen35moe_reference` и real-тесты).

### Устройство рекуррентного ядра и план переписывания

`candle-kernels/src/delta_rule.cu:206` (`delta_rule_kernel`):

```
Launch: grid=(n_v_heads,1,1), block=(head_v_dim,1,1)   // 8 голов -> 8 блоков x 128 потоков
threadIdx.x = col (0..hd-1)
```

Каждый поток владеет ОДНИМ столбцом матрицы состояния и делает три
последовательных прохода по 128 строкам:

```
1. decay:  state[row][col] *= exp(gate)
2. sk[col] = sum_row(state[row][col] * k[row])     // 128 итераций
3. d[col]  = (v[col] - sk[col]) * beta
4. state[row][col] += k[row] * d[col]              // 128 итераций
5. out[col] = sum_row(state[row][col] * q[row])    // 128 итераций
```

При 8 головах это 8 блоков x 4 варпа = 32 варпа на 28 SM (примерно один варп
на SM): задержки глобальной памяти прятать нечем. По профилю GPROF это и есть
58 % шага декода.

План без изменения математики — тайлить состояние ещё и по строкам. Блок
`(32 col, 8 row)` покрывает тайл `[8 x 32]`, сетка становится
`(n_v_heads, hd/8)` = 8 x 16 = 128 блоков, все SM заняты. Свёртка по строкам
для `sk[col]` делается в общей памяти: каждый поток считает свой вклад, затем
8 значений на столбец сворачиваются за 3 шага; далее `d[col]`, обновление и
`out` считаются такими же тайлами.

Порядок безопасного внедрения:

1. добавить `delta_rule_kernel_tiled` рядом с текущим, рабочий путь не трогать;
2. включать флагом `YTTRI_GDN_TILED=1` (по умолчанию выключено);
3. сверить логиты на `real_qwen35_*` / `qwen35moe_reference` и прогнать A/B
   декода (24k и короткий промпт);
4. включать по умолчанию только при подтверждённом выигрыше и совпадении чисел.

Опорные значения для A/B: декод 41.5 t/s на 24k, 50.3 t/s на коротком промпте
(f16 KV, chunk 16384, tail-split).

## Тайловое ядро GDN: первый замер (+3.7 %)

`delta_rule_kernel_tiled` (флаг `YTTRI_GDN_TILED=1`, по умолчанию выключено),
блок `(32 col, 8 row)`, сетка `(n_v, ceil(hd/32))`; свёртка по строкам — в
общей памяти блока. Математика та же, что у старого ядра. Коммит форка
`8ce4f0bd`.

```

В пересчёте на токен: 23.5 ms/ток против 22.6 ms/ток — **+3.7 %**. Ответ

Вывод: узкое место подтверждено (загрузка SM), но на коротком промпте выигрыш

### Поправка: тайловое GDN-ядро нейтрально на длинном прогоне

Первый замер на 128 токенах дал +3.7 %, но он не воспроизвёлся. Контрольный
прогон: 256 токенов генерации, три подряд (в логе шесть записей — прогрев плюс
три измерения), `temperature=0`, f16 KV, chunk 16384:

```
AB2|off  |n=256|ms=20,21,20,22,20,21|median_ms=20.21
AB2|tiled|n=256|ms=20,18,20,17,20,19|median_ms=20.18
```

Медиана не сдвинулась (20.21 против 20.18 мс/ток). Внутри серии у тайлового
варианта видны выбросы 17–18 мс, но на медиану они не влияют.

Вывод: гипотеза про загрузку SM подтверждается косвенно (выбросы), но
row-tiling сам по себе выигрыша не даёт. Похоже, ядро упирается в трафик к
матрице состояния, а не в латентность запуска: на голову это `hd*hd*4` =
64 КиБ, которые за шаг читаются и пишутся по два раза. То есть следующий
шаг — не расширять сетку, а сократить обращения к состоянию (держать тайл
в shared/registers между фазами decay→sk→update→out, либо кэшировать
`gate_exp` и `beta` в регистрах вместо повторных чтений).

`YTTRI_GDN_TILED` остаётся выключенным по умолчанию.

## Разбор attention-фазы (28 % шага): сетка по головам

`engine/qwen35-batch/src/real/flash_decode_cuda.rs` (dispatch_flash_decode):

| режим | grid | block |
|---|---|---|
| обычный | `(n_head, 1, 1)` | 128 |
| split-k | `(n_head, splits, 1)` | 128 |

При 8 attention-слоях и `n_head` порядка 8–32 это десятки блоков по 128
потоков на слой, то есть та же картина, что была у GDN: мало параллелизма на

Отличие от GDN: у attention есть готовый split-k режим
(`ENABLE_SPLITK_DECODE=1`, только при `kv_len >= 2048`), но его откатывали
раньше как «диагностический, даёт дрейф без выигрыша» — замер делался на
kv_len=2048 и до перехода на f16 KV. Сейчас контекст другой (f16 KV, длины
24k–100k), поэтому его стоит перемерить именно на длинном контексте: 5.5 мс на
8 слоёв — это 0.69 мс на слой, и при росте контекста эта часть растёт.

Порядок: (1) `ENABLE_SPLITK_DECODE=1` на 24k, сравнить с текущими 41.5 t/s;
(2) если выигрыш есть — проверить численно (логиты/качество) и только затем
включать; (3) если нет — смотреть, сколько ядер из 128 потоков реально занято
на слой, и расширять сетку по `kv_len` (тайлинг по блокам KV), как в GDN-плане.

## GPROF=3 не годится для декода: инструментирует префил

Прогон `GPROF=3` на декоде дал только строки префильного внимания:

```
[pfp-attn] f16=1 proj=0.1 kv=0.1 fa2=39.4 wo=1.2
[pfp-attn] f16=1 proj=0.1 kv=0.0 fa2=16.9 wo=0.2
... (fa2 падает с ростом позиции)
```

То есть это инструмент префила (fa2 на чанк), а не раскладка внутри
декодного GDN. Чтобы получить разбиение четырёх GDN-ядер на слой в декоде,
нужно добавить счётчики в `dispatch_delta_rule` (4 события на слой) — это
правка кода, а не переключение env.

Побочно зафиксировано: на префиле `fa2` при малой позиции стоит 39 мс и
падает до 0.6 мс на хвосте — то есть префильное внимание хорошо масштабируется
с ростом позиции, и разрыв −5 % по префилу не в нём.
