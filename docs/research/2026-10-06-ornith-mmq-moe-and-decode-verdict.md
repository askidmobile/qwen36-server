# Ornith-1.5-35B-A3B Q8_0: MoE на тензорных ядрах и граница паритета с llama.cpp

Стенд: `forge-gpu` (RTX 4090 48 ГБ, 49140 МиБ), Q8_0 GGUF, один слот,
контекст 262144. Замеры — свежий промпт на каждый повтор (общий префикс у
llama.cpp обрывается маркером в начале, иначе prompt cache даёт неправдоподобные
TTFT), медиана из 3–4 повторов. Промпты: 3916 / 12566 / 54448 токенов.

## Что было исходно

MoE-префил шёл через MMVQ `indexed_moe_forward[_dual]_q8_0_q8_1` с сеткой
`(n, batch, topk)`. Вес эксперта перечитывается на каждую пару (token, route);
при 256 экспертах, topk=8 и чанке 512 это ~1.1 ТБ чтений на чанк. Префил —
1074 t/s, то есть в 4.5 раза медленнее llama.cpp.

## Что сделано

Группировка пар по экспертам (count+scan → sort → обратная раскладка) и
`mul_mat_q` в layout llama.cpp (`ids_dst` + `expert_bounds`), эксперты
перебираются внутри ядра — вес эксперта читается один раз. Редукция topk
без атомиков. Ширина x-тайла подбирается по `ncols_max`, `PREFILL_CHUNK=4096`.

| конфигурация | префил |
|---|---|
| базовый MMVQ, чанк 512 | 1074 t/s |
| grouped-MMVQ (Q8_0) | 908 t/s |
| MMQ-MoE, чанк 512 | 4976 t/s |
| MMQ-MoE, чанк 4096, x64 | 7068 t/s |
| MMQ-MoE, чанк 4096, x128 | 7503 t/s |

Побочно найден и починен реальный баг: `nvcc` генерирует `trap` вместо тела
ядра при `atomicAdd` по локальной переменной («Cannot do atomic on local
memory»). Так были сломаны и новое sort-ядро, и лежавшее в движке неиспользуемое
`moe_sort_by_expert_kernel`. Счётчик перенесён в shared memory. Симптом был
обманчивым: падал следующий плотный MMQ в DeltaNet, а не sort.

Регресс-гард: `engine/candle-core/examples/moe_mmq_selftest.rs` — MMQ-MoE против
matmul на CPU по тем же деквантованным весам, относительная ошибка 4.7e-4,
mismatch=0.

## Декод: что пробовали и почему не вышло

По nsys наш MoE-декод стоит ~2.19 мс/токен против ~1.66 у llama.cpp — это и
есть недостающие ~0.6 мс. Плотные матрицы при этом у нас не хуже, так что
узкое место — рукописные `indexed_moe_forward[_dual]`.

| эксперимент | декод | вердикт |
|---|---|---|
| базовый MMVQ | 125.0 | отправная точка |
| MMQ-MoE на декоде | 89.9 | −28%: тайл из 32 колонок ради одной |
| fused `silu*mul` | 125.9 | +0.7%, оставлено |
| 4 строки веса на блок (оба ядра) | 125.3 | нейтрально |
| 8 warps вместо 4 | 119.8 | −4% |
| 2 строки на блок (только `down`) | 115.6 | −9% |
| совместный разбор потоков по (строка, k) | 126.4 | нейтрально |

Последний эксперимент стоит описать отдельно, потому что он проверял настоящую
ошибку, а не подбор константы. В `indexed_moe_forward` k-индекс брался прямо из
`tid`, и при k=512 (down-проекция Ornith) blocks_per_row_x=16 при
blocks_per_iter=32 — половина блока из 128 потоков вообще не попадала в цикл, на
каждом из 41 слоя каждого шага. Исправление: делить потоки сразу по
(строка, k), при нехватке слотов брать столько строк, сколько помещается,
и считать слот редукции по номеру warp-группы строки.

Починка заняла три итерации и два ложных улучшения: при rows_per_block > 1
редукция сначала суммировала чужие warp-ы (неинициализированный shared memory),
затем писала в слот `threadIdx.y - 1` вместо слота warp-группы. Обе версии
давали правдоподобные 132 и 134 t/s при выводе из одних `!!!!` — скорость
росла именно потому, что ядро считало не всё. После починки вывод связный, а
декод 126.4 t/s, то есть **простаивавшие потоки не стоили ничего**.

Вывод, который стоит сохранить: ядро упирается не в разбор потоков и не в
число блоков. Шесть проверенных рычагов (алгоритм, ширина тайла, warps, строки
на блок, слияние элементных операций, разбор потоков) не дают ничего. Чтобы
догнать llama.cpp, нужен другой дизайн ядра — по образцу его
`mul_mat_vec_q_moe` с собственной раскладкой блоков, а не настройка
существующего. Это отдельная работа; увеличение параллелизма split-K по k —
кандидат, но требует детерминированной редукции вместо атомиков.

Ориентир, который дал пользователь: vLLM на этой модели показывает ~90 t/s
префил и ~140 декод. По префилу мы перекрыты в ~75 раз, декод 124–143.

## Воспроизведение

Конфиг: `/root/ornith.env` + `run_ornith.sh` на стенде, `MOE_MMQ=0` откатывает
MMQ-путь, `PREFILL_CHUNK` и `MOE_MMQ_X` переопределяются из окружения.
