# Ornith-1.5-35B-A3B Q8_0: декод обогнал llama.cpp на всех окнах

Дата: 2026-10-07. Стенд `forge-gpu` (RTX 4090 48 ГБ, CUDA 12.8, AMD EPYC, 12
потоков), окно 262144, один слот. Конфигурация обоих движков одинаковая:
q8-KV, flash-attention, окно 262144. У yforge `PREFILL_CHUNK=4096`, `MOE_MMQ=1`.

## Как воспроизводилось

Один процесс на вариант, движки не работают одновременно. Перед каждым
запуском GPU дренируется до `nvidia-smi --query-gpu=memory.used ≤ 400 МиБ`.

Флаги движков (окно у всех одинаковое):

- **yforge** — env-файл `/root/yforge.env`: `CTX=CONTEXT_LIMIT=262144`,
  `SLOTS=1`, `GPU_ONLY=1`, `GPU_LAYERS=999`, `KV_POOL_Q8=1`,
  `KV_CACHE_TYPE=q8`, `CUDA_GRAPHS=1`, `PGRAPH=on`, `FLASH_ATTN=1`,
  `PREFIX_CACHE_MIB=0`, `SAMPLING_LOCK=1`, `MOE_EXPERTS=auto`, `MOE_MMQ=1`,
  `PREFILL_CHUNK=4096`.
- **llama.cpp** — `llama-server -m Ornith-1.5-35B-Q8_0.gguf -c <CTX> -ngl 999
  --parallel 1 --api-key x --no-warmup -fa on --cache-type-k q8_0
  --cache-type-v q8_0`.
- **vLLM** — `vllm serve /root/models/ornith-fp8 --max-model-len <CTX>
  --gpu-memory-utilization 0.90 --max-num-seqs 1 --trust-remote-code
  --served-model-name ornith`.

Харнессы (лежат на сервере в `/root/`, не в репозитории — это стендовые
скрипты):

| файл | что делает |
|---|---|
| `ornith_ab.py` | yforge или llama.cpp: TTFT, префил, декод, dVRAM; сэмплинг greedy |
| `ornith_ab_fair.py` | то же, но одинаковые поля сэмплинга на обеих сторонах (temp=0.6, top_k=20, top_p=0.95, seed=7) |
| `ornith_ab_topk.py` | развёртка по `top_k` при фиксированном числе потоков отбора |
| `vllm_bench.py` | те же метрики для уже поднятого vLLM |
| `three_way2.sh` | vLLM → yforge → llama.cpp подряд на одном окне |
| `interleave.sh` | чередование yforge/llama.cpp по кругу (контроль дрейфа) |
| `start_ttft.py` | «старт процесса → первый токен» для обоих движков |
| `determinism20.py` | 20 одинаковых запросов в одном процессе (проверка воспроизводимости) |
| `load_loop.py` | нагрузочный цикл для профилей nsys |

Методика: уникальный промпт на каждый повтор (иначе prompt cache llama.cpp
даёт фальшивый TTFT), медиана из 2–3 прогонов с пропуском первого, промпты
фиксированной длины (2656 / 12 578 / 54 460 / 108 928 / 119 998 токенов).
Профили ядер — `nsys profile --trace=cuda --cuda-graph-trace=node --delay=18
--duration=40`, нормировка на токен по инварианту «41 слой MoE на токен».

Грабли, которые надо помнить при повторных прогонах:

- `PREFILL_CHUNK=4096` обязателен: на дефолтных 512 префил падает с ~7600 до
  ~5000 t/s.
- `CUDA_GRAPHS=1` обязателен: без графов декод падает с ~153 до ~64 t/s.
- Повторный одинаковый промпт у llama.cpp почти не считает префил — сравнение
  на нём бессмысленно (наблюдалось 24k t/s против реальных 4.9k).
- `SAMPLING_LOCK=1` подставляет model-card (temp=0.6, top_k=20) независимо от
  запроса; для честного сравнения лок снимается, либо используется
  `ornith_ab_fair.py`.

## Корень: стоимость сэмплинга, а не ядер

Профиль декода (`nsys`, окно 8192) давал ядерное время практически равное:
yforge 6.038 мс/ток против 5.991 у llama.cpp, при этом end-to-end декод был
хуже на ~3 %. Изучение host-профиля объяснило остаток: 55 % времени CUDA API
уходило в `cuMemcpyDtoH_v2`, ровно по одной копии на токен — сервер копировал
на CPU **весь словарь логитов** (248 320 × f32 ≈ 993 280 байт) ради выбора
следующего токена. Плюс сам отбор шёл через rayon-пул.

Изоляция на живой модели (окно 8192, продовая конфигурация):

| конфигурация | декод |
|---|---|
| `TEMPERATURE=0` (argmax, без отбора кандидатов) | 153.5 |
| `TEMPERATURE=0.6; TOP_K=20` (прод) | 142.6 |
| `TEMPERATURE=0.6; TOP_K=20; RAYON_NUM_THREADS=1` | **152.7** |
| `TEMPERATURE=0.6; TOP_K=1` (отбор почти выключен) | 143.3 |

То есть платится не за алгоритм отбора (TOP_K=1 и TOP_K=20 равны), а за
подъём rayon-задачи на каждый токен. Калибровка по k на живом сервере:

| k | последовательно | параллельно (12 потоков) |
|---|---|---|
| 1 | 153.9 | 138.5 |
| 8 | 152.7 | 142.0 |
| 20 | 153.1 | 143.5 |
| 64 | 153.1 | 143.8 |
| 128 | 153.3 | 144.1 |
| 256 | 153.0 | 144.3 |
| 1024 | 152.7 | 143.4 |

Последовательный проход по словарю быстрее на всём диапазоне: один поток
обходит 248 320 логитов за ~0.2 мс, тогда как координация пула дороже.
Поэтому дефолт `top_k_indices` — последовательный (`TOP_K_THREADS=N>1`
включает параллельный, для больших батчей и будущих словарей).

Следствие: выигрыш декода на 8K/32K держится только при одинаковом сэмплинге.
В продовой конфигурации `SAMPLING_LOCK=1` подставляет model-card
(temp=0.6, top_k=20) независимо от запроса — то есть на равный сэмплинг
выходит сравнение с llama.cpp, у которого таких пресетов нет.

- **env-ручки горячего пути** закешированы через `OnceLock`: ~130 `getenv`

## Верификация

- Тесты сэмплера: 15/15, включая `top_k_indices_matches_full_sort` — новая
  последовательная ветка обязана совпадать с полной сортировкой.
- Отбор: 15/15 тестов сэмплера, включая `top_k_indices_matches_full_sort`
  (новая последовательная ветка обязана совпадать с полной сортировкой набором

- Честность сравнения: одинаковые поля сэмплинга в запросе, уникальный промпт
  на повтор (иначе prompt cache llama.cpp даёт фальшивый TTFT), оба движка
  стартуют с нуля и меряются подряд.

## Третья точка отсчёта: vLLM 0.28 на официальной FP8

Замер тем же харнессом в той же серии (окно одинаковое, свежий промпт на
повтор; у vLLM `--gpu-memory-utilization 0.90`, `--max-num-seqs 1`).

| окно | движок | префил | декод | VRAM |
|---|---|---|---|---|
| 32768 | vLLM FP8 | **10695** | 145.9 | 42 487 |
| 32768 | yforge Q8_0 | 7580 | **147.2** | **35 783** |
| 32768 | llama.cpp Q8_0 | 5222 | 140.1 | 35 703 |
| 131072 | vLLM FP8 | **8814** | 131.6 | 42 487 |
| 131072 | yforge Q8_0 | 6864 | **136.9** | **36 775** |
| 131072 | llama.cpp Q8_0 | 4923 | 118.6 | 37 008 |

Итог: против **llama.cpp** выиграны все метрики (префил, декод, TTFT, старт,
VRAM). Против **vLLM** мы впереди по декоду и VRAM, но отстаём по префилу
(7580 против 10 695 на 32K, 6864 против 8814 на 128K). Разрыв структурный:
vLLM считает префил на тензорных ядрах в FP8, а у нас Q8_0 GGUF, и это
flops-ограниченная часть, где формат весов решает. Декод, наоборот, ограничен
полосой памяти, где наш q8-GGUF и компактный paged-пул дают преимущество
(плюс vLLM держит на 5-6 ГиБ больше VRAM под KV-пул).

Ориентир, который давал пользователь (vLLM «~90 t/s префил, ~140 t/s
генерация»), нашим решением перекрыт по обоим пунктам: 7580/147.2 на 32K.

## Открытый дефект: декод не воспроизводится побитово

Текстовый оракул для этой серии не годится, и это стоит зафиксировать
отдельно. Контроль «одна и та же конфигурация дважды» дал **разный текст**:

| контроль | результат |
|---|---|
| `temp=0.6`, seed=1234, два запуска | `len 624 / 605`, sha разные |
| `temp=0.6`, последовательный vs параллельный отбор | sha разные |
| `temp=0` (greedy), два запуска | `len 551 / 562`, sha разные |

То есть при одинаковом промпте и одинаковой конфигурации выдача не побитовая.
Greedy тоже расходится — значит не только стохастика: логиты GPU не
бит-в-бит стабильны между запусками (недетерминированный порядок редукций /
графы). Раньше это маскировалось тем, что в продовой конфигурации
`SAMPLING_LOCK=1`, а текстовые сверки шли на длинных ответах, где первое же
расхождение обрывает LCP.

Уточнение: нестабильность **перемежающаяся**, а не постоянная. Внутри одного
процесса на 5 одинаковых запросах расхождение воспроизводилось в одной серии
(2 уникальных результата из 5) и отсутствовало в двух других (5/5 идентичны);
с выключенными графами (`CUDA_GRAPHS=0`) серия была 5/5 идентична. То есть
подозреваемый — захват/перезахват CUDA-графа (переиспользование буферов между
прогонами), но одного наблюдения мало: нужна серия на 20+ запросов в каждом
режиме. Проверка не входит в задачу о преимуществе над llama.cpp и вынесена
отдельно.

Практические следствия: сравнивать движки по тексту можно только по метрикам
(скорость, VRAM), а эквивалентность ядра — на изолированных стендах с
CPU-эталоном (как `delta_decode_tile_ab.cu`) или юнит-тестами на фиксированных
логитах. Это отдельная задача: найти источник нестабильности логитов
(кандидаты — порядок редукций в MoE-декоде и захват CUDA-графа).

## Ограничения

- Замеры на одной машине и одном окне; ±3 % дрейф между запусками.
- vLLM не участвовал в этой серии (остаётся быстрее по префилу за счёт FP8
  tensor-core, но потребляет на ~5 ГиБ больше).
- llama.cpp-дефолты сэмплинга отличаются от наших; здесь сравнивались равные
  условия, а не «как настроено из коробки».
