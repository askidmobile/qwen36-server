# Ornith-1.5-35B-A3B Q8_0: warp-роутер, чистое поядерное сравнение и ложный выигрыш DeltaNet

Стенд: `forge-gpu` (RTX 4090 48 ГБ, 49140 МиБ), Q8_0 GGUF, один слот.
Методика та же, что в `2026-10-06-ornith-mmq-moe-and-decode-verdict.md`:
свежий промпт на повтор, медиана из 3–5 прогонов.

## Что дало результат

### 1. Warp-на-токен роутер top-k — декод +2.2% (коммит `363be3d8`)

Блочный `moe_softmax_topk_kernel` на 256 экспертах делал 8 раундов argmax, в
каждом два `__syncthreads()` и два прохода по shared. По профилю nsys это
6.4 мкс на слой против 2.6 мкс у llama.cpp `topk_moe_cuda` — роутер был вторым
по величине проигрышем декода после DeltaNet.

`moe_softmax_topk_warp_kernel`: одно warp на токен, все 256 логитов в 8
регистрах на поток, softmax и top-k через shuffle — ни shared, ни барьеров,
4 токена на блок.

| конфигурация | декод (ctx 32768) |
|---|---|
| блочный (`ROUTER_WARP=0`) | 132.2 |
| warp (`ROUTER_WARP=1`) | **135.1** (+2.2%) |

Префил не изменился (7568 → 7590), VRAM тот же. Эквивалентность подтверждена
автономным nvcc-тестом против CPU-эталона: **mismatch=0, maxdiff=1.5e-8**,
включая подложенные ties (два эксперта с одинаковым логитом) — тай-брейк по
меньшему индексу сохранён. Плюс регресс-гард в
`gpu_router_matches_stable_cpu_top8` сравнивает новое ядро со старым.

### 2. Чистое поядерное сравнение декода (nsys, только декод)

Прежние профили снимались целиком и включали префил, поэтому их нельзя было
сопоставить: в окне оказывалось разное число токенов. Здесь сервер запускался
под `nsys --delay=18 --duration=45`, а в окне крутилась нагрузка коротким
фиксированным промптом с длинной генерацией — префил занимает <1% окна.

Нормировка на токен по числу вызовов MoE-роутера (41 слой):

| семейство | yforge мс/ток | llama.cpp мс/ток | Δ |
|---|---|---|---|
| чтение весов (все matvec + MoE-проекции) | 4.04 | 4.18 | −0.14 |
| DeltaNet (все ядра) | 0.32 | 0.12 | **+0.20** |
| роутер top-k | 0.16 | 0.11 | +0.05 |
| rmsnorm | 0.19 | 0.27 | −0.08 |
| quantize активаций | 0.30 | 0.37 | −0.08 |
| flash attention | 0.19 | 0.10 | +0.09 |
| элементные add/mul/silu | 0.37 | 0.34 | +0.03 |
| **ИТОГО** | **6.05** | **6.02** | **+0.03** |

Плюс: yforge делает 1472 ядра на токен, llama.cpp — 1706. Суммарная занятость
ядер практически равна (за окно 45 с: yforge 20963 мс при 3465 токенах,
llama.cpp 20262 мс при 3366 токенах), простой в обоих ~53–55%.

Вывод: по ядрам это **паритет**, а разрыв, который виден в end-to-end метрике,
надо искать в зазорах между ядрами и в хвосте, а не в отдельных семействах.

## Ложный выигрыш: `DELTA_COLS=16` и класс ошибки «константа против blockDim»

Эксперимент с числом блоков DeltaNet дал внешне убедительный результат и
**воспроизвёлся при реверсе порядка**:

| прогон | default (COLS=32) | COLS=16 |
|---|---|---|
| 1 | 135.6 | 142.0 |
| 2 | 133.0 | 140.2 |

То есть +5% и выше llama.cpp на 32K. На деле это был баг. Ядра
`delta_rule_kernel_batched_splitc` брали номер столбца состояния из
**константы** `DR_COLS=32`:

    col = blockIdx.z * DR_COLS + threadIdx.x

а `launch` задавал `block_dim.x = COLS = 16`. Половина столбцов состояния
вообще не считалась, ядро работало вдвое меньше и потому «ускорялось».
Проверка эквивалентности выдачу не поймала бы, если бы сравнивались только
две сломанные конфигурации между собой — контроль «COLS=32 против COLS=32»
тоже дал расхождение (харнесс нестабилен по тексту на длинных ответах).
Поймано тем, что вывод при COLS=16 оказался мусорным (`;`, `https``, `` ``` ``).

Исправление (yttri-forge, ветка main; перф-проверка на GPU не снята — стенд
отключился):
- ядра `*_splitc` и `*_split` берут stride/число групп из фактических
  `blockDim.x`/`blockDim.y`, а не из констант `DR_COLS`/`DR_ROWGRP`;
- предохранитель внутри ядра: `hd % cols != 0 || hd % rowgrp != 0` → выход;
- fail-closed проверки в Rust-диспетчере для **фактически выбранной**
  раскладки (`DELTA_DECODE=cols`), чтобы не ронять рабочий путь из-за ручки,
  к нему не относящейся.

Доказательство бага — эмуляция математики ядра на CPU
(`yttri-forge/docs/tools/delta_layout_sim.py`, `delta_coverage_proof.py`).
Модель считает, какие `(row, col)` состояния ядро реально трогает, при
раскладке из константы и из `blockDim`:

| раскладка | покрытие `hd*hd` | ΔS к эталону |
|---|---|---|
| COLS=32, const (дефолт) | 100.0% | 3.6e-15 |
| COLS=32, blockDim | 100.0% | 3.6e-15 |
| **COLS=16, const** | **50.0%** | **5.9e+00** ← ложное ускорение |
| COLS=16, blockDim | 100.0% | 3.6e-15 |

То есть при дефолтах правка численно **ничего не меняет**, а при COLS=16
старый код покрывал ровно половину столбцов — отсюда «+5%» при мусорном
выводе.

Правило, которое стоит сохранить: **если ручка конфигурации меняет раскладку
ядра, ядро обязано читать раскладку из `blockDim`, а не из `#define`.**
Иначе любая «оптимизация» такой ручкой будет измерять неполный расчёт.

## Продление вставки: обсуждение MTP F32 (отклонено)

Пользователь спросил, зачем MTP-роутеры в F32, если вся система int8. Ответ:
F32-роутеры — это формат публикации в GGUF (82.3 МиБ, 0.23% веса модели), не
наш выбор; на скорость и память они почти не влияют. MTP на Ornith закрыт
как убыточный ещё раньше (nextn-слой содержит полноценный MoE).

Профиль vLLM на декоде (torch profiler, 150 токенов): 38.6% GPU-времени —
**BF16 GEMV** cuBLAS, 17.8% — FP8 MoE-эксперты, 14.2% — cutlass FP8 blockwise
GEMM. То есть большая часть его декода — BF16 по слоям, исключённым из
квантования (`linear_attn`, `shared_expert_gate`, `mtp`), а не FP8. Наше
преимущество — VRAM (37.6 против 43.5 ГиБ) и GGUF-путь.

## Ограничение

Стенд `forge-gpu` отключился в ходе сессии (ICMP 100% loss, SSH timeout) —
вероятно, истёк срок аренды. Поэтому:
- исправление ядра DeltaNet (blockDim вместо константы) **не собрано и не
  проверено** на GPU, локальные правки откачены, чтобы не укладывать в git
  непроверенное;
- чистое сравнение с llama.cpp с warp-роутером **и** исправленным DeltaNet
  осталось неснятым.
