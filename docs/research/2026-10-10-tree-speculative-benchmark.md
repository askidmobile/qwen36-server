# Tree speculative decoding на Qwen3.5-9B: A/B против baseline и linear MTP

Дата: 2026-10-10.
Стенд: `yttri-win` (RTX 3060 12 GB, Windows).
Модель: `Qwen3.5-9B-Q4_K_M.gguf`.
MTP-голова: `mtp-Ornith-1.5-9B-head-Q8_0.gguf`.
Сервер: `qwen36-server` из worktree `qwen36-tree-server`, собран с `cargo build --release --features cuda`, `CUDA_COMPUTE_CAP=86`.
Движок: `yttri-tree-forge`, коммиты `073f314a` (трассировка), `dd7f7c0e` (DFS/RoPE/обход ветки), `6ab9a2d2` (перестройка принятого пути). Локальные эквиваленты: `a272a9c5`, `1d962643`, `f9a03235`.

## Условия теста

- `n_ctx=128000`, `n_slots=1`, `n_batch=2048`, `kv_cache_type=q8_f16`, paged int8 KV, `flash_attn=1`, CUDA graphs включены.
- `PREFIX_CACHE_MIB=0` для всех замеров: с включённым prefix cache повторные одинаковые запросы деградировали (55 -> 13 t/s), поэтому кэш отключён.
- `TRACE=0`, `MTP_TIMING=0` для всех замеров.
- Decode: промпт 4 слова (30 prompt-токенов), `max_tokens=128`, `temperature=0`, 3-4 прогона после загрузки модели.
- Prefill: промпт 1500 слов (6412 prompt-токенов), `max_tokens=1`; приведено полное время запроса как прокси prefill (оно включает один decode-шаг ~18-20 мс).
- `VERIFY_ONEPASS=0` — построчная verify-ветка. В ней trie-маска в attention не передаётся, поэтому это контрольный режим «tree-драфт + линейная построчная проверка».
- `VERIFY_ONEPASS=1` — однопроходная FA2-ветка с реальной trie-маской; именно она является целевым tree-verify.

## Что было исправлено по ходу

1. **DFS-порядок узлов дерева.** `FlatTrie::from_edges` теперь перестраивает узлы в DFS-preorder. Только в этом порядке поддерево узла — непрерывный `[start,end]`, как ожидает trie-маска в CUDA. BFS-порядок перемешивал ветки и маска могла разрешать «чужих» соседей.
2. **RoPE-позиция по глубине узла.** В `speculative_verify` строка узла получает позицию `pos + depth(parent)`, а не `pos + линейный_индекс`. Для ветвящегося дерева эти величины не совпадают.
3. **Приём по ветке, а не по линейному zip.** Scheduler теперь идёт от корня по фактическому распределению target: берёт строку первого ребёнка, среди детей ищет выпавший токен и продолжает только эту ветку. Раньше `rows.iter().zip(&draft)` обрывался на первом же sibling.
4. **Перестройка принятого пути в paged pool.** Для tree-режима `speculative_accept` откатывает target к checkpoint и одним causal prefill-проходом перестраивает paged KV/DeltaNet по фактическим принятым токенам, обновляет `kv_len_host` и hidden для MTP commit. Это устранило ошибку `speculative verify: позиция 33 против длины пула 30` и порчу состояния после первого раунда.
5. **`VERIFY_ONEPASS=1` больше не виснет** на исправленном дереве: ONEPASS tree-verify проходит, trie-маска реально используется в FA2.

## Root cause: почему tree всё равно медленный

- **MTP-драфт не tree-aware.** `draft_tree` вызывает `forward_node` последовательно для каждого узла через один MTP KV/state. Узлы соседних веток загрязняют состояние друг друга. Linear W1 с той же головой даёт acceptance 70-87%, а tree — 2-8%. Значит, проблема не в голове, а в способе построения дерева: одному узлу нужен state своего родителя, а не state предыдущего узла линейного обхода.
- **Целевой DeltaNet не tree-aware.** Даже с исправленной trie-маской target-проверка обрабатывает строки дерева последовательно через общий recurrent state. Off-path строки влияют на последующие ветки. Перестройка принятого пути сохраняет корректное состояние *после* раунда, но не делает корректными logits всех веток *внутри* раунда.
- **Стоимость раунда.** Tree K=8: draft ~29 мс, verify ~85-114 мс, accept/rebuild ~22 мс, итого ~137-147 мс на раунд. При фактическом acceptance ~1-2 токена за раунд это 70-130 мс/токен против ~18.5 мс/токен у baseline. Даже при идеальном приёме 8/8 раунд дал бы ~17 мс/токен, то есть примерно уровень baseline, без запаса на ускорение.
- **Linear MTP тоже не выигрывает.** При acceptance 70-87% он даёт 41.5-45.8 t/s против 53.5-54.4 t/s у baseline: стоимость draft+verify больше, чем экономит один-два принятых токена. Это согласуется с отчётом [2026-10-09-qwen35-mtp-linear-vs-baseline.md](2026-10-09-qwen35-mtp-linear-vs-baseline.md).

## Вывод

Tree speculative decoding на Qwen3.5-9B в текущей архитектуре не даёт ускорения и не может дать его только за счёт trie-маски. Маска, DFS, RoPE и приём ветки теперь корректны, ONEPASS не виснет, но качество tree-драфта убивается общим MTP-состоянием, а verify — общим DeltaNet-состоянием. Полученный результат — отрицательный и воспроизводимый: tree ~7.2-7.5 t/s, linear MTP ~41-46 t/s, baseline ~53-54 t/s.

Чтобы tree-подход стал конкурентоспособным, нужны минимум две крупные вещи:

1. **Per-node MTP state/KV для драфта.** Каждый узел дерева должен считать MTP-голову от состояния своего родителя, а не от предыдущего линейного узла.
2. **Per-node DeltaNet state для target-verify** либо отказ от ветвящейся проверки recurrent-слоёв в пользу другой схемы (например, отдельного draft-модели/self-speculation). Без этого logits веток внутри раунда некорректны.

Дополнительно: один батчевый проход MTP-драфта на уровень дерева (вместо последовательных `forward_node` с D2H), отказ от полного accept-rebuild в пользу tree-aware состояния и CUDA-тест trie-маски против построчного эталона.

## Ограничения

- Замеры сделаны на одной RTX 3060 12 GB и одной MTP-голове Ornith-1.5-9B; на другой голове/модели acceptance может отличаться.
- `MTP_VOCAB_TOP=32768`, sampling temperature 0; при другой температуре acceptance может измениться.
- Prefill-оценка включает один decode-шаг и не отделяет MTP catch-up от prefill.
- Prefix cache отключён: с ним повторные одинаковые запросы деградировали, и это отдельный баг/эффект стенда, который не исследовался в этом отчёте.
