## 1. Что было сделано

Прошлый отчёт заканчивался двумя выводами: у V4.1 нет ветки в
`family_banked_engine_continuous_generate`, и банки не дают прироста.

**`ds4_ds41_batch.inc`** (новый файл):

- `ds4_v41_bank` — `ds4_v41_state` + своя host-история токенов;
- `ds4_v41_batch_runtime` — `max_seq` банков, батч-состояние `mb`;
- `v41_batch_bank_prefill` / `_decode` — чанк и один шаг на банке;
- `v41_batch_bank_read_logits` / `v41_batch_bank_logits` — строка логитов
  на хост (тензор непрозрачен вне CUDA-TU, читается через
  `ds4_gpu_tensor_read`);
- `v41_batch_decode_multi` — шаг, где строки принадлежат разным банкам;
- `v41_batch_quote_bytes` — цена банка для цитаты памяти.

## 1a. Как устроен батч по банкам

Замер `cost(n) = 26.4 + 9.33·n` мс показал, что фиксированные 26.4 мс —
это чтение весов, и они делятся на все строки одного прохода. Значит
строки разных банков должны идти одним forward.

Оказалось, что внутри слоя **per-bank только KV**: кольцо окна
(`win[il]`), плоскости компрессора (`comp_kv`, `index_k`) и pending-буферы
(`cpre_*`). Всё остальное — hc-микс, q/kv-проекции, выходная проекция,
MoE и head — уже принимает `n` строк и работает построчно.

Поэтому правка обошлась без CUDA:

1. `ds4_v41_state` получил хук `mb_kv`; `v41_attention` при нём делится на
   `v41_attn_in` (батч) + KV-шаг (per-bank) + `v41_attn_out` (батч).
2. Батч-состояние `mb` держит `max_seq` строк — по одной на банк, и
   освобождает свои KV-плоскости сразу после создания (иначе ~19 МБ на
   слой).
3. `v41_batch_kv` для каждой строки подменяет у состояния банка входы
   (`xn`, `qrn`, `kvn`, `q`, `o`, `pos`) срезами строк батча, выставляет
   `n = 1` и `pos0` строки, вызывает штатный `v41_attn_cache`, затем
   возвращает указатели.
4. `family_banked_decode` зовёт `v41_batch_decode_multi` вместо цикла по
   банкам.

Ключевое: арифметика per-bank шага — это в точности одиночный декод
(`n = 1`), поэтому батч не меняет числа. Меняется только то, сколько раз
читаются веса.

Lossless: текст одиночного запроса байт-в-байт равен строке 0

## 1c. Почему 4 банка всё равно не влезают

Цена банка почти не зависит от контекста: 1.56 GiB при 128K и
1.50 GiB при 64K. Доминирует не KV, а prefill-буфер на 2048 строк
(~651 МБ) плюс плотные строки. Урезание контекста вчетверо экономит
60 МБ из 1560 — то есть 4 банка требуют отдельной правки: уменьшать
`DS4_V41_BATCH_CHUNK` (это цена prefill, а не декода), либо разделять
буферы между банками.

## 2. Три ошибки по пути

Каждая видна в логе:

| Симптом | Причина |
|---|---|
| пустой ответ, `served=0` | V4.1 не было в диспетчере continuous-цикла: запрос уходил в общий V4-путь, где такого рантайма нет |
| `engram layer L1 has no row feed` | банкам не дан per-bank engram-провайдер |
| `head needs 8 logits rows, buffer has 1` | банк аллоцировал одну строку логитов, а короткий блок (n ≤ 8) идёт через полный GEMM-head и пишет n строк |

## 3. Lossless

Банковый вывод сравнивался с serial-путём при одинаковом режиме engram:

```
diff banked_noengram.txt serial_noengram_400.txt  ->  идентичны
```

После перехода на батч проверка повторена: текст одиночного запроса
байт-в-байт равен строке 0 двухзапросного запуска, обе строки
двухзапросного идентичны. Это ожидаемо: per-bank шаг батча — тот же
`v41_attn_cache` с `n = 1`, а плотная часть всегда была построчной.

Единственное расхождение — с serial-путём **с** engram: банки идут без
него, потому что провайдер строк (`V41Feed` в Rust) держит одну историю
на процесс, а банку нужна своя. В банковом режиме это другая, более
слабая модель: serial с engram даёт 34.8 против 29.0 без него.

## 4. Сколько банков влезает

Цитата памяти честная:

```
quote: shared=105.76G per_bank=1.56G banks=2 floor=3.00G
       total=111.86G available=112.14G
```

| Контекст | Цена банка | 4 банка + веса + floor | Вердикт |
|---:|---:|---:|---|
| 128K | 1.56 GiB | 115.0 GiB | не влезает (доступно ~112) |
| 64K | 1.50 GiB | 114.8 GiB | **измерено, тоже не влезает** |
| 128K | — | 2 банка = 111.9 | влезает |

Контекст почти не влияет на цену банка: 1.56 → 1.50 GiB при
уменьшении вчетверо. Доминирует prefill-буфер на 2048 строк (~651 МБ);
KV при 128K — только ~200 МБ. Значит для четырёх банков нужно уменьшать
`DS4_V41_BATCH_CHUNK` (это цена prefill, а не декода) или делить буферы
между банками.

`available` здесь — не `MemTotal`, а живой лимит после загрузки весов:
модель резидентна в unified memory, `MemAvailable` падает до ~3 ГиБ,
поэтому цитата считает от `live + mapped`.

## 5. Что осталось

1. **Engram в банках.** Нужен `V41Feed` на банк (сейчас `FeedCore.hist`
   один на процесс). Вернёт качество и, судя по 29.0 → 34.8, скорость.
2. **Спекуляция в банках.** Драфтер однопользовательский. Батч уже
   доказал, что несколько строк в одном проходе работают; осталось
   добавить драфтер на банк.
3. **4 банка** — уменьшить prefill-буфер или разделить его между
   банками.

## 6. Рабочая конфигурация

Банки включаются явно и по умолчанию выключены:

```bash
DS41_BANKS=1 DS41_CTX_CAP=131072 \
  ./ds4-server --cuda -m DeepSeek-V4.1-Flash-vq8sh14-q4k-mtpnative.gguf \
  --engram-dir deepseek-engram --max-seqs 2 ...
```

Продакшен-конфиг для одиночного пользователя не менялся:
`--max-seqs 1 --mtp-mode on`, 40–51 tok/s на реальном контенте.

Для двух одновременных пользователей: **44.6 tok/s aggregate** (по
23 tok/s каждому) против 27.0 (по 13.8) до батча. Цена — банки идут без
engram, то есть без части качества и без спекуляции.

## 7. Клиенты: pi и Open WebUI

Подключение кодинг-агента pi выявило две вещи, не связанные с банками.

**`--prefix-reuse exact` вместо `off`.** pi отправляет системный промпт
на ~26–27 тыс. токенов в каждом запросе. С выключенным reuse это каждый
раз холодный prefill: 54 с на запрос. С `exact` первый запрос остаётся
холодным, а дальше в логе видно шаги агента:

```
[v41] KV reuse 27444/27530 token, prefill suffix 86
[v41] KV reuse 27530/27701 token, prefill suffix 171
[v41] KV reuse 27701/27771 token, prefill suffix 70
```

То есть пересчитываются только дописанные токены.

**Полный prefix hit при сэмплировании.** Патч `ds4_ds41_kvreuse.inc`
(коммит 809aee09 на сервере). Восстановление отказывалось от полного
хита, если включено device-сэмплирование: сэмплер читает `pos[row]`
(из него сеется Gumbel), а восстановление кладёт строку логитов в row 0,
оставляя позицию неинициализированной. Отказ означал полный prefill —
49 с на вызов. Теперь `pos[0] = np-1`, ровно то, что оставляет холодный
prefill. Проверено: при `temperature 0` вывод байт-в-байт, при
`temperature 0.8, seed 42` — тоже байт-в-байт, 0.74 с на повторный
запрос.

Частичный хит при сэмплировании даёт FP-уровневое расхождение с
холодным путём: суффикс префиллится с другой границы чанка. Это тот же
класс отличия, что и смена `--v41-chunk`, и он не копится в состоянии —
холодный и полный пути совпадают точно.

Итог для pi: первый запрос в новой сессии ~50 с (холодный prefill
27 тыс. токенов), дальше 5 с; правка файла в две реплики — около 1 мин
вместе с вызовом инструмента.

## 8. «Мусор» на длинном контексте — это сэмплирование

Симптом: агентская сессия на ~74 тыс. токенов начала выдавать
бессвязный текст с вкраплениями китайских, тайских и арабских символов
внутри `thinking`. Выглядело как распад модели на длинном контексте.

Это не контекст. Воспроизведено на промпте 73 тыс. токенов и ответе
2500 токенов, считал долю иероглифов по третям ответа:

| temperature | top_p | top_k | Чужие символы по третям |
|---:|---:|---:|---|
| 0.0 | 1.0 | — | 0 / 0 / 0 |
| 0.6 | 0.95 | — | 0 / 0 / 0 |
| 0.7 | 1.0 | — | 0 / 0 / 0 |
| 1.0 | 0.95 | — | 0 / 0 / 0 |
| **1.0** | **1.0** | **0** | **0 / 0 / 2.47 %** |
| 0.6 | 0.95 | 20 | 0 / 0 / 0 |

Механика: первая треть чистая, затем появляются чужие слова
(«Questionемы», «knowм»), и после первого случайного токена в контексте
распад разгоняется. При `top_p 1.0` и `top_k 0` выбор идёт из всех
129 280 токенов; у модели с потерями 1.6 бит/вес хвост распределения не
почти-нулевой, поэтому такие токены реально выпадают. Один выпавший
токен ломает самосогласованность дальше.

Второй эффект, отдельный: `reasoning` съедает весь `max_tokens`. pi с
`--thinking high` потратил 32 768 токенов на рассуждения и вернул
обрезку без ответа за 14 мин 50 с. С `--thinking off` тот же запрос —
400 слов за 46 с, с `--thinking medium` — корректный ответ за 36 с.

Что поправлено: `samplingParams` в `~/.pi/agent/models.json`
(`temperature 0.6, top_p 0.95, top_k 20`) и пресеты Open WebUI в
`/workspace/owui-data/webui.db` (было `top_p 1.0`, стало `0.95, top_k 20`).
