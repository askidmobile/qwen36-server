# V4.1 на DGX Spark: банки сделаны — что они дают и чего не дают

Дата: 2026-10-20. Продолжение
[отчёта о попытке банков](2026-10-20-dgx-spark-deepseek-banks-attempt.md).

## Итог

| Что | Результат |
|---|---|
| Настоящие банки V4.1 | **работают**: N независимых `ds4_v41_state`, 2 банка на 128K |
| Lossless | **да**: вывод байт-в-байт равен serial-пути с тем же режимом engram |
| Aggregate на 2 банках | **не растёт**: 27.0 против 27.1 tok/s |
| Причина | декод упирается в память, а не в латентность; два банка делят ту же полосу |

## 1. Что было сделано

Прошлый отчёт заканчивался тем, что у V4.1 нет ветки в
`family_banked_engine_continuous_generate`, и банки падают в core dump.
Теперь ветка есть.

**`ds4_ds41_batch.inc`** (новый файл, ~280 строк):

- `ds4_v41_bank` — `ds4_v41_state` + своя host-история токенов;
- `ds4_v41_batch_runtime` — `max_seq` банков, общая host-строка logits
  для сэмплера;
- `v41_batch_bank_prefill` / `_decode` — чанк и один шаг на банке;
- `v41_batch_bank_read_logits` / `v41_batch_bank_logits` — строка логитов
  на хост (тензор непрозрачен вне CUDA-TU, читается через
  `ds4_gpu_tensor_read`);
- `v41_batch_quote_bytes` — цена банка для цитаты памяти.

**`ds4.c`** — V4.1 добавлен в диспетчер
`ds4_engine_continuous_generate_impl` и в хелперы `family_banked_prefill_cap`,
`family_banked_logits`, `family_banked_logits_valid`, `family_banked_copy`
(копия банка явно отказывает: форк требует переноса сжатых KV-плоскостей,
а `--prefix-reuse off` на этом lane и так).

**`serving_host.rs`** — главный блокер прошлого раза. Цитата памяти
считала V4.1 за ноль, поэтому после уже состоявшейся аллокации банков
писала `quote_overflow` и отказывала в запуске. Теперь цена приходит из
самого движка (`ds4_bridge_v41_bank_bytes`) и равна тому, что
`v41_state_alloc` реально выделяет.

Три ошибки по пути, каждая видна в логе:

| Симптом | Причина |
|---|---|
| пустой ответ, `served=0` | V4.1 не было в диспетчере continuous-цикла: запрос уходил в общий V4-путь, где такого рантайма нет |
| `engram layer L1 has no row feed` | банкам не дан per-bank engram-провайдер |
| `head needs 8 logits rows, buffer has 1` | банк аллоцировал одну строку логитов, а короткий блок (n ≤ 8) идёт через полный GEMM-head и пишет n строк |

## 2. Замеры

Все замеры: ctx 131072, `temperature 0`, одинаковый промпт, 400 токенов,
один и тот же бинарь.

| Конфигурация | 1 запрос | 2 запроса |
|---|---:|---:|
| Банки (2), engram выкл. | 27.1 aggregate, decode 27.7 | 27.0 aggregate, decode 13.8 каждый |
| Serial, engram выкл., MTP off | 29.0 aggregate, decode 30.5 | — |
| Serial, engram вкл., MTP on | 34.8 aggregate, decode 37.1 | — |

Вывод: **банки не увеличивают суммарную пропускную способность**. Два
запроса обслуживаются одновременно, но каждый идёт вдвое медленнее.
Это не ошибка реализации, а физика: декод V4.1 упирается в полосу
памяти (105.75 GiB весов на токен), и два банка делят её, а не
складывают. Выигрыш банков — в латентности очереди, не в throughput.

Практический смысл всё равно есть: при `--max-seqs 1` второй запрос
ждал 14.8 с первого токена; с двумя банками он получает первый токен
через 0.7 с и видит поток. Aggregate при этом не падает.

## 3. Lossless

Ключевая проверка: банковый вывод сравнивался с serial-путём при
одинаковом режиме engram.

```
diff banked_noengram.txt serial_noengram_400.txt  ->  идентичны
```

То есть банковый lane — не «примерно то же», а тот же самый декод,
просто с другим состоянием. Единственное расхождение — с serial-путём
**с** engram: банки пока идут без него, потому что провайдер строк
engram (`V41Feed` в Rust) держит одну историю на процесс, а банку нужна
своя.

Практическое следствие: в банковом режиме модель считается без engram,
то есть это другая (более слабая) модель. Для сравнения: serial с engram
даёт 34.8 против 29.0 без него — engram не только меняет качество, но и
ускоряет декод на этом артефакте.

## 4. Сколько банков влезает

Цитата памяти теперь честная:

```
quote: shared=105.76G per_bank=1.56G banks=2 floor=3.00G
       total=111.86G available=112.14G
```

| Контекст | Банк | 4 банка + веса + floor | Вердикт |
|---:|---:|---:|---|
| 128K | 1.56 GiB | 115.0 GiB | не влезает (доступно ~112) |
| 128K | — | 2 банка = 111.9 | **влезает** |
| 64K | ~0.9 GiB | ~109 GiB | должно влезть, не проверено |

`available` здесь — не `MemTotal`, а живой лимит после загрузки весов:
модель резидентна в unified memory, и `MemAvailable` падает до ~3 ГиБ,
поэтому цитата считает от `live + mapped`. Отсюда и потолок в два банка
при 128K.

Формула цены банка идёт из движка, так что при смене контекста или
модели цифры пересчитаются сами.

## 5. Что осталось

1. **Engram в банках.** Нужен `V41Feed` на банк (сейчас `FeedCore.hist`
   один на процесс). Без этого банковый режим — другая модель. Это
   следующий по важности шаг: он и качество вернёт, и, судя по разнице
   29.0 → 34.8, скорость.
2. **Спекуляция в банках.** Драфтер однопользовательский, verify-путь
   gated single-seq. В коде движка прямо помечено: «the cont loop's
   multiseq forward has an unfixed race». Без этого банки не догонят
   46 tok/s одиночного пути.
3. **4 банка** — только на меньшем контексте или после того, как
   engram-провайдер перестанет дублировать историю.

## 6. Рабочая конфигурация

Банки включаются явно и по умолчанию выключены:

```bash
DS41_BANKS=1 DS41_CTX_CAP=131072 \
  ./ds4-server --cuda -m DeepSeek-V4.1-Flash-vq8sh14-q4k-mtpnative.gguf \
  --engram-dir deepseek-engram --max-seqs 2 ...
```

Продакшен-конфиг не менялся: `--max-seqs 1 --mtp-mode on`, 40–51 tok/s
на реальном контенте. Банки — для случаев, когда важнее не задерживать
второго пользователя, чем выжать максимум из одного.
