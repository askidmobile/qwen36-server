# Q4_K_M на 128k: честное сравнение yforge и llama.cpp (стенд 2080 Ti)

Дата: 2026-11-01. Стенд `tinycoder.dev`: RTX 2080 Ti 11 ГиБ, **PCIe 3.0 x16**,
2× Xeon E5-2686 v4 (36 ядер / 72 потока), 125 ГиБ RAM.
Модель: `Ornith-1.5-35B-Q4_K_M.gguf` у обоих движков, `ctx=131072`,
`CONTEXT_LIMIT=131072`, temp=0.

## Таблица

| Метрика | llama.cpp (`-ot exps=CPU`, 36 потоков) | yforge (эксперты в RAM через PCIe) | Отношение |
|---|---:|---:|---:|
| Prefill 512 | 214.8 т/с | 196.7 т/с | 0.92× |
| Prefill 4 096 | **440.6** т/с | 280.2 т/с | 0.64× |
| Prefill 16 384 | **604.2** т/с | 322.0 т/с | 0.53× |
| Prefill 32 768 | **683.5** т/с | не снято | — |
| **Декод 128 ток** | **45.75** т/с | 10.3–15.6 т/с | 0.23–0.34× |

Отдельно: новый sm75 prefill-kernel на 131 000 токенах даёт 383.7 т/с
(журнал `2026-10-30-turing-prefill.md`), но при коротких промптах на том же
контексте он проигрывает llama.cpp.

## Почему так — арифметика, а не догадка

Декод 35B-A3B читает **8 активных экспертов × 40 слоёв = 540 МиБ весов на
каждый токен**.

- Чтобы выдать 45 т/с, нужно 540 МиБ × 45 ≈ **24 ГБ/с**.
- PCIe 3.0 x16 физически даёт максимум **15.75 ГБ/с**.
- Значит потолок GPU-пути с экспертами в RAM — около **29 т/с**.
- llama.cpp этих 24 ГБ/с по PCIe не гоняет вообще: он считает экспертов
  на CPU из системной RAM (там полоса ~100+ ГБ/с), а на GPU оставляет
  внимание и плотные слои.

Проверено замерами, а не только расчётом:

- PCIe rx при декоде: **6.2 ГБ/с** (≈78 % теоретического трафика экспертов);
- кэш экспертов в VRAM: hit 93 % запросов, но VRAM покрывает лишь
  **62 из 256 экспертов** на слой (`[moe-audit] table_vram=62 cap=62`);
  кэш 16 МиБ → 10.2 т/с, кэш 4400 МиБ → 15.6 т/с, дальше упирается в VRAM;
- MMA/dp4a-загрузка ядра MoE — 0.04 % пика, то есть ядро ждёт память,
  а не считает;
- `MOE_MMQ_DECODE=1` (тензорные ядра) медленнее MMVQ: 11.35 против 12.9 т/с.

**Вывод: на PCIe 3.0 с Q4 эксперты через GPU ускорить нельзя в принципе.**
Чтобы обогнать llama.cpp на Q4 + 128k/256k, yforge обязан считать
маршрутизируемых экспертов на CPU — так же, как llama.cpp, но с более
быстрым остальным путём (наш prefill-kernel, наши DeltaNet/attention).

## Что нужно сделать, чтобы всё-таки обогнать

Единственный путь: **CPU-путь экспертов в yforge**.
В `moe.rs` уже есть `MoeBackend::Reference` (CPU-исполнение через
`reference_routed_swiglu`), но он требует `ExpertWeights::Packed`
(все эксперты в памяти) и не работает с выгрузкой `Store`.

План:
1. Загружать экспертов как `Packed` на CPU (20.7 ГБ Q4 в 125 ГиБ RAM влезает).
2. Добавить CPU-ядро GEMV для Q4_K (сумма `dp4a` по 36 потокам через rayon).
3. В декоде считать экспертов на CPU параллельно с GPU-путём остальных слоёв.
4. Проверить паритет выдачи и замерить: цель — ≥45 т/с на 128k.

Оценка: 2–3 инженерных дня. Без этого пункта преимущества на Q4 + 128k
не будет ни по prefill на коротких промптах, ни по декоду.

## Почему упёрлись

Замеры с аудитом таблиц (`[moe-audit]`) показали: кэш покрывает 62 из 256
экспертов на слой, hit 92–95 %, то есть PCIe-трафик промахов всего
~30 МиБ/токен. **Значит PCIe уже не узкое место.** Остаются сами ядра MoE:
на слой два запуска по ~0.5 мс, на 40 слоёв ~40 мс из 72 мс на токен.

LLVM/llama.cpp берёт 45.75 т/с потому, что считает экспертов **на CPU из
системной RAM** и не гоняет активации туда-обратно на каждом слое. Наш
CPU-путь выдаёт верный текст, но в 14 раз медленнее: 24 rayon-вызова на
слой (8 экспертов × 3 матрицы) и 80 синхронизаций GPU↔CPU на токен.

## Что нужно, чтобы закрыть цель

1. **Карта с 24+ ГиБ VRAM.** Q4 целиком в VRAM на контексте 128k даёт, по
   замеру IQ2-аналога, 100+ т/с. Это аппаратное решение, не программное.
2. **Недели на полноценную CPU-ветку декода** с асинхронным конвейером и
   батчингом экспертов в один проход (не 24 rayon-вызова на слой).
3. **Зафиксировать текущее преимущество** там, где оно уже есть: prefill на
   очень длинных промптах (383.7 т/с против 222.7 в пересчёте на 128k) и
   работа на коротких контекстах, где Q4 целиком в VRAM.

Ни один из этих вариантов не является настройкой — это либо другое железо,
либо отдельный многодневный проект.

## Решающий замер: сколько реально идёт по PCIe при декоде

Замер строго на декоде (128k-промпт уже в пуле, дальше 200 токенов):

```
decode_tps = 9.73
PCIe rx: avg = 4 131 МБ/с, peak = 7 870 МБ/с
```

Пересчёт: `4131 / 9.73 = 424 МиБ на токен`. Полный объём экспертов одного
токена: 8 активных × 10 MoE-слоёв... фактически 424 / 540 = **78 %**.

## Почему «decode hit 93 %» вводит в заблуждение

hit считается по уникальным экспертам за шаг; распределение скошено, десяток
горячих даёт 93 % запросов. Но покрытие другое:

```
[moe-audit] L0: dir_resident=62 table_host=194 table_vram=62 cap=62
```

62 слота из 256 = 24 %. Арифметика сходится:
`(1 − 0.24) × 540 = 410 МиБ/токен` против измеренных 424.

При идеальном кэше (весь VRAM) покрытие 59 %, трафик 221 МиБ/токен, при
7 ГБ/с это ~31 т/с — всё ещё ниже 45.75. Значит эксперты вообще не должны
ехать по PCIe: их надо считать на CPU, как llama.cpp.

CPU-путь доведён с 3.2 до **9.41 т/с** (два прохода на слой, плоский
parallel, AVX2 в бинарнике — 440 инструкций, 18 физических потоков).
До 45.75 нужны: repack `ggml_gemv_q4_K_8x8_q8_K` и один H2D/D2H на слой.

## Итог: где мы и что мешает (2026-11-01, после серии экспериментов)

### Работает
- **Q4_K_M, ctx 131 072**: пул `window=131072`, VRAM 9.25 ГиБ, выдача корректна.
- **Q4_K_M, ctx 262 144**: пул `window=262144` (5120 МиБ), VRAM 9.24 ГиБ — окно
  полное, контекст разворачивается.
- **sm75 prefill-kernel**: 383.7 т/с на 131k против 41 у старого пути.

### Честный профиль декода (128k)

Добавлен `DEC_TIMING=1` — узкий таймер, не ломающий CUDA-граф:

```
[dec] #160 before_step=0.58ms  graphed=101.52ms
[dec] #192 before_step=0.44ms  graphed=99.93ms
[dec] #224 before_step=0.49ms  graphed=103.59ms
```

| Компонент | мс/токен |
|---|---:|
| `before_step` (кэш экспертов) | 0.5 |
| Граф декода | 100 |
| Реальный токен при 14.5 т/с | 69 |
| llama.cpp на токен | 21.9 |

**Вывод:** `before_step` — 0.7 % времени. Все правки кэша/promotion/staging
били в 0.5 мс из 100 и поэтому не давали результата.

### Что реально влияет (измерено A/B)

| Конфигурация | Декод, т/с |
|---|---:|
| `EXPERT_CACHE_MIB=16` (0 % экспертов в VRAM) | 9.79–10.19 |
| `EXPERT_CACHE_MIB=4400` (23 %, аудит 60/256) | **14.44–14.57** |
| `EXPERT_CACHE_MIB=4530` (fail-closed) | не стартует |

Прирост +43 % от кэша есть, но покрытие упирается в 11 ГиБ VRAM:
18.6 ГиБ экспертов физически не влезают.

### Измеренный PCIe-трафик декода

```
decode = 9.73 т/с; PCIe rx avg = 4 131 МиБ/с, peak = 7 870 МиБ/с
→ 424 МиБ на токен при hit 93 %
```

`(1 − 0.23) × 540 = 416 МиБ` — сходится с измерением. «Hit 93 %» считается по
уникальным экспертам за шаг на скошенном распределении; покрытие — 23 %.
