# План: переиспользование распакованного блока в mmvq при b=2..4

**Спека:** [2026-08-29-mmvq-batch-reuse.md](2026-08-29-mmvq-batch-reuse.md)
**Дата:** 2026-08-29

## Форма плана

План устроен вокруг ворот. Фаза 0 стоит один день и может закрыть всю работу;
фазы 1-3 начинаются только после её числа. Это прямое следствие прожарки:
премиса про повторную распаковку не доказана, а оценка приза (+2.3% на Ornith)
не оправдывает дней работы вслепую.

---

## Фаза 0 — ворота: есть ли резерв (P0, ~1 день)

Цель: получить одно число — сколько миллисекунд на строку снимает вынесение
распаковки у Q4_K. Всё остальное зависит от него.

### 0.1. Микробенчмарк ядра вне сервера

**Где:** новый `engine/candle-core/examples/mmvq_bench.rs` (пример, не тест —
нужен реальный GPU и ручной запуск).

**Что делает:**
- строит `QTensor` формы `[248320, 4096]` в Q4_K из случайных данных (форма
  головы Ornith, самый крупный матвек в шаге);
- вызывает `mul_mat_vec_via_q8_1` при `b_size` = 1, 2, 3, 4;
- каждый размер: 20 прогревочных запусков, затем 200 замеряемых, время по
  `cuda_stream().synchronize()` вокруг группы;
- печатает мс на запуск и прирост на строку.

**Проверка:** отклонение между тремя повторами всего бенчмарка меньше 5%.
Если больше — поднять число запусков, пока не сойдётся; на шумном замере
ворота не работают.

### 0.2. Ручное вынесение для Q4_K

**Где:** `engine/candle-kernels/src/quantized.cu:4404`, копия `mul_mat_vec_q`
под именем `mul_mat_vec_q_hoisted`, инстанцируется только для Q4_K и `ncols_y=2`.
Внимание: `mmvq_gguf.cu` — мёртвый код, он исключён из сборки, править его
бесполезно.

**Что делает:** внутри итерации по `kbx` один раз читает и распаковывает блок
в регистры, затем в цикле по `j` считает только скалярное произведение с
активацией. Это черновик для замера, не продакшен: корректность проверяется,
но код не обязан быть красивым и покрывать все типы.

**Проверка:** выход совпадает с прежним ядром на случайных входах побитово. Если
не совпадает — значит порядок накопления изменился; зафиксировать это, замер
всё равно годен, но в фазе 2 побитовость требовать нельзя.

### 0.3. Развилка

Сравнить прирост на строку до и после.

| Что вышло | Решение |
|---|---|
| Меньше 0.3 мс на строку | **Стоп.** Компилятор уже выносил распаковку. Работа закрывается, в спеку пишется результат. Стоимость выяснения — один день |
| 0.3-1.5 мс на строку | Приз соответствует оценке: Ornith +2.3%, 4B выходит в паритет. **Решение пользователя**, продолжать ли ради Q2_K/IQ2, где распаковка дороже |
| Больше 1.5 мс на строку | Допущение про «неустранимые 3.68 мс у Q8_0» неверно, приз кратно больше оценки. Идём в фазу 1 без дополнительных вопросов |

**Артефакт фазы:** абзац в спеке с числами и выбранной веткой. Без него фаза 1
не начинается.

## Фаза 1 — ядро для Q4_K и Q6_K (P1, ~2-3 дня, только после ворот)

### 1.1. Разделить вычисление на распаковку и произведение

**Где:** `quantized.cu`, функции `vec_dot_q4_K_q8_1` и `vec_dot_q6_K_q8_1`.

Разбить каждую на пару: `unpack_<тип>(vx, kbx, kqs) -> регистры` и
`dot_<тип>(регистры, y) -> float`. Прежние функции остаются как обёртка
`dot(unpack(...))`, чтобы путь `ncols_dst=1` не менялся вовсе.

**Проверка:** обёртка даёт побитово прежний результат; ядро для `ncols_dst=1`
не изменилось ни на инструкцию (сравнить PTX-текст функции до и после).

### 1.2. Поднять распаковку в `mul_mat_vec_q`

Для `ncols_dst >= 2` вызывать `unpack` один раз перед циклом по `j`, внутри —
только `dot`. Для `ncols_dst == 1` оставить прежний путь.

**Проверка:**
- побитовое совпадение с прежним ядром на случайных входах для обоих типов,
  если фаза 0.2 показала, что порядок накопления сохраняется; иначе — расхождение
  не больше 1e-6 по максимуму модуля;
- занятость ядра (`--ptxas-options=-v`) не упала настолько, чтобы `ncols_dst=1`
  замедлился: замер из 0.1 повторяется, регресс больше 1% — откат.

### 1.3. Замер на моделях

**Что:** штатная обвязка, `QWEN36_MTP_TIMING=1`, по три повтора на конфигурацию.

Опорные числа снять заново на текущей сборке перед правкой — прежние получены
в разных прогонах, и разброс на стенде доходит до 9%. Сравнивать только пары
«до/после», снятые подряд.

| Модель | Метрика | Сейчас | Цель |
|---|---|---|---|
| 4B UD-Q4_K_XL | `verify(2)` | 18.94 мс | ≤ 18.1 |
| 4B UD-Q4_K_XL | ток/с с MTP+шортлист | 67.5 | ≥ 70.5 (паритет с базой) |
| Ornith 9B Q6_K | `verify(2)` | 30.6 мс | ≤ 30.1 |
| Ornith 9B Q6_K | ток/с с MTP+шортлист | 43.7 | ≥ 44.5 |
| обе | `E[m]` | 1.671 / 1.670 | без изменений ±0.02 |
| обе | обычный декод (MTP=0) | 70.5 / 39.3 | не хуже 1% |

**Проверка качества:** десять задач с проверяемым ответом (набор из
`docs/plans/2026-08-24-qwen35-4b-benchmark.md`) решаются так же. Побитовое
совпадение вывода модели **не требуется** — при изменении порядка накопления
расхождение на почти-ничьих неизбежно и дефектом не является.

## Фаза 2 — порог векторного пути (P2, ~0.5 дня)

**Где:** `engine/candle-core/src/quantized/cuda.rs:1466`, константа `8`.

Расширить пример из 0.1: замерить оба пути (`dequantize_matmul_vec` и
`dequantize_matmul`) при `b*m` = 2, 4, 8, 12, 16 для Q4_K и Q6_K.

**Проверка:** таблица «путь × b*m → мс» получена; константа либо подтверждена
замером и в комментарии рядом появляется ссылка на него, либо изменена вместе с
замером. Формулировка «подтверждена или изменена» без таблицы не принимается.

## Фаза 3 — гигиена трассировки (P2, ~0.5 дня)

**Где:** `quantized/cuda.rs:1426,1438` и оба модуля-заглушки.

Удалить `fast_mmvq.rs`, `fast_mmq.rs` и их вызовы; печать `QWEN36_TRACE_MMQ`
переписать так, чтобы она называла **выбранный** путь (`vec` / `matmul` / `mma`),
а не факт отказа несуществующего быстрого пути.

**Проверка:** на запросе из 40 токенов печатается распределение по путям, сумма
совпадает с числом вызовов матмула; замеры фазы 1.3 не изменились.

**Почему это в плане, хотя выигрыша нет:** при подготовке спеки я прочитал 453
строки `mmq-entry` как «быстрый путь промахнулся» и построил на этом вывод.
Строки печатаются на каждом вызове. Ловушка стоит в коде и ждёт следующего.

## Порядок и распределение

```
Фаза 0 (ворота) ──> развилка ──> Фаза 1 ──> Фаза 2
                       │                      │
                       └── стоп               └── Фаза 3 (независима)
```

- **Фаза 0.1, 1.3, 2** — эта сессия: замеры, обвязка и стенд готовы.
- **Фаза 0.2, 1.1, 1.2** — партнёр: ядра CUDA его область.
- **Фаза 3** — любой.

Фаза 3 не зависит от ворот и может идти параллельно.

## Чего в плане нет

- Q2_K и IQ2 (целевая 27B по BD-003) — переносим приём туда после фазы 1, когда
  будет известен настоящий приз. Модели на стенде нет, замер до/после негде снять.
- MoE-ядра (`moe/gguf.cuh`) — своя развилка и свои типы.
- Префил и кеш префикса — отдельный фронт, и для агентской нагрузки более
  крупный: при промпте 80K и ответе 400 токенов префил это больше половины
  времени запроса, и ядро проверки его не трогает.

## Что откатывать, если пошло не так

Каждая фаза — отдельный коммит. Фаза 1 трогает только `quantized.cu`; откат —
`git revert` одного коммита, пересборка ядер 10-25 секунд (заголовки flash-attn
не затрагиваются, длинной пересборки не будет).
