# Спецификация: переиспользование распакованного блока в mmvq при b=2..4

**Дата:** 2026-08-29
**Приоритет:** P1
**Тип:** Оптимизация (ядро CUDA)

## 1. Проблема

Ядро квантованного матвека распаковывает блок весов заново на каждую строку
пакета. В `engine/candle-kernels/src/quantized.cu:4434-4441` (шаблон `mul_mat_vec_q`,
строка 4404) вызов `vec_dot_q_cuda` стоит внутри цикла по строкам:

```cpp
for (int j = 0; j < ncols_y; ++j)            // строки пакета
  for (int i = 0; i < rows_per_cuda_block; ++i)
    tmp[j][i] += vec_dot_q_cuda(&x[kbx + (row0+i)*blocks_per_row_x],
                                &y[j*blocks_per_col_y + kby], kqs);
```

Адрес блока весов `&x[kbx + (row0+i)*blocks_per_row_x]` от `j` не зависит —
меняется только активация. По исходнику это выглядит как повторная распаковка одного и того же
блока `ncols_dst` раз.

**Премиса подтверждена замером 2026-08-29** (фаза 0 плана, микробенчмарк на
матрице `[248320, 4096]` в Q4_K, 20 прогревочных и 200 замеряемых запусков, по
три повтора):

| | пакет 1 | пакет 2 | лишняя строка |
|---|---|---|---|
| текущее ядро | 1.684 / 1.699 мс | 1.950 / 1.922 | **+0.266 / +0.223** |
| распаковка вынесена | 1.684 | 1.742 / 1.754 | **+0.058 / +0.070** |

Стоимость лишней строки падает **вчетверо**, с ~0.245 до ~0.064 мс, при
побитово совпадающем выходе (`max_abs_diff = 0`). Пакеты 1, 3 и 4 между
прогонами не изменились (вынесенный вариант инстанцирован только для пакета 2) —
это контроль, что эффект не артефакт замера. Компилятор распаковку НЕ выносил.

**Фаза 1 (2026-08-29): выигрыш только у Q4_K, у Q6_K регресс.**

Вынесение распространено на пакеты 2..8 и на Q6_K, замер на свободном стенде,
по два-три повтора (побитово `max_abs_diff = 0` везде, пакет 1 не тронут):

| пакет | Q4_K база | Q4_K вынесено | | Q6_K база | Q6_K вынесено | |
|---|---|---|---|---|---|---|
| 1 | 1.684 | 1.684 | — | 2.659 | 2.666 | — |
| 2 | 1.918 | 1.755 | **−8.5%** | 2.839 | 3.354 | **+18%** |
| 3 | 2.540 | 2.279 | **−10.3%** | 3.089 | 3.347 | **+8%** |
| 4 | 3.117 | 2.589 | **−17%** | 3.443 | 3.457 | 0 |

Причина регресса у Q6_K — почти наверняка регистровое давление: распакованный
блок там крупнее (`vl`, `vh`, `scales`, `d` против `v[2]`, `aux[2]`, `dm` у
Q4_K), занятость падает и съедает выигрыш от переиспользования.

**Следствие, важное для продукта: Ornith 9B работает в Q6_K.** То есть в
нынешнем виде правка ухудшила бы именно рабочую модель. Q6_K обязан остаться на
прежнем пути; включать вынесение можно только для Q4_K, пока для Q6_K не найден
вариант с меньшим числом регистров.

**Замер на моделях (2026-08-29): выигрыш ядра на модели не виден. Работа
закрывается.**

4B Q4_K, MTP с шортлистом, по три повтора, новое ядро против старого на одной
сборке (`QWEN36_MMVQ_HOISTED=0` возвращает прежний путь):

| | ток/с | verify(2) |
|---|---|---|
| новое ядро | 67.0 | 18.89 мс |
| прежнее ядро | 66.0 | 18.93 мс |

**Verify упал на 0.04 мс, то есть на 0.2%.** Ornith 9B (Q6_K, прежний путь по
умолчанию) не изменился: 43.0 / 42.8 ток/с.

Почему выигрыш ядра не дошёл до модели:
- микробенчмарк мерил одну матрицу 4096×248320 — самый крупный матвек в шаге;
- в самом шаге 58-62% занимает DeltaNet, который через mmvq не проходит вовсе;
- голова 4B это 2560×248320, в 1.6 раза меньше замеренной;
- −8.5% от головы даёт ≈0.16 мс из 18.9, то есть 0.85% по арифметике и 0.2% по
  замеру.

Итог: **ядро ускоряется на 8-17%, модель — на доли процента.** Приз, ради
которого писалась спека, на уровне продукта отсутствует. 266 строк
дублированного ядра ради этого не окупаются, и правка не вливается.

**Развёртка по формам и Q2_K (2026-08-29): вопрос закрыт окончательно.**

Пакет 2, режимы «прежний путь» и «вынесенный», по два валидных повтора,
побитовость подтверждена во всех комбинациях:

| форма | Q4_K база | Q4_K вынесено | выигрыш |
|---|---|---|---|
| 248320×4096 — голова 9B | 1.928 | 1.746 | 9.4% |
| 248320×2560 — голова 4B | 1.485 | 1.281 | 13.7% |
| 4096×4096 — проекция 9B | 0.0385 | 0.0360 | 6.5% |
| 2560×2560 — проекция 4B | 0.0225 | 0.0215 | 4.4% |
| 11008×4096 — MLP | 0.0900 | 0.0840 | 6.7% |

| форма | Q2_K база | Q2_K вынесено | |
|---|---|---|---|
| 248320×5120 — голова 27B | 2.272 | 2.269 | 0.1% |
| 5120×5120 — проекция 27B | 0.0530 | 0.0570 | **−7.5%** |

Два вывода.

Первый: у Q4_K выигрыш есть на всех формах, но проекции слоёв в 40-80 раз
дешевле головы (0.02-0.09 мс против 1.5-1.9), поэтому проценты с них ничего не
весят. Арифметика по этим числам даёт около 2% на шаге проверки, замер на
модели — 0.2%. Разрыв означает, что часть проекций в реальном шаге через mmvq
не проходит вовсе.

Второй, решающий: **у Q2_K — кванта целевой 27B по BD-003 — выигрыша нет**
(0.1% на голове) **и есть регресс на проекциях** (−7.5%). То есть на модели,
ради которой затевался проект, приём не работает.

Итог по трём квантам: Q4_K — выигрыш ядра без выигрыша модели, Q6_K (Ornith) —
регресс, Q2_K (целевая 27B) — регресс. **Тема закрыта.** Код остаётся в
отдельном дереве `git worktree`, побитово корректен; поднять его — минуты,
если появится причина.

Регресс Q6_K (пакет 2 хуже на 18%) остался без объяснения: число регистров у
всех четырёх ядер одинаково (56, spill 0), версия про регистровое давление не
подтвердилась.

Ниже — исходное рассуждение до замера, оно осталось верным по направлению, но
переоценивало приз на уровне модели.

**Премиса до замера считалась недоказанной, и это был главный риск спеки.** `ncols_dst` — константа
времени компиляции, оба цикла помечены `#pragma unroll`, загрузки при разных
`j` идентичны по адресу: компилятор мог вынести их сам. Попытка проверить по
PTX не разрешила вопрос — варианты ядра различаются не только числом строк:
`rows_per_cuda_block = ncols_y == 1 ? 1 : 2` и `nwarps = ncols_y <= 4 ? 4 : 2`,
то есть при пакете 2 блок считает вдвое больше строк матрицы. Поэтому счётчики
обращений между вариантами несопоставимы (у Q4_K 14 против 30 при переходе 1→2,
у Q6_K 33 против 22 — меньше). Ядро специализировано под размер пакета.

Косвенный довод в пользу премисы — замер на одной модели (Qwen3.5-4B из MTP-репозитория unsloth) в трёх квантах,
ширина 2, по три повтора:

| квант | база мс/ток | verify(2) | отношение | прирост 2-й строки |
|---|---|---|---|---|
| UD-Q4_K_XL | 14.2 | 18.94 | 1.33 | **4.74** |
| Q6_K | 16.5 | 20.92 | 1.27 | **4.42** |
| Q8_0 | 18.4 | 22.08 | 1.20 | **3.68** |

Прирост падает по мере упрощения распаковки, хотя байт весов растёт. Для
простого чтения весов ожидалось бы обратное, и это единственный довод в пользу
того, что распаковка выполняется повторно. Довод косвенный: разница 4.74 против
3.68 составляет 22%, а разброс между повторами на стенде доходит до 9%, так что
на одном измерении вывод не построить.

Развёртка по k линейна (4.74 / 4.64 / 5.34 при k=2/3/4), скачка на первой
лишней строке нет — построчные накладные планировщика исключены надёжно.

Отдельно неизвестно, сколько из прироста неустранимо. Оценка приза ниже
опирается на допущение, что 3.68 мс у Q8_0 — это чистая арифметика лишнего
скалярного произведения. Допущение не проверено: если и там время уходит на
повторное чтение блока, приз кратно больше.

Следствие для продукта: MTP выигрывает на Ornith 9B (Q6_K) и **проигрывает на
4B (Q4_K)** — 67.5 против 70.5 ток/с. Чем дешевле квант, тем дороже обходится
проверка.

## 2. Цель

Распаковывать блок весов один раз на группу строк и переиспользовать для всех
`ncols_dst` активаций. Ожидаемый эффект — снижение стоимости лишней строки
проверки, а значит рост скорости при MTP на всех квантах, где распаковка
нетривиальна.

## 3. Текущее состояние

- `engine/candle-kernels/src/quantized.cu:4404` — шаблон `mul_mat_vec_q`,
  инстанцируется в `mul_mat_vec_q<тип>_q8_1_cuda1..8` для 10 типов квантов.
  **Это и есть работающее ядро.**
- `engine/candle-kernels/src/mmvq_gguf.cu` — похожий шаблон `mmvq_core_impl`,
  но файл исключён из сборки (`candle-kernels/build.rs:37`) и никуда не
  включается: **мёртвый код**. Первая редакция этой спеки разбирала именно его —
  ошибка найдена при делегировании задачи внешнему агенту.
- `engine/candle-core/src/quantized/cuda.rs:1466-1477` — развилка: при
  `b*m ≤ 8` идёт `dequantize_matmul_vec` (векторный путь), иначе
  `dequantize_matmul`. Порог `8` задан константой.
- `engine/candle-core/src/quantized/cuda.rs:682` — `mul_mat_vec_via_q8_1`,
  квантует активации в Q8_1 и запускает ядро; поддерживает `b_size` 1..8.
- `engine/candle-core/src/quantized/fast_mmvq.rs` и `fast_mmq.rs` — заглушки по
  14 строк, всегда возвращают `Ok(None)`. В оригинальном candle на их месте
  полноценные реализации (323 и 400 строк), но они зовут FFI-лаунчеры
  `launch_mmq_gguf_*` из статической библиотеки, а наш форк перешёл на
  **динамическую загрузку PTX**: `ffi.rs` пуст по этой самой причине, а
  `candle-kernels/build.rs:37` исключает `mmvq_gguf.cu` и `mmq_*.cu` из
  статической сборки. То есть заглушки — рудимент другого способа сборки, а не
  потерянная оптимизация: их работу делает PTX-путь.
- Трассировка `QWEN36_TRACE_MMQ=1` вводит в заблуждение: `mmq-entry` и
  `mmq-fallback` печатаются на КАЖДОМ вызове, потому что заглушки всегда
  возвращают `None`, а настоящая работа идёт после них. Наблюдённые 453 и 245
  строк — это счётчик вызовов, а не признак промаха.
- Замерная обвязка готова: `QWEN36_MTP_TIMING=1` даёт `verify=` и `E[m]` по
  раундам, `QWEN36_TRACE_MMQ=1` — выбранный путь, скрипты прогонов на стенде.

## 4. Сценарии

### Сценарий 1: ворота — доказать, что резерв вообще есть (P0)

> Это не подготовка к работе, а решение, делать ли её. Сценарии 2-4 не
> начинаются, пока сценарий 1 не дал число.

**Как** разработчик, **я хочу** знать, сколько на самом деле даёт
переиспользование блока, **чтобы** не потратить дни на выигрыш в проценты.

**Шаги:**
1. Микробенчмарк ядра вне сервера: одна матрица `[248320×4096]` в Q4_K,
   `ncols_dst` = 1 и 2, замер по CUDA-событиям.
2. Вручную вынести чтение и распаковку блока из цикла по `j` для Q4_K.
3. Сравнить время при `ncols_dst=2` до и после.

**Критерии приёмки:**
- [ ] Известно время ядра при `ncols_dst` = 1 и 2 до правки, отклонение между
      повторами меньше 5%.
- [ ] Известна та же пара после ручного выноса распаковки.
- [ ] Записано, какая часть прироста второй строки снимается: приз в
      миллисекундах на строку и в процентах от `verify(2)`.

**Развилка после сценария 1.** Оценка по замерам сервера даёт приз около
1.1 мс на строку у Q4_K и 0.7 мс у Q6_K — это разница между приростом второй
строки у Q4_K/Q6_K и у Q8_0, где распаковки почти нет. При таком призе
ожидается: Ornith 9B 43.7 → ~44.7 ток/с (+2.3%), 4B Q4_K 67.5 → ~70.9, то есть
выход в паритет с базой, но не выше. **Если микробенчмарк подтвердит только
эти числа — работу дальше сценария 2 не продолжать без отдельного решения.**
Если же вынесение снимает и само чтение весов (а не только распаковку), приз
может оказаться ближе к полным 4.7 мс, и тогда экономика меняется полностью.

### Сценарий 2: ядро для Q4_K и Q6_K (P1)

**Как** пользователь стенда, **я хочу** чтобы спекуляция не проигрывала базе на
Q4_K, **чтобы** MTP можно было держать включённым на любой модели.

**Шаги:**
1. Разделить `vec_dot_q_cuda` для Q4_K и Q6_K на две части: распаковка блока в
   регистры и скалярное произведение с активацией.
2. В `mmvq_core_impl` поднять распаковку выше цикла по `j`.
3. Сохранить путь для `ncols_dst=1` без изменений либо убедиться, что он не
   деградировал.

**Критерии приёмки:**
- [ ] Побитовое совпадение выхода с прежним ядром на случайных входах для обоих
      типов (допуск 0, тип накопления не меняется).
- [ ] `verify(2)` на 4B Q4_K падает не меньше чем на 0.8 мс от 18.94.
- [ ] `verify(2)` на Ornith 9B Q6_K падает не меньше чем на 0.5 мс от 30.6.
- [ ] Скорость при `ncols_dst=1` (обычный декод) не ухудшилась больше чем на 1%.
- [ ] `E[m]` не изменилось: 1.671 ± 0.02 на 4B, 1.670 ± 0.02 на Ornith.

### Сценарий 3: порог между векторным и матричным путём (P2)

**Как** разработчик, **я хочу** знать, где после починки проходит граница
`b*m ≤ 8`, **чтобы** ядро выбиралось по замеру, а не по унаследованной константе.

**Шаги:**
1. Замерить `dequantize_matmul_vec` и `dequantize_matmul` на одних входах при
   `b*m` = 2, 4, 8, 16.
2. Если оптимум сместился — заменить константу и записать замер в решение.

**Критерии приёмки:**
- [ ] Есть таблица «путь × b*m → мс» для Q4_K и Q6_K.
- [ ] Константа порога либо подтверждена замером, либо изменена вместе с ним.

### Сценарий 4: заглушки fast_mmvq и fast_mmq (P2)

**Как** разработчик, **я хочу** чтобы трассировка не врала, **чтобы** следующий
человек не принял счётчик вызовов за признак промаха мимо быстрого пути — как
это случилось при подготовке этой спеки.

Выигрыша в скорости здесь нет: заглушки — рудимент статической сборки, их
работу делает динамический PTX-путь. Это чистая гигиена.

**Шаги:**
1. Удалить оба модуля и их вызовы из `quantized/cuda.rs:1426,1438`.
2. Переписать печать `QWEN36_TRACE_MMQ` так, чтобы она называла выбранный путь
   (`vec` / `matmul` / `mma`), а не факт отказа несуществующего быстрого пути.

**Критерии приёмки:**
- [ ] Сборка проходит, замеры сценария 2 не изменились ни на один процент.
- [ ] На запросе из 40 токенов `QWEN36_TRACE_MMQ=1` печатает распределение по
      реально выбранным путям, и сумма совпадает с числом вызовов матмула.

## 5. Функциональные требования

### Must Have (P0)
- **FR-001**: Распакованный блок весов используется для всех строк пакета в
  пределах одного вызова ядра, при любом `ncols_dst` от 2 до 8.
- **FR-002**: Численный результат совпадает с прежним ядром побитово.
- **FR-003**: Путь `ncols_dst=1` не деградирует.

### Should Have (P1)
- **FR-010**: Покрыты Q4_K и Q6_K — кванты моделей, работающих на стенде.
- **FR-011**: Замер до/после снимается штатной обвязкой (`QWEN36_MTP_TIMING=1`)
  на обеих моделях, по три повтора на конфигурацию.

### Nice to Have (P2)
- **FR-020**: Порог `b*m ≤ 8` подтверждён или изменён по замеру.
- **FR-021**: Мёртвые заглушки `fast_mmvq`/`fast_mmq` убраны.
- **FR-022**: Тот же приём перенесён на Q2_K и IQ2 — кванты целевой 27B по
  BD-003, где распаковка дороже всего и приз, предположительно, больше.

## 6. Нефункциональные требования

- **Платформа**: CUDA, RTX 3060 (SM 8.6). Metal и CPU не трогаем.
- **Регистровое давление**: распакованный блок держится в регистрах; если
  занятость падает настолько, что ядро замедляется при `ncols_dst=1`,
  требование FR-003 имеет приоритет над FR-001.
- **Совместимость**: формат GGUF и раскладка весов не меняются, перекванта
  моделей не требуется.

## 7. Вне объёма

- Ядра для MoE (`moe/gguf.cuh`) — там своя развилка и свои типы.
- Матричный путь `mul_mat_q_mma` для префила (m > 8).
- Ускорение префила и кеш префикса — отдельный, и для агентской нагрузки более
  крупный, фронт.
- Q2_K/IQ2 в первой итерации: перенос приёма туда — FR-022, после замера на
  Q4_K/Q6_K.

## 12. Критерии успеха

- [ ] `verify(2)` падает не меньше чем на 0.8 мс на 4B Q4_K и 0.5 мс на

- [ ] MTP на 4B Q4_K перестаёт проигрывать базе: не хуже 70.5 ток/с против

- [ ] Ornith 9B: не хуже 44.5 ток/с против нынешних 43.7.

      должны решаться так же.
- [ ] Обычный декод (`ncols_dst=1`) не медленнее прежнего больше чем на 1%.

## Где на самом деле живёт стоимость проверки (2026-08-29, после закрытия темы)

Замер, поставленный партнёром уже после закрытия работы по mmvq, нашёл настоящую
статью расходов — и она в разы крупнее.

Развёртка по **длине последовательности** (не по `QWEN36_CTX`: он задаёт окно
пула, а не длину, и на коротких промптах ничего не меняет — первая попытка дала
плоские 4.46 / 4.63 / 4.66 и чуть не увела в ложный вывод):

| длина промпта | декод (MTP=0) | verify(2) | прирост 2-й строки |
|---|---|---|---|
| 452 токена | 13.87 мс | 20.38 | +6.51 |
| 32 685 токенов | 23.51 мс | 40.05 | **+16.54** |

Решающая арифметика: длинно-зависимая часть декода 23.51 − 13.87 = **9.64 мс**
(одно чтение 32k KV); длинно-зависимая часть прироста второй строки
16.54 − 6.51 = **10.03 мс**.

Числа совпадают. **Каждая строка проверки читает весь KV слота заново**, по
полной цене первого чтения: при k=2 KV читается дважды, линейно по k.

Отсюда масштаб: на 32k контекста перечитывание даёт около 10 мс из 40-мс
раунда — четверть. Для агентской нагрузки, где контекст десятки тысяч, это
основная статья, и она растёт с длиной диалога. Спор про распаковку кванта
касался фиксированных 4-6 мс, которые с длиной не растут, — то есть меньшей
части, и на модели она дала 0.2%.

Лечение (за партнёром): один вызов FA2 на k строк с causal-маской вместо k
построчных, чтобы K/V читались один раз. Новых ядер не требует.

## Слитая проверка: +5%, а не +30% (2026-08-30)

Первая реализация давала verify 40.15 → 28.05 на длинном промпте, но считала
неверно: принятие падало с 1.90 до 1.53, вывод расходился с эталоном с нулевого
символа, в тексте появлялось `'Anбыр'` вместо `1786`.

Причина оказалась не в маске, а в раскладке памяти Q. Требуемый адрес —
`((position * h_k + kv_head) * ngroups + group) * d`, вычислялся —
`((position + kv_head) * ngroups + group) * d`. Разные пары
`(position, kv_head)` перекрывались, включая записи в выход: гонка, отсюда
порча текста. Специальная маска была лечением не того и удалена целиком.

Правильная реализация — T позиций как батч из T последовательностей с
`seqlen_q = 1`, общая таблица страниц (`batch_stride = 0`), точные длины ключей
через накопительные seqlens. Тензорная сверка с построчным путём:
`max_abs_diff = 0` на обеих длинах.

| путь | verify, промпт 452 | verify, промпт 32 685 | E[m] |
|---|---|---|---|
| построчный | 20.06 | 40.31 | 1.925 / 1.900 |
| слитый | 17.75 (−11.5%) | 38.53 (−4.4%) | **1.925 / 1.900** |

Совпадение E[m] до третьего знака — подпись верного счёта.

Сквозная скорость, по три повтора:

| модель | построчный | слитый | |
|---|---|---|---|
| Qwen3.5-4B Q4_K | 62.0 | 65.3 | **+5.3%** |
| Ornith 9B Q6_K | 42.8 | 44.8 | **+4.7%** |

**Те 30% были куплены багом.** Корректный слитый путь экономит запуск ядра
(2.3 мс на коротком промпте), но кеш по-прежнему читается k раз: каждый элемент
батча читает свою длину. Один проход по KV требует того, что было удалено, —
причинной границы по позиции, сделанной верно, — и это отдельная работа.

Путь включается `QWEN36_VERIFY_FUSED=1`, `k = 1` не затронут.
