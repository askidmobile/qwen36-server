# Specification: Выгрузка экспертов MoE в pinned RAM с кэшем горячих экспертов в VRAM

**Дата:** 2026-09-04
**Приоритет:** P0
**Тип:** Extension (движок `yttri-forge/engine`: MoE-блок, загрузчик, ядра; MTP-загрузчик)

## 1. Проблема

Qwen3.6-35B-A3B (архитектура `qwen35moe`, 256 экспертов, 8 активных, 3B активных параметров) на RTX 3060 12 ГБ работает только в урезанном режиме. Замер 2026-09-04 на стенде yttri-win, файл `Qwen3.6-35B-A3B-UD-IQ2_XXS.gguf`:

| что лежит на GPU | МиБ |
| --- | --- |
| ствол blk.0–39, из них эксперты (`ffn_*_exps`) | 10 408, из них **9 624** |
| ствол без экспертов (внимание, DeltaNet, роутеры, shared-эксперты) | 784 |
| `output.weight` | 272 |
| MTP-слой blk.40 (не грузится, см. ниже) | 307 |
| свободно по `cudaMemGetInfo` после загрузки без MTP | **375** |

Из 375 МиБ пул KV получает 201 МБ, то есть окно 20 480 токенов. Для агентских задач (системные промпты 10–20K, диалоги 25–30K) модель непригодна. С MTP веса выросли бы до 10 988 МиБ, и пул не получил бы ничего.

Все известные обходы не работают:

- `GPU_LAYERS<999` кладёт на CPU целые слои, но бэкенд MoE выбирается один на модель по её устройству (`moe.rs::select_backend`), PTX-ядра CPU-тензоры экспертов не переварят; эталонный CPU-бэкенд — только диагностика.
- `UD-IQ1_M` меньше на 432 МиБ, но у него 20 блоков экспертов в IQ1_M, которых PTX-ядра MoE не поддерживают.
- Планер сервера (`src/vram_plan.rs`) считает веса как 0.95 × размер файла и отказывает до загрузки; сейчас обходится `NO_VRAM_PLAN=1`.
- MTP не грузится вовсе: `MtpProfile::read_and_validate` и `Qwen35Mtp::load` знают только плотный `qwen35` (ключи `qwen35.*`, FFN `ffn_gate/up/down` в `blk.0`), а nextn-слой этой модели — MoE в `blk.40` с экспертами, роутером и shared-экспертом.

При этом модель — MoE с 3B активных параметров: на каждом токене декода нужны 8 экспертов из 256 на слой, то есть 301 МБ весов из 9 624 МиБ. Держать в VRAM все эксперты ради 3 % обращений — расточительно именно на карте, где VRAM — узкое место.

## 2. Цель

На RTX 3060 12 ГБ сервер поднимает Qwen3.6-35B-A3B IQ2_XXS с окном 131 072 токенов и включённым MTP, эксперты живут в оперативной памяти стенда (64 ГБ), горячие эксперты кэшируются в освободившейся VRAM, и декод на одном слоте держится не ниже 40 ток/с (сегодня без выгрузки — 65). Выход модели при выгрузке совпадает бит в бит с выходом при резидентных экспертах: те же ядра читают те же байты.

## 3. Текущее состояние

**Движок `yttri-forge/engine/qwen35-batch/src/real/`:**

- `moe.rs` — `Qwen35MoeBlock`, `PackedExperts { gate, up, down: Arc<QTensor>, n_experts }`, `select_backend` (матрица поддерживаемых dtype: IQ2_XXS/XS/S, IQ3_XXS/S, IQ4_XS, Q8_0, Q2–Q6_K). Боевой путь `forward_ptx_cuda`: роутер → `gpu_softmax_topk` → `indexed_moe_forward_dual_cuda` (gate+up) → SiLU·up → `indexed_moe_forward_cuda` (down) → взвешенная сумма + shared. Ни одного D2H/H2D за шаг — именно поэтому блок целиком захватывается в CUDA-граф декода.
- `model_weights.rs` ~6651 — эксперты грузятся `load_heavy(...)` на устройство модели как `QTensor` с упаковкой `[n_experts, n, k]`. ~8817 — окно страничного пула считается как `свободная VRAM − VRAM_HEADROOM_MIB`.
- `adapter.rs` ~1466 — декод одним `cuGraphLaunch`; ~1942 — графовый префил чанка (`PGRAPH`), фиксация пути `PrefillPath` (paged↔eager внутри промпта запрещена).
- `mtp.rs` — `Qwen35Mtp::load` читает nextn-слой по префиксу `blk.{mtp_block}` с плотным FFN; `draft_graphed` захватывает черновик в граф.
- `model_profile.rs` 465–620 — `MtpProfile`, валидация только под `qwen35`; для текстового профиля `Architecture::Qwen35Moe` (строка 680) уже знает список MoE-тензоров.

**Ядра `yttri-forge/engine/candle-core` и `candle-kernels`:**

- `candle-core/src/quantized/cuda.rs` — `indexed_moe_forward`, `indexed_moe_forward_dual`, диспетчер по dtype; веса передаются одним базовым указателем `[num_experts, n, k]`.
- `candle-kernels/src/quantized.cu` ~6585 и ~7292 — `indexed_moe_forward_iq_f32` и `_dual`: адрес эксперта `all_weights + (expert_id · n + row) · blocks_per_row`. Это единственное место, где ядро «знает», что эксперты лежат подряд.
- `cudarc 0.19.7` — `alloc_pinned` (`cuMemHostAlloc` с флагами), `memcpy_htod_async`; отображение host-памяти в адресное пространство устройства доступно через `sys`.

**Сервер `Qwen3.6 27B/src/`:**

- `vram_plan.rs` — оценка весов по размеру файла, `compute_dynamic`; `config.rs::apply_vram_plan` с обходом `NO_VRAM_PLAN`.
- `api.rs` `/v1/models` — публикует квант, контекст, слоты, `capabilities.mtp`.

**Стенд:** RTX 3060 12 ГБ, PCIe Gen3 x16 (≈12 ГБ/с), 64 ГБ RAM (37 свободно), Windows WDDM (перерасход VRAM не падает, а молча уходит в системную память и замедляет втрое — детектируется через GPU Process Memory Shared Usage).

**Проверочный инструментарий, который уже есть:** `tools/logits_parity.py` (top-10 логпробов двух серверов), реплей записанной сессии `.tmp-test/ornith_exact_hero_replay.mjs` с детектором подмен, `multiturn.ps1` (многоходовой прогон с prefix cache), `qwen35_mtp_gate` (шлюз MTP), `qwen36_inspect`.

## 4. Сценарии

> Каждый сценарий — самостоятельный инкремент. Сценарии 1–3 вместе дают MVP; порядок выкладки — по номерам.

### Сценарий 1: Эксперты в RAM, контекст 131K (P1)

**Как** владелец стенда, **я хочу** запустить 35B-A3B с экспертами в оперативной памяти, **чтобы** получить окно 131 072 токена на карте 12 ГБ без потери точности.

**Шаги:**

1. Владелец ставит в `.env` размещение экспертов в RAM (или оставляет `auto`), `CTX=131072`, `MTP=0`, перезапускает задачу.
2. Загрузчик кладёт `ffn_gate/up/down_exps` всех 40 слоёв в pinned host-память, отображённую для устройства; остальной ствол и `output` — в VRAM как сегодня.
3. Движок строит на устройстве таблицу указателей на экспертов; ядра адресуют эксперта через таблицу.
4. Окно пула считается от освободившейся VRAM; сервер объявляет 131 072.
5. Результат: префил и декод работают, логиты совпадают с резидентным режимом.

**Критерии приёмки:**

- [ ] Given IQ2_XXS и `CTX=131072` на 3060, when сервер стартует, then в логе `[kv] paged pool: window=131072`, Dedicated Usage процесса не выше VRAM минус `VRAM_HEADROOM_MIB`, а GPU Process Memory Shared Usage не превышает размер pinned-хранилища + 100 МиБ (отображённая pinned-память под WDDM учитывается как shared).
- [ ] Given один и тот же промпт 4 096 токенов, when сравниваем top-10 логпробов последней позиции при экспертах в RAM и в VRAM (`tools/logits_parity.py`; обе стороны с `PGRAPH=off`, одинаковыми `PREFILL_CHUNK` и `FA_SPLITS`, иначе различается путь внимания, а не эксперты), then максимальная разница равна 0.
- [ ] Given промпт 120 000 токенов, when запрос уходит на сервер, then ответ приходит с `finish_reason=stop|length`, без HTTP 500 на границе окна.
- [ ] Given неподдерживаемый dtype экспертов или нехватка host-памяти под pinned-хранилище, when сервер стартует, then загрузка завершается ошибкой с явным текстом причины, а не молчаливым откатом на VRAM.

### Сценарий 2: Кэш горячих экспертов держит скорость (P1)

**Как** пользователь агента, **я хочу**, чтобы декод при выгрузке не проседал ниже 40 ток/с, **чтобы** выгрузка не превращала модель в медленную.

**Шаги:**

1. После сценария 1 движок выделяет под кэш экспертов всю VRAM, оставшуюся после пула (создан при загрузке), стейджинга, резерва графов и запаса.
2. На каждом шаге декода ядра читают попадания из VRAM, промахи — напрямую из pinned RAM по PCIe (zero-copy); графы декода остаются захваченными.
3. После шага хост читает след маршрутизации (выбранные эксперты по слоям), поднимает промахи в свободные или вытесненные по LRU слоты на боковом потоке и обновляет таблицу указателей до следующего шага.
4. На префиле перед экспертами каждого слоя хост читает маршрутизацию чанка и поднимает недостающих экспертов одним пакетом: в свободные слоты кэша, а переполнение — в стейджинг размером в один слой; из кэша префил не вытесняет, ядра читают только VRAM.
5. Результат: доля попаданий растёт по ходу генерации, скорость держится.

**Критерии приёмки:**

- [ ] Given контекст 4 096 токенов и один слот, when генерируется 1 000 токенов, then средняя скорость декода ≥ 40 ток/с, и в логе строка статистики кэша с долей попаданий.
- [ ] Given промпт 32 768 токенов, when идёт префил, then средняя скорость префила ≥ 150 ток/с.
- [ ] Given графы декода включены (`CUDA_GRAPHS=1`), when эксперты в RAM, then в логе `[graphs] captured` и ни одной строки ухода на eager из-за выгрузки.
- [ ] Given 50 запросов подряд, when замеряем VRAM после каждого, then разброс не более 64 МиБ (кэш не растёт за бюджет).

### Сценарий 3: MTP на MoE (P1)

**Как** пользователь агента, **я хочу** включить MTP на 35B-A3B, **чтобы** декод стал быстрее без изменения распределения ответов (BD-029).

**Шаги:**

1. Владелец ставит `MTP=1`, `MTP_PATH` указывает на тот же GGUF (nextn-слой упакован внутри, `blk.40.*` и `blk.40.nextn.*`).
2. Профиль MTP принимает архитектуру `qwen35moe`: метаданные по префиксу `qwen35moe.*`, номер nextn-блока — последний блок, набор тензоров — внимание + роутер + эксперты + shared-эксперт + `nextn.*`.
3. Черновой слой считает FFN тем же MoE-блоком, что и ствол; эксперты MTP-слоя (307 МиБ) всегда резидентны в VRAM. При выгрузке адаптивная ширина драфта включена по умолчанию: проверка черновика гонит через ствол k+1 токенов, объединение экспертов на слой растёт до 8 × (k+1), и трафик промахов на шаг умножается.
4. Результат: MTP грузится при старте (BD-030), черновик и проверка работают на 131K.

**Критерии приёмки:**

- [ ] Given `MTP=1` и путь на тот же GGUF, when сервер стартует, then в логе загрузка MTP без ошибок валидации и `/v1/models` показывает `mtp.available=true`.
- [ ] Given шлюз `qwen35_mtp_gate` на трёх промптах, when сравниваем выход с MTP и без, then расхождения только в позициях с разрывом кандидатов ниже порога шлюза (как для плотных моделей по BD-029).
- [ ] Given контекст 4 096 и один слот, when декод с MTP, then скорость не ниже декода без MTP на том же контексте, и в логе доля принятых черновых токенов.

### Сценарий 4: Наблюдаемость размещения (P2)

**Как** владелец, **я хочу** видеть, где лежат эксперты и как работает кэш, **чтобы** настраивать бюджет без чтения кода.

**Критерии приёмки:**

- [ ] Given сервер запущен, when читаем `/v1/models`, then в расширениях есть размещение экспертов (`vram`/`ram`), размер кэша в МиБ и число слотов кэша.
- [ ] Given идёт генерация, when читаем лог, then раз в N шагов строка с долей попаданий по декоду и объёмом подъёмов по префилу за окно.

### Сценарий 5: Автовыбор размещения (P2)

**Как** владелец, **я хочу** не переключать размещение руками при смене модели, **чтобы** Ornith и 35B-A3B работали с одним `.env`.

**Критерии приёмки:**

- [ ] Given `MOE_EXPERTS=auto` и модель, чей ствол с `output` и запасом помещается в VRAM, when сервер стартует, then эксперты резидентны (как сегодня), в логе решение и числа.
- [ ] Given `MOE_EXPERTS=auto` и 35B-A3B на 3060, when сервер стартует, then эксперты в RAM, в логе решение и числа.

## 5. Функциональные требования

### Must Have (P0)

- **FR-001** Размещение: маршрутизируемые эксперты (`ffn_gate_exps`, `ffn_up_exps`, `ffn_down_exps`) каждого MoE-слоя ствола хранятся в pinned host-памяти, отображённой в адресное пространство устройства; роутер, shared-эксперт, внимание, DeltaNet, нормы и `output` размещаются как сегодня; `token_embd` (272 МиБ) при выгрузке копируется в обычную RAM, а не читается из mmap на каждом токене — под давлением памяти (pinned + prefix cache) страницы файла вытесняются, и каждый токен уходил бы на диск.
- **FR-002** Таблица указателей: для каждой матрицы каждого слоя на устройстве лежит массив из `n_experts` адресов; ядра `indexed_moe_forward` и `_dual` берут адрес эксперта из таблицы, а не как `base + id·stride`. Резидентный режим использует ту же таблицу (все адреса в VRAM).
- **FR-003** Тождественность: при любом размещении выход MoE-блока бит в бит совпадает с резидентным (те же ядра, те же байты); квантованные данные экспертов не перекодируются.
- **FR-004** Декод: промахи читаются ядрами напрямую из host-памяти, без синхронизаций и без выхода из CUDA-графа; след маршрутизации шага доступен хосту после шага. След покрывает весь батч форварда: T до ширины драфта MTP плюс один (проверка черновика) и все B слотов, а не один токен. След пишется явным копированием внутри графа в постоянный буфер `[слой][B×T][k]`, а не читается из временных тензоров top-k: пул графа переиспользует их адреса, и к концу прогона ids ранних слоёв уже перезаписаны.
- **FR-005** Префил: перед экспертами каждого слоя хост получает объединение выбранных экспертов чанка, поднимает недостающих одним пакетом на VRAM-слоты и обновляет таблицу. Допускается одна синхронизация на слой на чанк. Переполнение сверх свободных слотов кэша поднимается в стейджинг — VRAM-буфер размером в один полный слой экспертов (максимум по слоям, у IQ2_XXS ≈300 МиБ), один на модель и переиспользуемый послойно; ядра префила читают только VRAM, zero-copy на префиле нет (хвостовой эксперт читался бы по PCIe столько раз, сколько токенов его выбрали — при выровненном роутинге это дороже подъёма в разы). Префил не вытесняет из кэша: подъём только в свободные слоты и в стейджинг, иначе LRU при объединении больше ёмкости перекачивал бы весь кэш на каждом чанке. Записи таблицы для экспертов в стейджинге действуют только на время слоя: порядок «записать адреса стейджинга → посчитать эксперты слоя → вернуть записи на кэш или host» обязателен, иначе первый шаг декода после префила прочитает затёртый стейджинг. После префила кэш пополняется экспертами последнего чанка в порядке убывания частоты обычным LRU-вытеснением. При выгрузке чанк префила не меньше 256: меньшее значение `PREFILL_CHUNK` поднимается до 256 со строкой в логе, иначе число синков и объём подъёмов на токен растут кратно.
- **FR-006** Кэш: VRAM-слоты экспертов (эксперт = его gate+up+down) с бюджетом «свободная VRAM после весов и пула минус `VRAM_HEADROOM_MIB` минус резерв графов», переопределяемым настройкой; вытеснение LRU. Стейджинг на один слой (FR-005) выделяется всегда и отдельно от кэша; сам кэш может быть нулевым (чистый zero-copy декод — сценарий 1). Порядок выделения при выгрузке: ствол без экспертов и `output`, затем пул на объявленный `CTX` — он создаётся сразу при загрузке, а не лениво на первом запросе, как сегодня, иначе кэш заберёт его память, — затем стейджинг, затем кэш из остатка минус `VRAM_HEADROOM_MIB` и резерв графов. Если стейджинг или пул не помещаются — fail-closed с числами. Подъём промахов декода — асинхронно на боковом потоке после шага и без задержки следующего шага: пока копия не завершена, ядра читают промах zero-copy. Порядок через события: (1) запись в таблицу «вытесняемый эксперт → host», (2) копия нового эксперта в слот, (3) запись «новый эксперт → слот»; слот не переиспользуется, пока (1) не выполнен на основном потоке. Подъёмов не больше `EXPERT_PROMOTE_PER_STEP` экспертов за шаг (умолчание 64: ≈60 МБ, ≈5 мс PCIe), чтобы прогрев холодного кэша не насыщал PCIe поверх zero-copy чтений; прогрев сходится за несколько сотен шагов. Доля попаданий считается по выборам (слой, токен, k): попадания к сумме попаданий и промахов. Раз в N шагов лог печатает долю попаданий декода, объём подъёмов префила за окно и ход прогрева; при старте — расчётное f (доля резидентных экспертов) и WARN, если f ниже целевого по §6.
- **FR-007** Графы декода остаются включёнными при выгрузке; графовый префил (`PGRAPH`) при выгрузке принудительно выключается: явный `PGRAPH=on` — не ошибка, а строка WARN (FR-005 требует хост-логики между слоями). Стартовая сводка печатает эффективные значения `PGRAPH`, `PREFILL_CHUNK`, размещения и бюджета кэша, а не содержимое `.env`.
- **FR-008** Fail-closed: нехватка host-памяти под pinned-хранилище, невозможность отобразить его для устройства, неподдерживаемый dtype экспертов — ошибка старта с текстом причины. Молчаливого отката на другое размещение нет.
- **FR-009** Настройка размещения — одна переменная без префиксов: `MOE_EXPERTS=vram|ram|auto`; бюджет кэша — `EXPERT_CACHE_MIB` (по умолчанию автоматический). Умолчание `auto`. `ram` на модели без маршрутизируемых экспертов — не ошибка, а строка в логе «размещение не применяется»; на Metal и CPU `ram` — ошибка старта. `EXPERT_CACHE_MIB` больше доступного — ошибка старта с числами, а не молчаливое урезание; `EXPERT_CACHE_MIB` при `vram` игнорируется со строкой в логе. `MOE_BACKEND=reference` вместе с `ram` — ошибка старта: выгрузка существует только для PTX-пути.
- **FR-010** Планер сервера учитывает размещение: при экспертах в RAM оценка весов на GPU исключает `ffn_*_exps` и nextn-слой без MTP; `NO_VRAM_PLAN=1` перестаёт быть обязательным для 35B-A3B.
- **FR-011** MTP на MoE: профиль MTP принимает `qwen35moe` (метаданные по префиксу архитектуры, nextn-блок = последний, MoE-набор тензоров), черновой слой считает FFN тем же `Qwen35MoeBlock`; эксперты MTP-слоя всегда резидентны в VRAM; при выгрузке адаптивная ширина драфта включена по умолчанию (проверка k+1 токенов умножает промахи); загрузка при старте по BD-030; распределение выхода по BD-029.
- **FR-012** Выгрузка и горячая смена модели освобождают pinned-хранилище, слоты и таблицы до сброса CUDA-контекста; после двух смен Ornith ↔ 35B-A3B подряд host RAM и VRAM возвращаются к исходным значениям с точностью до 256 МиБ.

### Should Have (P1)

- **FR-020** Наблюдаемость: `/v1/models` публикует размещение экспертов, бюджет и число слотов кэша, текущую долю попаданий; сводка кэша при выгрузке модели (строка попаданий в логе — уже в FR-006).
- **FR-021** Автовыбор: `auto` кладёт эксперты в RAM только когда ствол с экспертами, `output`, MTP-слой (если включён), пул на объявленный `CTX`, запас и резерв графов не помещаются в свободную VRAM (та же формула пула, что у движка); решение, числа и расчётное f печатаются при старте, WARN при f ниже целевого (например при `CTX=262144`).

### Nice to Have (P2)

- **FR-030** Прогрев: при старте кэш заполняется экспертами по сохранённому профилю частот предыдущих запусков.
- **FR-031** Многослотовость: `SLOTS>1` при выгрузке работает корректно (след и подъём покрывают B слотов по FR-004), но цель 40 ток/с относится к одному слоту; лог при старте печатает расчётное f для заданных `SLOTS` и `CTX`. Деление бюджета кэш/пул по настройке — заготовка (сегодня один слот, D-002).

## 6. Нефункциональные требования

- **Скорость.** Один слот, 3060, IQ2_XXS: декод ≥ 40 ток/с на контексте 4 096; префил ≥ 150 ток/с на промпте 32 768; старт с раскладкой в RAM ≤ 3 минут при прогретом файловом кэше.
- **Бюджет кэша от полосы PCIe.** Роутинг у Qwen3-MoE выровнен обучением: за длинную генерацию один поток токенов использует почти всех экспертов слоя, поэтому доля попаданий определяется долей резидентных экспертов f, а не политикой вытеснения. Трафик промахов ≈ (1 − f) × 301 МБ на токен. Бюджет токена при 40 ток/с — 25 мс, из них ≈15 мс вычисления (сегодняшние 65 ток/с), значит на промахи остаётся 10 мс: f ≥ 1 − B × 10 мс / 301 МБ, где B — полоса zero-copy. При 12 ГБ/с f ≥ 0.60 (кэш ≥ 5.8 ГБ), при 8 ГБ/с f ≥ 0.73 (≥ 7.0 ГБ), при 6 ГБ/с f ≥ 0.80 (≥ 7.7 ГБ, столько на стенде нет). Это условие цели, а не предпочтение: оно и делает D-002 (один слот) обязательным.
- **Бюджет VRAM на стенде** (по замеру 2026-09-04: при занятых 11 320 МиБ CUDA видел 375 свободных, то есть процессу доступно ≈11 350 МиБ):

  | статья | МиБ |
  | --- | --- |
  | ствол без экспертов | 784 |
  | `output` | 272 |
  | MTP-слой (резидентен) | 307 |
  | контекст CUDA | ≈290 |
  | пул KV на 131 072 (int8, 10 слоёв внимания) | ≈1 290 |
  | `VRAM_HEADROOM_MIB` | 512 |
  | резерв графов | 512 |
  | стейджинг (один слой: эксперты blk.39, без внимания) | ≈300 |
  | **остаток под кэш** | **≈7 050 → f ≈ 0.73** |

  При запасе 1 024 кэш ≈6 540 (f ≈ 0.68). Отсюда порог ворот 0: 8 ГБ/с — минимальная полоса, при которой доступный кэш ещё даёт 40 ток/с.
- **Подъём на префиле лежит на критическом пути.** Роутинг слоя L+1 неизвестен до конца слоя L, поэтому копирование нельзя перекрыть вычислениями. Ожидаемая цена при f ≈ 0.73: ≈(1 − f) × 9.6 ГБ / 12 ГБ/с ≈ 0.22 с на чанк в 512 токенов при ≈1.7 с вычислений (≈13 %); на холодном кэше первые чанки дороже до ≈0.8 с, пока кэш заполняется. Это ожидаемое поведение, а не дефект; спекулятивная предвыборка — вне рамок.
- **VRAM.** Без подкачки WDDM: Shared Usage процесса ≤ размер pinned-хранилища + 100 МиБ на всём прогоне (отображённая pinned-память под WDDM учитывается как shared, поэтому прежний детектор «≤ 100 МиБ» здесь не работает); Dedicated Usage ≤ VRAM − `VRAM_HEADROOM_MIB`. Кэш по замыслу занимает всё оставшееся, так что верхней границы «занято по nvidia-smi» нет — границу задаёт запас.
- **Host RAM.** Pinned-хранилище ≤ размер экспертов + 256 МиБ и выделяется по слою и по матрице (около 120 буферов до 110 МиБ, а не один блок на 9.6 ГБ — под Windows он может не пройти). Суммарная RAM процесса ≤ размер GGUF + `PREFIX_CACHE_MIB` + 2 ГБ (файл остаётся mmap, эксперты в pinned, двойного удержания после загрузки нет): на стенде это ≈ 11 + 8 + 9.6 + 0.3 (`token_embd`) ≈ 29 ГБ из 64. При старте проверяется, что свободной физической памяти на момент запуска не меньше размера экспертов + `PREFIX_CACHE_MIB` + 2 ГБ, иначе fail-closed. Требование к RAM записывается в `scripts/README.md` стенда: pinned-память не свопится, и параллельные сборки другого агента должны его учитывать.
- **Стабильность (BD-008).** Реплей записанной сессии и 8-ходовой прогон с prefix cache на 131K — без подмен токенов, без ухода на eager, без роста VRAM.
- **Совместимость.** Windows+CUDA — первично (BD-011). Metal и CPU не меняют поведения: там единая память, размещение `ram` отвергается с ошибкой, `auto` даёт `vram`. Плотные модели (Ornith, 27B) не затрагиваются. Поддерживаемые dtype экспертов — как в `select_backend`; IQ1_M/IQ1_S вне рамок.
- **Ворота риска.** Первый измеримый шаг реализации — то же ядро `indexed_moe_forward` (T=1, k=8) на device-mapped host-весах против VRAM под WDDM; полоса считается по фактическому времени ядра, синтетический memcpy не годится (ядро читает структуры по 66 байт с шагом). Замер делается на всех 9.6 ГБ отображённой pinned-памяти, не на образце; ворота подтверждают, что в контексте cudarc отображение работает (указатель `cuMemHostGetDevicePointer` совпадает с host-указателем при UVA либо контекст создан с флагом отображения) и выбирают флаги аллокации по замеру (с write-combined и без). Если полоса < 8 ГБ/с, вариант D-005 пересматривается до начала остальной работы (см. §11).

## 7. Модель данных (концептуально)

```
Entity: ExpertStore (на слой)
  - layer: usize
  - gate, up, down: pinned host-буферы [n_experts × expert_bytes], device-mapped
  - expert_bytes_{gate,up,down}: usize (по dtype матрицы)
  - dtype_{gate,up,down}: GgmlDType

Entity: ExpertSlotPool (на слой, VRAM)
  - capacity: usize (слотов; бюджет / размер эксперта)
  - slot[i] → (gate, up, down) одного эксперта
  - relation → ExpertStore (источник байтов)

Entity: PointerTable (на слой, на матрицу, устройство)
  - entry[expert_id]: адрес (VRAM-слот или host-mapped)
  - relation → ExpertSlotPool, ExpertStore

Entity: CacheDirectory (на слой, хост)
  - resident: expert_id → slot
  - lru: порядок использования
  - pending: подъёмы, поставленные на боковой поток (событие завершения)
  - stats: hits, misses, promotions_bytes

Entity: Staging (VRAM, одна на модель)
  - capacity: max по слоям (n_experts × expert_bytes слоя)
  - занята только на время экспертов текущего слоя префила
  - relation → ExpertStore (источник байтов)

Entity: RouteTrace (устройство → хост)
  - ids[layer][token][k]: выбранные эксперты последнего шага/чанка
  - читается хостом после шага декода и перед экспертами слоя на префиле

Entity: Placement (настройка)
  - mode: vram | ram | auto
  - cache_budget_mib: Option<usize>
```

## 8. Настройка и наблюдаемость

Переменные `.env` (без префиксов, как и остальные):

```env
MOE_EXPERTS=auto          # vram | ram | auto (умолчание)
EXPERT_CACHE_MIB=         # пусто = вся VRAM после весов, пула и стейджинга минус VRAM_HEADROOM_MIB и резерв графов
EXPERT_PROMOTE_PER_STEP=64 # потолок подъёмов промахов за шаг декода
PREFILL_CHUNK=512         # при выгрузке минимум 256, меньшее поднимается со строкой в логе
```

Строки лога при старте и работе (форма ориентировочная):

```
[moe] experts: ram (9624 MiB pinned, 40 layers × 256), reason: trunk+output+pool+headroom 12 492 MiB > free 11 330 MiB
[moe] staging: 300 MiB (blk.39); cache: 7 050 MiB → ≈7 500 slots (≈188 на слой из 256), f=0.73 (target ≥ 0.60 при 12 ГБ/с), promote ≤ 64/step
[kv] paged pool: window=131072 ...
[pg] disabled: experts in ram (prefill needs per-layer promotion)
[moe] decode hit 91.3% (last 200 steps), prefill promoted 1 230 MiB (last chunk window)
```

`/v1/models` → `capabilities.moe = { experts: "ram", cache_mib: 7900, cache_slots: 8400 }`.

## 9. Архитектура

```mermaid
graph TD
  G[GGUF IQ2_XXS] --> L[Загрузчик model_weights]
  L -->|внимание, DeltaNet, роутеры, shared, output| V[(VRAM)]
  L -->|ffn_*_exps| H[(Pinned RAM, device-mapped)]
  L --> T[PointerTable на слой]
  T --> V
  T --> H

  subgraph Декод: один cuGraphLaunch
    R[Роутер + top-k на GPU] --> K[indexed_moe_forward via PointerTable]
    K -->|попадание| S[(VRAM-слоты кэша)]
    K -->|промах, zero-copy| H
    R --> RT[RouteTrace]
  end
  RT -->|после шага| D[CacheDirectory LRU]
  D -->|подъём промахов, боковой поток| S
  D -->|обновление| T

  subgraph Префил: eager, на каждый слой
    R2[Роутер чанка] --> U[Объединение экспертов слоя]
    U -->|в свободные слоты| S
    U -->|переполнение| ST[(Стейджинг: один слой)]
    S --> K2[indexed_moe_forward только из VRAM]
    ST --> K2
  end

  M[MTP nextn-слой: тот же MoE-блок] -->|эксперты резидентны| V
  P[Планер сервера vram_plan] -->|веса на GPU без exps| L
```

Потоки: основной поток вычислений (графы и eager), боковой поток подъёмов; порядок «подъём завершён → таблица обновлена → следующий запуск графа» гарантируется событиями. Таблица — единственная точка, через которую ядра узнают адрес; резидентный режим отличается только содержимым таблицы.

## 10. Вне рамок

- Многослотовый бюджет и балансировка кэш/пул при `SLOTS>1` (FR-031 — нишевая заготовка; сегодня один слот по D-002).
- Поддержка IQ1_M/IQ1_S в PTX-ядрах MoE; переквантование файлов.
- Вычисление экспертов на CPU (путь llama.cpp `-ot exps=CPU`); предсказание экспертов следующего шага и упреждающая подкачка.
- Графовый префил при выгрузке (PGRAPH остаётся для резидентного режима).
- Выгрузка чего-либо кроме маршрутизируемых экспертов (внимание, DeltaNet, `output`, KV — есть отдельная спека многоуровневого KV).
- Metal/CPU-бэкенды: поведение не меняется.
- Диск как третий уровень для экспертов.

## 13. Критерии успеха

- [x] **Ворота 0.** Все 9.6 ГБ экспертов выделены как pinned и отображены для устройства (проверка потолка отображаемой host-памяти под WDDM), ядро `indexed_moe_forward` (T=1, k=8) на этих весах против VRAM на 3060: эффективная полоса по времени ядра ≥ 8 ГБ/с — минимум, при котором расчётный кэш (f ≈ 0.73, §6) даёт 40 ток/с; попутно подтверждено отображение в контексте cudarc и выбраны флаги аллокации. Ниже — пересмотр D-005 до начала остальной работы. — **выполнено 2026-09-04 (`moe_zero_copy_bench`): 8644 МиБ маршрутизируемых экспертов в 120 pinned-буферах DEVICEMAP; полоса mapped 10.61 ГБ/с против VRAM 77.5 ГБ/с (порог 8 пройден); флаги — без WRITECOMBINED; UVA dev==host без WC.**
- [ ] **Ворота 0б (решение пользователя).** До начала работ — реплей записанной сессии на нынешнем окне 20K с IQ2_XXS: качество приемлемо → P0 подтверждён; иначе приоритет пересматривается, механизм остаётся полезным для других MoE-моделей и карт.
- [ ] Сервер стартует с IQ2_XXS, `CTX=131072`, `MTP=1` на 3060: `[kv] paged pool: window=131072`, MTP загружен, Dedicated Usage ≤ VRAM − `VRAM_HEADROOM_MIB`, Shared Usage ≤ pinned + 100 МиБ.
- [x] Паритет логитов с резидентным режимом на промпте 4 096 токенов: максимальная разница top-10 логпробов = 0 (`tools/logits_parity.py`, оба сервера с `MTP=0`, `PGRAPH=off`, одинаковыми `PREFILL_CHUNK` и `FA_SPLITS`). — **выполнено 2026-09-04**: ram-vs-vram на одном exe (выгрузка против резидента), 4 096 токенов, Δ = 0.0.
- [ ] Декод ≥ 40 ток/с на контексте 4 096 и ≥ 25 ток/с на контексте 100 000 (один слот, без MTP); доля попаданий на генерации 1 000 токенов ≥ 60 %; числа записаны в отчёт.
- [ ] Две смены модели Ornith ↔ 35B-A3B подряд через `/admin/switch`: host RAM и VRAM возвращаются к исходным с точностью до 256 МиБ; третий запуск 35B-A3B отвечает на пробный запрос.
- [ ] Префил ≥ 150 ток/с на промпте 32 768; графы декода захвачены; PGRAPH выключен строкой лога.
- [ ] Реплей записанной сессии (детектор подмен) и 8-ходовой прогон с prefix cache на 131K — чисто; VRAM за 50 запросов в пределах 64 МиБ.
